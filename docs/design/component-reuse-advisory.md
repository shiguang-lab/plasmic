# MCP 编辑后的组件复用建议

状态：设计提案，尚未实现。范围是 Agent 通过原生编辑工具创建或修改原型后，由工具返回可复核的组件候选；保留自定义 UI，替换决定由 Agent 结合当前需求作出。

## 目标和成功条件

当某个已编辑区域可能由现有组件承载时，在成功回执中指出具体目标、观察依据、真实候选和待确认项，促使 Agent 再做一次组件选择。编辑不因此失败，不自动替换，不要求用户逐项确认，也不增加业务页面里的提示。

成功条件：

1. 每个候选都能定位到当前项目实际可引用的组件及当前版本的契约；不把名称搜索结果说成可直接替换。
2. 对原生控件、明确的 ARIA 控件及可静态辨认的交互结构发出建议；普通内容、标准组件内部结构和证据不足的布局不被认定为违规。
3. 同一批次按最终结果分析，后续事件绑定、复制和本地组件定义修改均在覆盖范围内；中途已删除或已替换的结构不产生过时建议。
4. Agent 可以替换、保留自定义或记录尚未核实；重新读取 skill 本身不算完成复核。
5. 检测失败不改变已成功的编辑结果；不因建议重复执行成功操作。
6. 用真实多轮 Agent 对照实验检验是否增加了规则读取和正确处理，不能只根据回执出现了文字就宣称有效。

## 现有基础及缺口

| 已有能力 | 当前边界 |
| --- | --- |
| [原生批次编辑](../../platform/wab/src/wab/client/copilot/index.ts)统一处理单次编辑、批次及本地 AI 编辑 | 没有编辑后组件复用建议；当前身份差异主要记录 UUID，不能单凭它发现旧节点新增交互 |
| [编辑回执](../../platform/wab/src/wab/shared/copilot/mutation-receipt.ts)包含 created、目标身份及 messages | 精确的候选和判断依据需要小型结构化输出，不能塞入完整组件模型 |
| [运行时契约读取](../../platform/wab/src/wab/shared/copilot/model-read.ts)提供真实 Props、Slots、事件签名等 | 属性结构不等于业务用途；动态元数据不能通过执行回调来发现 |
| [组件库查询](../../platform/wab/src/wab/client/copilot/libraries.ts)搜索名称、描述、导入名、分类 | 查询的是最新发布模型，不能用它证明当前安装版本具有同样契约；文本匹配不是适配结论 |
| [组件选择检查](../../ai/plasmic/scripts/verify_selection.py)具有当前管理端套件的角色映射 | 是套件特定的要求，不能直接升级为所有项目的复用规则 |
| [结构检查](../../ai/plasmic/scripts/verify_structure.py)识别原生功能标签、ARIA 和点击目标 | 是事后校验；无法仅凭 CSS 判断假 Tabs，也不能证明自定义实现不合理 |
| [规则索引](../../ai/plasmic/scripts/rules_manifest.py)从各库 rules.json 得到注册名与规则文档的对应 | 还没有通用的检测模式到候选组件映射 |

当前未提供统一的业务语义能力标签，不能通过简单搜索或“有 onClick”自动证明一个组件适配。现有任务计划也未自动传入每次 MCP 编辑；第一版不能假定 MCP 能读取 Agent 的对话、源需求、已读规则或本地计划文件。

## 核心判断：把四件事分开

一次建议必须分别回答：

1. **观察到什么**：目标区域有哪些原生标签、显式语义、状态、事件和内容结构。
2. **候选是否实际可用**：项目当前能否引用该组件，其注册是否加载、契约是否可读、所需父级是否具备。
3. **为什么相关**：受版本管理的候选索引或组件元数据表明它可能承载该类用途，且契约提供相关接口。
4. **目标区域是否已复用**：该区域是否已经由同类组件或包含该类组件的组合承载。

满足以上条件，工具也只得出“值得评估的复用候选”。业务行为、视觉要求、特殊交互和用户明确选择是否允许替换，留给 Agent。输出不设置 replaceable:true，不把检测置信度当成业务正确性的概率。

## 一、从最终模型识别目标用途

读取 Studio 的 Tpl 模型及原生交互，覆盖保存模型里的变体与隐藏分支；不扫描组件渲染出来的 DOM，不执行用户表达式或业务事件。

| 模式 | 可以使用的证据 | 边界 |
| --- | --- | --- |
| 操作入口 | button；role=button 且存在业务事件；普通节点上的独立操作事件 | 普通容器点击仅为弱信号；整卡跳转、拖动、画布命中区不自动归为 Button |
| 值输入 | input 的静态 type、textarea、select，以及显式 textbox/combobox 等语义 | input[type=number] 只能证明数值输入形态，不能证明业务值不是带前导零的标识符；不据此决定 InputNumber |
| 内容切换 | 成组 tab/tablist；或多个触发器给同一状态写入互斥常量，内容分支读取同一状态 | 仅有横排文字、下划线、active 类名或名为 Tabs 的节点不足；复杂 customFunction 不猜测 |
| 重复记录 | table 及其行列；或 grid/row/cell 的完整语义结构 | CSS grid、重复卡片、只读键值组不自动映射成 Table |
| 覆盖层 | dialog/aria-modal、显式开关状态及内容关联 | 不由 fixed、高 z-index、阴影推断 Modal；浮动工具栏不等于弹窗 |
| 业务提交区域 | form、实际提交事件与多个字段的所有权 | 不因若干 Input 相邻就推荐 Form；Form 与 SearchForm 的业务区别须看需求 |

显式原生结构属于强证据；静态可证明的结构与事件组合属于中等证据；名称、文案、尺寸、颜色和单个模糊点击属于弱证据。第一版只对强证据和明确列入测试的中等模式输出建议。

处理结构时先识别完整区域，再识别其内部独立操作。例如 tablist 内每个 tab 的点击是内容切换的一部分，不对每个 tab 再重复推荐 Button。表格单元格中独立的“删除”操作仍可单独建议。

状态关联仅解析已知原生动作或可静态证明的表达式结构；不执行 JS，不用字符串中含有 active/open 等词作为关联证据。无法证明就保留 unknown。

## 二、怎样发现真实候选

### 当前项目是可用性的事实来源

候选集合由本地可复用组件、已安装的直接/传递依赖和当前有效的代码组件注册构成，使用组件 UUID、来源项目和实际安装版本确定身份。页面、画板 Frame、全局 Context 不作为普通可插入候选。

代码组件须存在当前有效注册；导入模型存在但注册尚未加载时，不宣称可用。普通设计组件不要求代码注册，但须能通过当前项目的原生组件引用与契约读取路径定位。子组件必须检查真实父级或 Slot 约束，不能把 Table.Column、Form.Item 当独立 Table/Form 推荐。

第一版自动分析只使用当前项目集合，不逐次查询整个在线商店、不下载最新发布包、不自动安装或升级。没有候选时表示“本轮未找到已验证候选”，不表示平台不存在相关组件；Agent 仍可主动调用现有组件库搜索。

### 用途索引提供稳定匹配，文本检索只补充线索

建议在已有库 rules.json 中加入可选的 `reuseHints`，明确列出注册名和检测模式，由构建产物提供给原生编辑层。索引只描述候选用途和规则入口，不复制 Props、默认值、状态或事件签名，不写入设计模型，不建立另一套面板属性模型。

拟议数据示例，尚不是现有规则格式：

```json
{
  "components/button.md": {
    "registrations": ["plasmic-antd6-button"],
    "reuseHints": [
      {"registration": "plasmic-antd6-button", "patterns": ["action"]}
    ]
  }
}
```

每个提示项的注册名必须属于同一文档的 registrations，关联文档从现有索引获得；子组件按实际用途独立声明，不把整份文档中的所有注册都赋予相同用途。构建时检查模式名、注册名及文档存在性，并输出索引内容哈希，避免服务端再维护一份组件名映射。索引随对应原生编辑构建发布；Agent 所用规则资源与索引的版本/内容不一致时，先重新解析适用资源，不能把旧文档的配置要求应用到当前组件。

该索引不改变现有管理端 ROLE_COMPONENTS 的验收语义。初始覆盖有规则资料的库，匹配前再与当前项目实际集合求交；项目没有安装某库，就不会因索引中有该名字而报告“可用”。不同库的同名 Button 依靠真实身份区分。

未进入索引的业务/第三方组件，可以用现有名称、描述、分类和契约做补充召回。但 `onClick` 属性或 Button 字样单独出现，只能成为检索线索，不能升级为已验证用途。此类弱候选由 Agent 主动搜索复核，第一版不自动推送。因此第一版不承诺穷尽所有自定义业务组件。

### 每个候选再核对契约

索引命中后，读取当前版本的真实契约，记录相关 Slot、状态、事件及父级要求：

- action 候选检查实际操作事件和承载标签/图标内容的接口；不能只因同名就推荐不可交互展示组件。
- content-switch 候选检查实际内容条目、选择状态及变化事件；不能将 Radio 的字段值选择直接当成 Tabs 的内容所有权。
- 表格、表单等复杂组件检查主组件和必要子组件是否存在；数据值转换、验证或现有业务绑定尚未对齐时列为待确认，不能声称一键替换。
- 所需接口缺失则排除；契约不完整则降为未知，不虚构接口；所需 Context/父组件缺失则标明还需配置，不能称“当前可直接使用”。

候选排序是分档而非随意打分：当前任务明确采用的组件身份（仅在已有可信任务上下文实际可访问时）优先，其次是当前区域/页面已经采用的库，其余同模式、契约可读候选并列。不同库的候选不靠显示名称选赢家；更高档候选是否满足业务需求仍由 Agent 判断。

## 三、怎样确认“此处没有使用”

检查单位是目标功能区域，而不是整页是否出现过某个组件。

- 同页另一个位置已有 Button，不会消除本处原生 button 的建议。
- registered Button 的内容 Slot 里有 span/icon，不对这些展示子节点建议 Button。
- local SaveAction 组件的定义已经使用目标 Button，则按组合复用处理；只套一层本地组件但内部仍是自绘操作，不因此漏过。
- 只展开相关本地设计组件定义，记录定义 UUID 与引用位置，使用 visited 集合处理循环引用；共享定义的一次发现合并为一条建议，不逐实例刷屏。
- 已有已知同模式注册组件承载本区域时，不进一步检查其运行时内部 DOM。未知第三方代码组件内部不可见，标记边界，不猜测也不因为名字陌生就建议替换。
- 库继承的默认 Slot 内容不当成本次 Agent 新建；本次明确写入的 Slot 内容和新增独立交互按其真实所有权分析。
- 真正的导航链接、说明文字、代码展示、图片/SVG、布局容器不单独触发；SVG 外的独立业务按钮仍可能触发。

用户明确要求特殊视觉或交互不会被规则推翻。MCP 未掌握该要求时仍可能发出相关候选提示，Agent 可以依据原需求保留自定义；工具不声称其违规。

## 四、编辑接入、增量范围与失败处理

在 runNativeBatch 成功完成后，对本批最终结果运行只读分析，并附加到成功回执。不能在每个 operation 的中间态发提示，也不能用中间态不完整为由中止批次。

追踪的不只是新增 UUID，还包括目标节点的事件、语义属性、显隐/重复绑定、所属功能区域，以及引用的本地组件定义变化。插入/替换、复制/移动、changeElement、create/update/deleteInteraction 和会影响这些区域的状态修改均可能改变分析结果。第一版在受影响的组件内识别区域，再与编辑前的区域信号比较，不全项目扫描。纯文本、间距或颜色修改不因旧有自定义结构反复发同一建议。

新发现、新增交互、功能所有权改变或相关库版本改变可以产生新建议。删除后不存在的区域不报告；失败/回滚批次不报告编辑建议。直接或传递依赖、注册状态及来源版本变化时失效候选缓存；切项目/编辑会话清理内存缓存。

同一区域同模式先合并；记录已发送提示仅用于去重，不证明 Agent 已评估或采纳。复核结论沿用当前任务计划/检查点，不新增模型属性、永久豁免字段或专门的确认工具。

分析不访问网络、不执行元数据回调、不调用另一个模型。候选索引和简短契约摘要按项目依赖/注册版本复用。编辑成功后分析异常必须与编辑异常分开处理：返回“编辑成功，组件复用分析未完成”，不得让调用者把成功修改当失败重试。分析过程不修改画布选择、临时显隐、保存状态或撤销记录。

输出预算初始设计为每批最多 5 个区域、每区域最多 3 个候选、建议字段总计不超过 6 KiB；这些是待性能验证的上限，不是实测结果。超过预算时报告未返回条数；达到遍历/时间边界时明确标记覆盖不完整。未覆盖不能折算成“已检查且没有候选”。第一版不为此新增分页工具，不把自动提示当全页验收。

## 五、成功回执与 Agent 复核协议

在现有 MutationReceipt 增加可选 `componentSuggestions`，同一区域在批次最后一个相关操作的回执中出现一次。messages 只增加一句“编辑成功，有 N 个区域可复核”，详细证据放结构化字段。保持原有 created、as 和目标 UUID 的语义。

每条建议包含：

| 字段 | 意义 |
| --- | --- |
| target | 定义组件 UUID、元素 UUID、可选节点名；共享定义的引用位置保持有界 |
| pattern / evidence | 识别的用途模式及具体模型证据，区分显式语义和静态结构推断 |
| candidates | 精确组件 UUID、来源/版本、注册名、已核实接口及仍需的父级/配置 |
| unknowns | 尚未证明的业务、样式、值转换或交互适配条件 |
| rule | 当前索引提供的资源相对规则路径，不猜客户端本地绝对路径 |
| nextAction | 读取适用规则和真实候选契约，再决定替换、保留或待核实；不重放成功编辑 |

批次的覆盖/预算信息附在承载分析摘要的回执中。具体类型名称在实现时按现有回执风格确定，不新增顶层 MCP 工具或修改工具调用 envelope。

工具说明和 skill 工作流同步规定：

1. 检查建议，先核对原始需求、当前用户的自定义要求和现有组件所有权。
2. 当前上下文已保留适用规则时复用；缺失或版本不一致时，走 read_skill/resolver 定点读取，不每次整套重读。
3. 读取候选真实契约，尤其检查事件参数、Slot、受控/初始值和数据转换，不能根据候选名直接重写。
4. 若组件/组合能满足要求且没有冲突，使用普通编辑操作替换，保留数据、事件、路由和真实行为并验证；无法满足则保留自定义并在已有任务记录中说明具体原因；未知项未解决则记录待核实。任务本来适用 elementFallbacks 时继续满足其现有证据约定，建议机制不增加通用许可或永久豁免。
5. 不需要用户例行批准，不在业务界面加入复核说明，不将“已读 skill”或“工具返回了候选”汇报成适配通过。

这提高了 Agent 在相关编辑后再评估的机会，不保证所有模型每次遵从。没有读取或没有复核，应在真实 Agent 评测中如实记录。

## 六、第一版边界和验收用例

第一版优先覆盖 action、原生输入/选择、显式内容切换、原生表格、显式 dialog 和提交区域。自由拖拽画布、富文本编辑器、可视化流程编排、纯 CSS 仿制外观及复杂自定义 JS 不做自动替代判断。更多能力只有在具备模式证据和候选索引时增加。

| 场景 | 预期 |
| --- | --- |
| 原生 button + 项目已安装且已注册的 Button | 返回该区域及真实候选；编辑成功 |
| 原生 button，但项目未安装索引中的库 | 不宣称现有可用；不自动安装 |
| 库最新版本有能力，项目安装版本没有 | 使用安装版本排除候选，不使用最新发布契约代替 |
| 同名 Button 来自两套库 | 保留来源身份，结合已用库排序；不跨库套用契约 |
| 普通容器后来新增独立业务事件 | 新增复核机会，不依赖新节点 UUID |
| 最终已换成注册组件，或批次内又删除 | 不输出中间态建议 |
| 同页别处已用 Button，本区域仍原生实现 | 仍返回本区域候选 |
| 自定义组合内部已有标准组件 | 不重复建议；独立的自绘操作仍可识别 |
| 自定义地图、拖拽画布、导航卡片、普通链接 | 不因点击、图形或布局本身推荐 Button |
| ARIA tablist，且存在当前可用 Tabs | 返回内容切换候选及需核实的状态/事件接口 |
| 只有横排 span 和下划线的静态外观 | 不自动断言 Tabs 可替代；记录为未覆盖的外观识别 |
| 原生 Table 与复杂数据绑定 | 可提示 Table 候选，绑定/行事件适配保留待确认 |
| 本地包装组件内是自绘控件 | 在定义中识别并合并引用，不靠包装名放行 |
| 内部实现不可见的第三方代码组件 | 不推断内部违例，不声称已完成内部检查 |
| 候选仅为 Context、页面或不适配父级的子组件 | 不推荐成直接可插入组件 |
| 用户明确要求特殊自定义交互 | Agent 可以保留；不报错、不回滚、不要求永久例外 |
| 修改文案/间距、读模型、保存 | 不反复提示同一个已存在区域 |
| 建议分析抛错、耗尽预算或无效索引 | 保持编辑成功并说明分析范围；不输出全量通过 |
| 实际编辑事务失败 | 原有失败/回滚语义，不能被建议分析的容错吞掉 |

实施验证分开进行：

- 确定性测试：候选身份、契约过滤、区域所有权、变体/隐藏分支、本地定义、循环引用、增量触发、输出预算、缓存失效及分析失败隔离。
- MCP 端到端：真实编辑回执保留候选数据，JSON/XML 输出及单次/批次调用一致；successful mutation 不因分析失败被重试，undo/save/read 结果正确。
- Agent 对照评测：相同任务在无提示/有提示下比较；包含新会话、长对话和压缩恢复，固定客户端/模型/规则与候选版本，重复运行。分别记录建议被读取、规则/契约被读取、发生复核、正确替换、正确保留、误替换、未处理和额外工具/token 开销。

组件候选召回率只在明确列入支持模式且有已验证候选的样本上计算；同时报告不支持和未知样本。评测必须包含确需自定义的负例。是否启用以实际误报、误替换和 Agent 处理结果决定，不能将所有候选都被替换当成成功。

## 实施顺序

1. 确认模式表、候选索引来源、可用性分层及误报负例，完成当前设计评审。
2. 先实现只读识别、候选交集与契约摘要，并通过确定性正反例；不改现有验收的强制规则。
3. 接入原生批次成功回执和小型结构化字段，验证失败隔离、预算、实际 MCP 传输与 Agent 复核指引。
4. 运行真实 Agent 对照评测后按项目既有 devflag 机制启用。现有支持范围外的能力保持明确未知，不因增加建议就取消原有业务验收。
