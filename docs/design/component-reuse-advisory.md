# MCP 编辑后的组件复用建议

状态：源码已实现；已验证编辑工具、MCP 协议、增量缓存与本机 Node/native 检索。研究核对日期：2026-11-04，实施与测试：2026-11-05。目标是跨组件库寻找可参考组件，由 Agent 评估是否替换，保留自定义 UI；不增加一次生成式模型请求，不自动重写设计。

## 推荐方案

Agent 在原来的编辑请求中提交必填的结构化功能上下文；MCP 结合真实编辑范围，在当前项目的组件目录中检索候选，检查实际可引用性，通过成功回执返回少量建议。功能含义主要来自原本就在工作的 Agent，不要求 MCP 从几个 div 的外观猜出 Tabs。

实现采用 EmbeddingGemma 2 纯文本 GGUF Q4，由 Desktop 的 Node 主进程管理独立 llama.cpp CPU 进程，按需启动、空闲 15 秒退出；ONNX q4 保留为离线质量参考。关键词与向量融合检索，先做程序判断，再为确有必要的功能区域计算查询向量。embedding 只负责文本匹配，不生成解释、不决定替换、不读完整聊天，不内置聊天模型或 reranker。

两种限制必须分清：

- **不增加生成式模型/API 请求**：Agent 生成原有编辑调用时多写一句摘要；可以再使用本地 embedding。仍增加少量 token 和本地计算，不能称零成本。
- **完全不运行额外模型**：使用摘要、关键词检索和确定性事实检查；可以跨库，但中英文、同义词及抽象描述匹配有边界。

现有组件规则资料仅补充说明和规则链接，不作为候选白名单。没有专属规则文档的业务组件，只要项目实际能引用并有可检索信息，也能入选。

## 一、编辑请求提供功能上下文

所有设计 mutation 必填 reviewContext；读取、保存、撤销、视图操作和 Preview 保持原有参数。单次调用放在原生 input 内；execute_batch 只在批次外层放一份，不在子操作中重复。共享 Zod 契约生成 Desktop MCP JSON Schema，外部 Agent 与内置 AI 使用相同字段说明。

~~~json
{
  "reviewContext": {
    "purpose": "Switch customer information panels on the same page, keeping selection and content synchronized without route navigation"
  }
}
~~~

只有两个字段：

| 字段 | 约束与含义 |
| --- | --- |
| purpose | 必填、非空、最多 500 字符；描述整次编辑的功能，交互和明确限制自然写进去，不要求段落格式 |
| customOnly | boolean；只有用户明确要求本次功能自行实现、不要使用现有注册组件时传 true，其余情况一律传 false；遗漏按 false 处理 |

Agent 不提供区域列表或操作编号。程序根据实际操作和回执定位检查目标，合并相同或包含的范围，可跨组件定义；每次最多五处，超出报告 partial。所有目标共用同一功能说明，查询向量可复用。多个无关功能共用说明可能降低精度，不声称能自动拆出每处的独立意图。

功能语义优先使用简短英文以匹配当前英文注册契约；界面文案、名称和用户引述保持原文。这只是同一次 Agent 工具参数生成，不增加翻译或额外聊天请求。中文输入仍合法，已归档诊断中跨语言召回较弱。purpose 的字段说明提供正反例，不能只写“Update UI”“Add divs”“Use Tabs”，不能编造用户未要求的行为。

customOnly 由 Agent 判断。只有用户明确要求自行实现且不使用现有注册组件才传 true；单纯要求自定义样式或交互、已有自定义代码、Agent 自行选择手写都传 false。它作用于整次调用；若用户只针对其中一处要求不用组件，其他功能另一次编辑。MCP 不核实聊天原文或语义，不要求原话或理由字段。回执使用 user-choice-agent-reported 标记跳过原因。上下文不写入业务 Props 或页面模型。

### 前置判断先于模型

1. 推荐入口只属于 Agent 编辑工具；用户手动操作不触发推荐。
2. 实际操作只有文案、名称、样式、移动、删除或辅助状态配置时跳过。
3. 目标已是注册代码组件，或组合仅由现有组件及正常文字/Slot 容器承载时跳过。新增的原生按钮、输入、表单、表格、事件等仍单独检查，不因页面别处存在 Button 而跳过。
4. 无注册组件的原生区域，在存在真实功能控件/事件或可识别字段对/语义列表时检查；简单文字和空布局不检索。纯 div 且无可识别行为的功能不能保证自动识别。
5. customOnly:true、已提示区域及其真实替换后的身份同样跳过。字段缺失、空白、类型错误或未知字段在修改前拒绝，operationExecuted:false。

共享输入与输出：[component-review.ts](../../platform/wab/src/wab/shared/copilot/component-review.ts)；实际目标定位：[component-reuse.ts](../../platform/wab/src/wab/client/copilot/component-reuse.ts)。结构校验不能证明摘要真实，检索建议也不是自动替换许可。

## 二、当前项目的组件检索目录

纳入项目自己的可复用组件、已安装直接/传递依赖中的可引用组件和当前有效代码组件。包括尚未在页面使用的组件，不限库和注册前缀，不在每次编辑时扫描在线商店。

每条检索文档来自实际版本的信息：

1. 精确身份：组件 UUID、来源项目、安装版本、注册名和导入信息。
2. 用途文本：显示名、描述、分类，以及可核实的现有组件说明。
3. 能力文本：真实 Props 名称及描述、Slots、状态、事件与参数、父级要求的短摘要。
4. 可用性：代码注册是否有效、是否 Context、是否只能作为子项、是否还需父级或配置。

同名组件保留独立身份；长契约可拆为用途/交互/数据片段，结果合并回同一精确组件，避免 className 等大量样式属性淹没用途。分片预算按检索器/模型输入上限确定。

页面、画板 Frame、全局 Context 不作为普通可插入组件；全局反馈动作不能被当作组件。子组件保留父级约束，不能将 Table.Column 当独立 Table 推荐。注册未就绪或契约缺失时，不声称当前可直接使用。

索引是当前模型/契约的派生缓存，不新增持久化设计 schema。依赖、版本、注册信息或本地契约变化时更新受影响条目；切项目释放活动目录与任务，保留本账号隔离的磁盘向量缓存。未读取完整时报告 partial，不把未收录当不存在。

描述含糊的业务组件仍可按名称和接口匹配，但 embedding 也不能凭空补出用途。应先统计描述缺失情况，必要时完善原有注册描述。

## 三、召回、筛选与放弃提示

~~~text
同次请求的功能摘要 + 最终区域的客观模型事实
                    ↓
当前项目的真实组件目录
                    ↓
BM25 与本地 embedding 分别召回
                    ↓
融合排名、按身份去重、检查可引用性
                    ↓
核对前几个候选契约与区域已有组件
                    ↓
有依据才返回短建议；否则静默或标记未覆盖
~~~

### 零额外模型基线

使用分字段 BM25：名称、用途描述、文档与接口说明。切分 camelCase/snake_case 标识符，中文采用可复现的分词或字词片段，不用整句 substring。只利用已有别名/说明，不手写每个库的“交互对应注册名”白名单。

onClick、children、className 等高频词不能主导排名；字段权重从独立样本确定。该方案可以跨库，但中文摘要与英文描述无共同词时会漏召回，不能宣传为完整语义理解。

### 本地 embedding 增强

组件文档变化时计算并缓存向量；每段新意图只计算一次查询向量。关键词和向量分别召回，采用 RRF 等排名融合，再检查候选与契约。向量缓存按固定模型产物和输入处理版本隔离；不混用不同量化、维度或预处理版本的文档/查询向量。用途与接口分段，避免长属性列表稀释用途，也避免只改用途却重算全部接口片段。BM25 词项在目录更新时准备并复用，不在每次查询中重新分词整个库。

本地推理仍占 CPU/内存。组件规模未证明有必要前，可评估内存向量比较，不默认引入向量数据库和外部服务。

### 索引持久化、增量更新与调度

实现目标为重复打开未变化项目时零组件 embedding 调用，仅变化的片段补算。查询意图还有有界的 128 条内存缓存，同一会话重复意图可直接复用向量；换项目/账号清除。增量管线已做测试，真实 Studio 并行交互负载仍未验收。

区分项目目录和可复用向量：

- 项目目录记录当前可引用组件的精确身份、来源/安装版本、检索片段哈希和就绪状态；每次使用仍依据当前安装版本及有效注册过滤。向量命中缓存不代表该组件已安装或可直接插入。
- 向量键由固定模型文件/分词器、输入格式/截断/池化/维度等处理签名，以及实际输入文本的内容哈希组成。项目 UUID、库版本与修改时间不塞进文本缓存键，避免同样内容因身份/版本变化重算；精确身份保留在项目目录。
- 向量持久化到本账号的本地缓存；活动目录在内存中由当前项目重新核对。重启、切项目或结束聊天不删除已计算向量；相同组件文本和相同处理签名可在该账号的不同项目复用。1000 条 768 维 Float32 向量原始数据约 2.93 MiB，不含元数据；缓存向量无需常驻整个模型。

| 变化 | 应执行的工作 |
| --- | --- |
| 页面拖拽、颜色、间距、实例字段值/业务文案 | 不重建组件目录向量；本次功能查询按原有触发规则处理 |
| 新增组件、用途描述/Props/Slots/事件契约或相关组合能力变化 | 重新派生受影响组件的检索文本；仅为文本哈希变化的片段补向量 |
| 安装/升级库或代码注册重新加载 | 核对当前真实定义并比较各片段哈希；复用未变内容，补新增/变化内容 |
| 删除组件、卸载库、注册失效 | 立即从可用目录排除；无需推理，磁盘共享向量以后清理 |
| 模型产物、量化、维度或输入处理语义变化 | 使用新的缓存签名，后台准备新版本；每次检索固定同一签名，禁止新旧向量混算 |

组合能力变化可能影响引用该定义的本地组合，更新范围包括这些实际受影响的组合；普通实例变更不直接触发全库扫描。使用原生模型/注册变更信息标记相关定义，短时间连续修改合并后取最新文本；任务只保留最新待处理版本，结束时核对版本，过时结果不挂回当前目录。重开项目重新核对目录，不能只依赖进程内事件。缓存损坏只重算缺失/损坏片段，不全库清空。

准备时机优先于提高索引算力：

1. 项目组件/注册就绪时先读磁盘向量，只把缺失项加入有界后台队列；不阻塞页面首次打开。首次没有缓存时不承诺瞬间完成，编辑仍可用。
2. 当前构建会执行本仓库 Antd6 和 Overseas 的真实注册函数，预生成公共向量并随应用资源提供；客户端只按当前真实注册文本的哈希复用，绝不因此安装组件或引入不在项目里的组件。其他库及自有组件走相同的动态增量路径，不受预制库名单限制，不要求新增在线推理服务。
3. 正常编辑查询优先，后台索引每次只提交一个小片段，结束后重新检查查询队列与编辑活动；有前台查询则暂停提交索引。已经在执行的单次推理不能假定可立即抢占，需要实测其最长阻塞时间。
4. 复用唯一模型进程，先按已测 2 线程限制 CPU，不再并开索引模型；在用户持续操作时暂停索引提交，空闲后继续。小任务之间保留检查点，重启可续做，不人为增加编辑扫描等待。
5. 每条完成后原子写缓存并更新其目录状态，已完成条目可以参与检索。新版本/新条目未就绪时只用当前可引用且同签名的已就绪条目和关键词结果，准确标记 partial；不把旧契约向量当作新定义，不因等待索引延长本次扫描，不事后补发该次建议。

按内容哈希识别变更、持久化并复用处理结果是已有检索管线的做法，可参考 [LlamaIndex ingestion 的 upsert/delete 与持久化机制](https://developers.llamaindex.ai/python/framework-api-reference/ingestion/)；这里采用其思路，不引入该框架或复制其整批转换缓存粒度。

接入后的验收包括：重复打开零重算、单片段变化仅重算该片段、同内容跨项目复用、卸载后不再召回、未完成/中断后续做、更新期间不混算签名，以及真实拖拽/输入同时索引时的查询 P95、最长在途任务和 UI 响应。不能仅以独立进程或低线程数宣称完全不影响使用。

### 有候选不等于该提示

Top-K 永远有第一名，不能因此总发建议。BM25、余弦和 RRF 分数都不是可替换概率，不设跨模型通用的 0.8 阈值。提示阈值需用含无候选、跨语言和特殊自定义的样本校准。

多个合理候选可以并列；不能仅因第一二名分差小就认定无结果。无足够用途/接口依据则静默，不给泛化的“请再看看组件库”提醒。

回执区分内容相关、可引用、需额外配置和契约不足。接口存在不证明键盘操作、数据转换、表单验证或完整需求已满足；未确认能力列入 unknowns，不虚构也不直接宣称可替换。

## 四、模型初筛与本机资源结果

以下保留模型选择的离线对照。当前实现使用 **EmbeddingGemma 2 纯文本 GGUF Q4**；ONNX q4 为质量参考。模型按需启动，空闲 15 秒退出；向量缓存继续保留。以下历史探针不能代替本轮完整检索测试。

### 同一组离线召回对照

冻结 101 份仓库组件文档和 41 条手工编写的功能摘要：37 条有候选、4 条无候选或不适用。每份文档使用注册名和前 1800 字符；不是当前项目的完整运行时契约。模型采用各自正确查询前缀、相同 512-token 上限与真实部署量化版本；所有测试运行在 CPU。

| 模型 | 首位命中 / 37 | 前三命中 / 37 | 当前用途 |
| --- | ---: | ---: | --- |
| multilingual-e5-small q8 | 9 | 15 | 不作为默认方案 |
| Qwen3-Embedding-0.6B q8 | 22 | 31 | 较重的对照候选 |
| EmbeddingGemma 2 文本 q8 | 20 | 30 | 精度/占用对照 |
| **EmbeddingGemma 2 文本 ONNX q4** | **24** | **34** | 当前质量基准 |

q4 在这组小样本上更好，不意味着量化普遍提高精度。样本未经独立复核、尚无独立留出验收集，不能宣布“所有场景最优”。4 条负例仅保存排名，未校准建议阈值，不能据此声称已经控制误提示。

输入、逐条排名、模型 revision、资源数据和复现脚本见 [证据目录](component-reuse-evidence/README.md)。

### ONNX 质量基准的具体版本与接入

- 原模型：[google/embeddinggemma-2](https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2)，仅使用 270M 文本部分。
- ONNX 产物：[onnx-community/embeddinggemma-2-ONNX](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX)，固定 revision 为 daa72c51243991dfcaf9f9137d2c573d8f7790c0。
- 仅加载文本 q4：model_q4.onnx 和 model_q4.onnx_data；显式移除 vision_config、audio_config，不使用会默认加载所有编码器的通用 pipeline。
- 当前探针使用 Transformers.js 4.3.2、ONNX Runtime Node 1.30.0，CPU，intra-op 2 线程、inter-op 1 线程。属于已验证的本机组合，仍需验证 Electron 打包和其他目标平台。
- 查询按模型要求添加搜索前缀；组件文档使用标题/正文前缀。采用模型返回的 768 维 sentence_embedding 并做 L2 归一化，不截短维度，不新增生成式小模型或 reranker。

### 已测资源：整进程与权重必须分开

硬件是 Apple M4、24 GiB 内存；Node v24.20.0。30 次短摘要查询来自 10 条正例。新进程使用本地文件，未清理操作系统磁盘缓存，加载不包括网络下载。

| 指标 | Qwen3 q8 | Gemma 2 文本 q8 | **Gemma 2 文本 q4** |
| --- | ---: | ---: | ---: |
| 预热后摘要计算中位数 | 72 ms | 101 ms | **54 ms** |
| 摘要计算 P95 | 79 ms | 110 ms | **63 ms** |
| 本地加载模型（不含运行库 import） | 594 ms | 550 ms | **515 ms** |
| 模型、tokenizer、配置等文件合计 | 596 MiB | 330 MiB | **197 MiB** |
| 查询后工作进程 RSS | 1651 MiB | 840 MiB | **617 MiB** |

q4 文本权重数据约 174 MB，加入 tokenizer 等文件约 207 MB；不能称为运行内存只有 174 MB。617 MiB 是包含 Node、运行库、tokenizer 和模型的进程 RSS，不是纯权重内存；本轮没有证明 100–200 MB 的进程占用可以保持相同中英文召回质量。

这些只是摘要 embedding 探针，没有完整 BM25/向量融合、候选契约核实、Electron 打包或实际 Studio 操作负载，不能将 54 ms 当成整个 MCP 检查耗时，也不能保证画布帧率不变。不同平台、长文本和索引构建仍需测量。

### 低常驻内存的执行方式

用户允许扫描内有限等待，因此首选按需工作进程而非永久驻留：

1. 使用已经准备好的本地模型文件和组件向量缓存，扫描内启动或复用唯一的活动工作进程。
2. 执行本批短摘要检索、返回候选，排队工作用同一实例，不为每个 MCP 客户端/区域复制模型。
3. 无工作后最多空闲 15 秒退出进程释放模型 RSS；平时仅保留目录与向量缓存，不能把 OS 文件缓存称为额外占用已归零。
4. q4 探针的运行库导入约 72 ms、模型加载约 515 ms，按需加载具有可行性，但真正的子进程启动、IPC、检索和退出仍需纳入扫描总预算测试。
5. 模型文件提前随受控资源准备；扫描过程中不等待联网下载。初次整库向量构建在后台完成，未就绪时明确检查覆盖，不用无限等待拖住编辑。

1000 条 768 维 Float32 文档向量的原始数据约 2.93 MiB；这是计算值，不含目录、对象和检索索引开销，也不意味着一个组件只对应一条文档。

### 更小候选的实测结论

2026-11-05 使用同一冻结文档/查询评测四个更小候选；纯 CPU，每模型三个独立进程测量资源，表中内存和耗时为三次指标中位数。

| 模型 | 前三命中 / 37 | 查询后整进程 RSS | 含 101 文档索引峰值 | 预热查询 P95 |
| --- | ---: | ---: | ---: | ---: |
| Bekko-static 128d INT8 | 15 | 268 MiB | 292 MiB | 0.14 ms |
| Bekko-static 256d INT8 | 19 | 362 MiB | 385 MiB | 0.18 ms |
| BGE-small-zh-v1.5 INT8 | 15 | 168 MiB | 448 MiB | 2.96 ms |
| Granite 97M multilingual INT8 | 30 | 617 MiB | 823 MiB | 4.51 ms |

静态模型更快，但在这组中英文组件文档上损失较多召回；BGE 查询占用最低，质量尚不足以替换基准。Granite 查询很快，但内存没有明显降低。权重更小不能直接推断进程更小，本轮没有证明低于 100 MiB 的进程能保持现有召回水平。

继续保留 Gemma 2 文本 ONNX q4 为质量基准，不因模型文件体积小而替换。旧 Gemma 探针未测索引峰值，不能直接拿旧查询 RSS 与新候选索引峰值比较。原始数据、固定 revision、12 次资源测量、接口和复现边界见 [证据目录](component-reuse-evidence/low-memory/README.md)。Go 和 Gemma 原生运行方式的对照见下文；索引 batch 大小及图优化策略尚未系统调优，不把实测值当作理论内存下限。

### Go 运行方式的对照

同日补测 Hugot v0.8.5 + ONNX Runtime 1.30.0，复用同一 BGE/Granite 权重，替换为 Go 分词和工作进程；另测 go-potion v0.1.2 的英文 8M 与中英文多语言 128M 静态模型。每配置三个独立进程，CPU。

| 配置 | 前三命中 / 37 | 查询后 RSS | 含索引峰值 | 查询 P95 |
| --- | ---: | ---: | ---: | ---: |
| Hugot + BGE INT8 | 15 | 106 MiB | 466 MiB | 2.77 ms |
| Hugot + Granite INT8 | 30 | 446 MiB | 747 MiB | 4.98 ms |
| go-potion 8M F32 | 7 | 17 MiB | 33 MiB | 0.037 ms |
| go-potion multilingual 128M F32 | 20 | 118 MiB | 153 MiB | 0.086 ms |

Hugot 的 BGE/Granite 查询 RSS 比 Node 对照分别降低约 37% / 28%，BGE 索引峰值没有降低。BGE 全部 142 条 token IDs 一致；Granite 有 7 份文档分词不同，同为 30/37 不证明完全等价。现有 Gemma q4 导出无法直接通过 Hugot 的 video_features 输入校验，未取得 Go 资源结果。

go-potion 的低 RSS 受 mmap 实际访问页面影响，多语言原始文件仍约 531 MB；语料扩展后不能保证 RSS 保持 118 MiB。该组使用相同原文片段但不截断 512 tokens，不作为纯语言切换对照。两型号已与官方 model2vec 独立核对全部 token IDs 和抽样向量。

这些是模型选型阶段的语言对照；当前实现采用 Node 管理 C++ 原生进程，Go MCP 只负责协议传输。结果、未完成的纯 Go 后端探索、独立校验、波动和复现见 [Go 探针证据](component-reuse-evidence/go-probe/README.md)。

### Gemma 的 LiteRT / GGUF 原生对照

2026-11-05 使用同一冻结语料，分别完成质量评测和三次独立进程 CPU 资源测量：

| 配置 | 首位 / 37 | 前三 / 37 | 查询后 RSS | 短查询 P95 | 资源测试含索引峰值 RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原 Node / ONNX q4 | 24 | 34 | 617 MiB | 63 ms | 未测 |
| Python API / LiteRT INT4 | 22 | 30 | 384 MiB | 34 ms | 483 MiB |
| 原生 llama.cpp / GGUF UD-Q4_K_XL | 20 | 33 | 360 MiB | 34 ms | 409 MiB |

新配置的资源列为三次中位数，原 Node 为旧单次探针。GGUF 查询 RSS 低约 42%，因此选为当前实现后端；该历史探针的首位和前三命中未完全保留。GGUF 全部 142 条截断后 token IDs 与 ONNX 一致；LiteRT 内部分词未核对。GGUF RSS 不含 Python HTTP/计分观察器，LiteRT RSS 包含 Python；均不是整个 Studio 占用，不能将差异全部归因于语言。

LiteRT 先建索引的质量运行曾测到 **556 MiB** 峰值，不能把后三次资源进程的 483 MiB 当作上限；GGUF 质量运行峰值约 411 MiB。整库 101 份文档索引中位数约 11 / 35 秒，必须提前缓存；短查询结果不代表编辑总耗时。尚未证明低于 200 MiB 并保持现有质量。固定版本、文件哈希、全部运行和复现见 [原生运行证据](component-reuse-evidence/native-gemma/README.md)。

### 扫描效果内完成检查，有限等待后统一返回

编辑写入完成后，在现有编辑扫描生命周期内执行组件检查，整理候选后再结束扫描并返回同一次工具结果。不采用 100–200 毫秒内结束、以后再补发建议的路径，也不要求 Agent 轮询。

实现顺序：

~~~text
开启现有编辑扫描
    → 参数与权限检查
    → 原生编辑事务成功提交
    → 取得最终区域快照
    → 检索可参考组件并核实候选
    → 整理成功回执及检查状态
    → 结束该次编辑扫描
    → 返回同一次 MCP 结果
~~~

模型计算仍放在 Desktop 独立后台进程/worker，工具调用可以等待，画布主线程不能因此被同步计算阻塞。检查期间不持有 Studio 模型写事务或撤销 recorder，不因检查失败回滚已经成功的编辑。用户或其他调用改变了该区域时重新核实快照，过时结果丢弃，不自动循环重试。

当前检查预算与仍待真实 Studio 验收的体验目标：

- 预热后一次功能区域检查目标为 0.5–2 秒；不用人为延时把快结果拖长。
- 原生编辑成功后的检查阶段，整个调用最多额外等待 5 秒。5 秒是批次共享的总截止时间，不是每区域各等 5 秒，也不等同于整个编辑/渲染流程的超时。
- 模型文件和组件向量缓存在项目准备阶段提前准备；按需加载仍受同一截止时间约束，不临时延长扫描以等待联网下载和整库重建。
- 超时、模型不可用或候选不足时结束检查，返回真实编辑成功及 completed/partial/timeout/unavailable 等检查状态。无候选仅在已完成的覆盖范围内成立；timeout 不是“检查通过”。
- 检查超时不生成“等待后续回执”的悬挂建议，不自动补发。后台只允许有界预热/缓存准备，不为已超时编辑继续堆积推理任务。
- 用户取消或项目/会话切换要释放该次扫描和检查资源；编辑是否已经执行必须准确报告，不能把取消检查写成编辑回滚。

当前扫描入口 [CopilotActivity](../../platform/wab/src/wab/client/copilot/activity.ts) 已有 running/scanning 与 finish 生命周期，检查接在原生事务结束和目标呈现之后、同一次 finish 之前；executeLocalEdit 与批次复用相同检查，不在外层和每个子操作各做一轮。扫描最短动画时间当前是 1600 毫秒，只影响动画，不是模型等待预算，不应据此声称检查必定完成。

整个过程保持同一次编辑调用和同一个扫描效果，不拆分用户可见阶段、不切换提示文案、不新增进度条或并行扫描。上面的顺序只描述内部执行边界。扫描不延长到 Agent 读 skill、决定替换和后续编辑的全过程；后续明确编辑使用正常的新扫描生命周期。

仍需验证真实 Studio 并行操作下的检查 p50/p95、取消、扫描释放及后台 CPU 竞争。五秒总截止及分析期间扫描保持已由单测覆盖；不能仅以“放到 worker”宣称完全无影响。

## 五、检查区域是否已有组件承载

按功能区域而非整页检查：

- 页面别处已有 Button，不消除本处操作入口的建议。
- Button 内容 Slot 的展示 span/icon 不当成新控件；不扫描注册组件的运行时 DOM。
- 本地组合已有相关组件则按组合处理；只套本地包装仍可检查其定义。仅展开相关定义，visited 防循环，共享定义合并提示。
- 未知第三方代码组件内部不可见，不能因名字陌生就推断其不合适。
- 相同或包含的实际编辑范围合并；不同目标使用同一功能说明分别核对已有组件。定位不明确时标记边界，不猜节点名对应关系。
- 导航链接、说明、布局、图片、拖拽画布和特殊自定义 UI 不因未用标准组件被判错。

纯 CSS 静态 UI 可以由功能摘要提供查询入口；无摘要、无可识别交互时，不承诺仅靠 CSS 理解功能。

## 六、成功回执和防循环

批次成功后分析最终结果，在 MutationReceipt 或批次输出中增加有界 componentReview。每区域最多 3 个候选，包含目标、匹配依据、真实身份/版本、契约事实、未知项及规则入口；不返回整个组件库。后端结果上限 5120 字节，为前端跳过原因等元数据留出空间，总预算 6 KiB；超限报告 partial。

无足够候选就不提示。分析异常/超时保持编辑成功；实际编辑失败仍按原有失败/回滚处理。既不自动替换，也不把读取 skill 作为解除编辑限制的条件。

实现确保：

1. 仅检索本次结构/交互变化涉及的区域，按最终批次合并；读、保存、文案微调、颜色和间距不重新触发。
2. 同一编辑会话同一功能区域最多主动提示一次。以项目/编辑会话、定义和目标身份去重，不以可随意改写的摘要为键；区域替换沿本次真实替换关系关联新目标。
3. 同一编辑会话/调用者、同一页面或组件定义内，同一候选组件也只提示一次。该限制不依赖目标节点 UUID、用途描述或替换方式，覆盖删除后重建；不同候选和其他页面仍可提示。已发送不等于已处理，但不因仍保留自定义持续催促。库版本变化使检索缓存失效，不解除本会话一次提示限制。
4. Agent 读取适用规则和候选契约，决定替换、保留或待核实，一次复核后继续。结论沿用任务记录，不新增永久豁免属性或确认工具。
5. 替换必须保留并验证数据、事件、路由和实际行为；特殊 UI 可以保留。提示不替代原有适用业务验收，不在业务界面增加复核说明。

一次提示限制可能漏掉后续重新评估：同页另一独立区域需要相同组件时，不再重复提醒该候选。Agent 仍可主动搜索。编辑工具返回建议后即结束，不等待 Agent 读 skill 或做后续编辑；此限制防止同一建议反馈循环，不保证 Agent 不会因其他原因继续调用工具，新会话/调用者也有独立记录。

## 七、评测与实施

分开检验检索与 Agent 处理，不把出现建议文字当成功：

| 比较组 | 检验目的 |
| --- | --- |
| 现有名称/描述文本搜索 | 原始基线 |
| 功能摘要 + BM25 | 摘要本身带来的收益 |
| 同一摘要 + 各本地 embedding | 比较模型，避免把更好的摘要误算为模型收益 |
| 同一摘要 + 混合检索 | 检查收益是否值得部署成本 |
| 无提示/有提示的多轮 Agent | 正确替换、正确保留、未处理、误替换与额外回合 |

使用真实安装版本的库存/契约快照和独立标注需求。允许多个合理候选、组合、无候选和信息不足。包含自有业务组件、跨库同名、尚未使用的已安装组件、中文对英文、同义词、描述缺失、只有 onClick 的干扰项、纯样式、特殊自定义、已有组合，以及错误/遗漏摘要。

调参样本与验收样本分开，至少留出一个未调参的库，不能只用预先维护的 Button/Tabs 验收。测 Recall@3、前几项精度、无合适组件时的提示率、真实可引用性及覆盖范围；另外测索引耗时、模型冷启动、查询 p50/p95、峰值/常驻内存、分发体积、纯 CPU/目标平台及与 Studio 并行影响。

真实 Agent 固定客户端、模型、规则和组件版本，覆盖新会话、长对话及压缩恢复，重复运行。记录摘要遵守率/真实性、规则/契约读取、正确处理及服务端总提示次数。确需自定义的正确负例必须保留，不能以替换率越高越好评分。

当前已实现共享结构化输入契约、原生单次/批次和 executeLocalEdit 成功回执、同一扫描内有界检查、程序跳过与去重、Desktop Node/native 进程、BM25/向量融合、公共预制向量和账号隔离的增量缓存。默认模型固定为 EmbeddingGemma 2 文本 GGUF Q4，并由现有 devflag 控制。

源码测试和本机检索探针已经完成；尚未完成独立留出集、安装版 Studio 并行负载、其他平台与长会话 Agent 行为验收。源码验证、实际数据与边界见 [实施测试报告](component-reuse-implementation/README.md)。
