# Plasmic 产品演进方案

更新日期：2026 年 10 月 10 日。状态：建议实施方案。

Plasmic 的近期定位是**基于真实组件体系的业务原型与工程协作工作台**。产品应帮助团队把需求变成可编辑、可运行、可评审的页面，并把已确认的设计和行为交给目标工程实现。AI 负责加速生成和修改，人工编辑负责精确控制，真实组件和交互验收负责保证结果可信。

演进顺序为：**业务流程完整 → 编辑操作顺畅 → 团队评审与工程交付 → 按需求扩展设计输入和自动化**。界面优化从第一阶段开始，重点解决查找、选择、修改和反馈；底层建设以真实使用瓶颈为依据。

## 产品定位与目标用户

近期优先服务已经拥有 React 组件库的业务团队，重点覆盖管理后台、运营工作台、表单、列表、详情和审批类页面。这个范围来自当前 Antd6、业务组件、模板及验收积累，是首批验证市场和场景的选择；布局、样式和自定义组件能力继续支持更广泛的页面设计。

| 用户 | 希望完成的任务 | 产品需要交付的结果 |
| --- | --- | --- |
| 产品经理与业务负责人 | 把需求转成可讨论的业务流程 | 能操作的原型，清楚呈现正常、空、失败、只读等实际需要的状态 |
| 设计师 | 调整布局、信息层级和组件表现 | 精确可编辑的画布、稳定属性面板、可复用的组件与样式 |
| 前端工程师 | 理解设计、行为与组件使用方式，并接入现有工程 | 真实组件身份、Props/Slots、状态事件、设计版本和可审阅代码变更 |
| 组件库维护者 | 让团队正确复用组件 | 与实现一致的注册元数据、默认值、事件和使用示例 |

核心价值主张：**用团队真实组件完成原型，在预览里验证业务行为，在目标工程里交付可维护实现。** “零研发门槛”仅适用于受支持的原型操作；接入未知接口、宿主和自定义逻辑仍需要工程上下文。

## 用户主流程

### 创建与继续编辑

工作台优先展示最近项目、搜索、创建页面和模板入口。项目较多时可切换紧凑列表；网格使用保存后生成并缓存的缩略图，避免首页同时运行大量页面。缩略图失败时显示明确占位，不阻塞项目打开。

创建页面提供“从模板开始”“描述需求”“空白页面”三种入口。新手可从经过验证的模板开始，已有项目默认复用当前组件库、主题和页面外壳。生成只询问影响页面结构或行为的缺失信息；其他细节形成可编辑的初稿。

“描述需求”入口只有在执行服务可用时才进入生成流程。首阶段继续支持外部 Agent，通过现有 MCP 使用当前项目和选区上下文。界面清楚显示连接状态和操作范围；未连接时提供可完成任务的模板与手动入口。

### 画布编辑

编辑器采用稳定的工作区结构：左侧页面、结构与组件资产，中间画布，右侧选中对象属性。顶部保留项目与保存状态、撤销重做、预览、分享和交付入口。支持折叠侧栏进入专注视图。

右侧面板按选中对象逐步展示内容：组件属性与内容、布局、外观、交互，以及低频高级项。分类只改变显示组织，所有值仍写入现有 Props、Slots、样式和事件模型。按上下文隐藏无关项；以真实任务测试决定高频项，不预设“80% 操作可以被悬浮条替代”。

画布直接操作优先支持文本编辑、拖动排序、间距与尺寸调整，以及实际允许的组件内容编辑。选区悬浮条保留少量高频动作和 AI 修改入口，并遵循只读权限、键盘焦点、缩放与可视边界。

Tabs 非活动内容、关闭的 Drawer 等可通过结构树或组件编辑入口临时展示。临时展示只影响编辑会话，不能改写保存后的默认业务状态。属性面板中的显式业务属性修改正常进入撤销和保存流程。

Studio 与 Desktop 外壳跟随共享语言包；组件注册名称、Props、Slots、描述、枚举标题和动作名称保持英文注册契约，业务文案保持用户配置语言。编辑器主题限制在编辑器作用域，画布内容使用项目自身主题。

### AI 修改与人工接管

AI 入口共享当前项目、页面和选区；不把页面级请求默认为全项目修改。执行过程中显示目标区域、任务状态和可理解的错误，完成后给出变更摘要及撤销入口。现有扫描反馈可以保留，但要与实际操作状态绑定。

局部明确修改在用户授权范围内直接执行并允许撤销。涉及整页重组、多页批量修改等范围较大的操作，先展示影响范围与修改方案。AI 通过现有 Studio 操作修改真实模型，不建立第二套设计数据。

单次原子批量操作失败时整体回滚。跨多个批次的长任务如被取消，应报告已完成部分和可恢复范围，不能承诺所有已完成修改自动消失。保存失败必须显式呈现，不能把“画布已变化”显示为“已保存”。

内置自然语言执行后续采用一个最小可用的 Agent 入口，复用同一套工具契约、权限与撤销链路。供应商选择和连接配置放在设置中，不占用日常编辑流程。是否扩展多 Agent 调度由任务收益决定。

### 预览与评审

预览运行真实组件和交互，保留页面自身的路由、状态与视口行为。业务原型可使用明确的模拟数据；模拟运行与真实接口联调分别验收。

分享入口让评审者直接进入预览或设计评审视图，清楚区分“最新内容”和“固定评审版本”。复用现有分享、版本和权限机制实现可行范围；访客评论能力先核对现有授权契约。

评论关联稳定节点身份，并记录相关页面及设计版本上下文。评论转为 AI 修改任务时，先检查目标节点和当前内容，完成后展示结果。节点已删除或页面已变更时提示重新定位。

### 工程交付

保存设计、分享预览、交付代码、部署应用各自保留清楚的动作语义。普通原型用户重点看到预览与分享；已连接工程的项目提供代码交付入口。Git 提交不能代替部署状态，也不能代替设计保存。

默认业务工程路径是：读取设计和真实组件契约 → 对照目标仓库组件、宿主与接口 → 生成或修改原生项目代码 → 检查变更 → 构建与行为验收。官方 Plasmic codegen/sync 用于明确选择官方集成的项目，并清楚说明生成文件所有权。

首次工程连接确定目标仓库、路由、组件库和代码维护方式。后续交付记录设计 revision、目标代码基线和受影响文件，只修改本次需求关联内容。分支和 PR 基于可审阅 diff 创建，不自动推送或部署每次画布编辑。

首版代码视图展示组件来源、关键 Props/Slots 和相关代码片段；具备准确关联后增加节点定位和 diff。任意手写 React 反向恢复为完整设计模型不属于近期承诺。

## 技术约束

1. **使用现有模型。** 页面、组件、变体、状态事件和样式继续由现有 Studio 模型承载；UI 与 AI 通过受支持操作修改它。
2. **以组件实现为契约。** 先修正注册中的默认值、事件、Slot、受控和编辑态映射，再重组属性面板。面板不增加业务属性翻译层。
3. **复用操作和恢复能力。** 使用现有事务、撤销、保存和权限机制；补缺时先验证现有覆盖范围。多个 Agent 不同时写入同一编辑上下文。
4. **保持编辑态和运行态边界。** 选择、临时内容展示、AI 覆盖层不进入业务模型和导出结果。
5. **保留真实网页运行。** 多画板布局与 iframe 渲染可以共存。根据打开耗时、缩放响应和内存等实测优化；不以“无限画布”为理由重写渲染引擎。
6. **明确代码所有权。** 原生工程与官方生成代码使用各自清楚的维护规则。设计到工程的转换参考当前真实契约，不建立长期维护的第二套页面 schema。
7. **精确限定主题。** 编辑器使用语义 Token 和明确作用域；禁止以全局标签、模糊类名及大量强制覆盖实现整站换肤。
8. **使用可核验版本。** 验收记录源码或构建版本、组件库版本、设计 revision 和实际操作结果，使问题可复现。

## 实施阶段与交付门槛

UI 工程按以下依赖顺序实施：

1. **统一设计基础**：Studio 使用 Ant Design 6 + antd-style；共享主题 Token、暗色/亮色/跟随系统、字体、控件状态和弹层主题。登录、注册、重置密码沿用现有交互；业务画布内容使用项目自己的主题。
2. **统一应用布局**：项目、组织、工作区、设置和 CMS 共用导航与内容滚动规则；随后统一编辑器顶部、左右侧栏和浮层布局。
3. **画布交互**：布局验收后处理平移、缩放、画板导航、选区和快捷键，复用当前模型与 iframe 渲染。
4. **页面细化**：工作台、编辑面板、AI、预览交付、设置和 CMS 按已确定的全页面图集完善。

详细页面顺序与验收条件见 [全页面 UI 改造计划](ui-design/2026-10-10/consistent-v2/implementation-plan.html)。以下产品能力阶段用于业务验收，不改变上述 UI 工程依赖顺序。

阶段按依赖推进。团队人数、可投入时间和基线尚未确定，日历工期在首阶段任务拆分后估算；以下顺序不等同于已承诺排期。

### 第一阶段 业务流程与编辑基础

目标：通过现有能力完成一个端到端业务任务，同时解决该流程中最明显的编辑障碍。

| 任务 | 交付物 | 验收条件 |
| --- | --- | --- |
| 建立业务基线 | 同一版本下的任务耗时、操作路径和问题清单 | 覆盖新建、局部修改、预览、保存重开和分享；数据可复测 |
| 核对组件契约 | Form、Table、Tabs、Drawer 及所用业务组件的修正 | 面板值、保存模型、运行 Props 与实际行为一致 |
| 验证模板消费 | 一条可用模板入口与当前项目绑定流程 | 无重复 AppShell、残留样例 Slot 或失效状态引用 |
| 整理属性面板 | 高频属性分组、内容入口、低频项收起 | 能完成列调整、表单规则、Tab 内容和弹层编辑；无需改写契约 |
| 完善局部编辑反馈 | 正确选区、可理解的操作状态、撤销与保存反馈 | 修改范围准确；失败状态明确；保存重开后结果一致 |
| 整理外壳样式 | 有作用域的主题与基础可访问性 | 编辑器样式不改变业务画布；键盘入口可用 |

进入下一阶段的门槛：主验收场景完整通过；没有尚未解释的保存丢失、撤销破坏、错误组件 Props 或编辑状态泄漏。

### 第二阶段 生成与持续修改体验

目标：让用户快速得到可用页面，并能持续完成小范围修改。

| 任务 | 依赖 | 验收条件 |
| --- | --- | --- |
| 工作台与缩略图 | 第一阶段保存流程可靠 | 项目可搜索，列表和网格可用，缩略图缓存更新正确 |
| 页面创建入口 | 模板及组件契约稳定 | 从模板、自然语言或空白页进入同一编辑流程 |
| 选区 AI 与上下文工具条 | 选区、权限、撤销可靠 | 页面级和节点级范围准确；不遮挡关键操作 |
| 最小内置 Agent 试点 | 执行服务可用且复用现有操作契约 | 生成、局部修改、失败、取消、撤销和保存均可解释与验证 |
| 基础评审体验 | 核对现有分享、版本、评论能力 | 评审者能打开目标内容、定位问题并回到修改结果 |

进入下一阶段的门槛：相同任务集的耗时或人工修正量有稳定改善，且交互正确率不下降。若内置 Agent 的价值主要来自入口便利，保持最小实现，不扩大为独立 Agent 平台。

### 第三阶段 工程交付与团队资产

目标：把已确认的原型转成目标工程中的可维护改动，并支持后续迭代。

| 任务 | 交付物 | 验收条件 |
| --- | --- | --- |
| 一条目标工程交付路径 | 设计版本、代码基线、修改文件与验证结果 | 使用真实组件、真实路由及宿主，不创建第二套预览应用绕过集成 |
| 代码变更审阅 | 相关代码与 diff 展示，分支或 PR 流程 | 用户能看清修改范围；类型、构建和实际行为检查完成 |
| 第二轮需求变更 | 对已人工调整的工程作局部更新 | 保留无关代码改动；契约冲突被识别并处理 |
| 组件与模板资产管理 | 来源、版本、升级影响和使用说明 | 升级不会静默覆盖业务编辑；模板绑定和交互回归通过 |
| 评论驱动修改 | 评论定位、修改范围、结果关联 | 修改当前有效对象；评审问题可追踪到具体结果 |

进入下一阶段的门槛：首轮实现与后续局部更新都通过真实工程验收，人工返工量可量化。通过编译不能替代交互与视觉验收。

### 第四阶段 Figma 输入与规模优化

Figma 输入按三层推进：视觉参考、可编辑布局、真实组件映射。先选一套已有 Figma 设计系统与 React 组件库，核对组件身份、变体、Props/Slots、Token 和图标。扩展现有导入与映射能力，避免新建平行转换模型。

导入结果需要区分已映射真实组件、普通布局节点和未支持内容。无法恢复的交互或组件语义明确提示；视觉相似不等于组件契约或业务行为已恢复。只在样本证明映射可靠后扩大支持范围。

大画布优化先测量实际项目在代表性设备上的打开时间、缩放响应、切换耗时和内存。根据瓶颈考虑可见区域加载等措施；任何新渲染策略都要重新验证截图、选区和预览行为。

更广的移动端页面、复杂动效、无界面运行和多 Agent 任务，分别以实际需求与可测收益排期，不与核心业务流程捆绑建设。

## 首个验收场景

建议使用客群管理场景；若现有真实需求另有字段和行为，以需求为准。以下操作清单是产品能力验收样本，不是新增业务需求。

1. 从当前可访问的列表模板创建页面，配置筛选、分页和列表操作。
2. 增加或修改一个实际需要的 Tab，以及创建、编辑或详情 Drawer。
3. 通过 AI 或手工修改表格列、表单字段和布局，核对变更范围；执行撤销。
4. 在真实 Preview 中操作查询、重置、翻页、Tab、表单校验、提交、取消和重新打开。
5. 检查场景实际需要的 loading、空数据、失败、只读与无权限状态，明确模拟范围。
6. 保存后重开，核对页面结构、绑定和弹层初始状态；编辑时临时打开的 Drawer 不得成为运行默认值。
7. 分享给评审者并定位一条问题；在当前页面完成修订和结果复核。
8. 选定一个真实目标工程完成实现，检查组件、路由、宿主与接口契约。
9. 在工程已有人工调整后，再提出一次局部需求变更，验证无关修改被保留。

第一、二阶段先完成前七项中的适用流程；第三阶段完成全部链路。每一步都记录操作与结果，静态截图只证明视觉，不证明交互成功。

## 衡量方式与发布条件

| 指标 | 定义 | 使用方式 |
| --- | --- | --- |
| 首次可用耗时 | 开始创建到通过该任务必要交互检查的时间 | 同任务、同用户类型比较中位数和较慢样本，包含失败重试 |
| 局部修改耗时 | 提出一个明确修改到验证正确的时间 | 同时记录 AI 等待和人工操作时间 |
| 首次验收通过率 | 无需人工修正即可通过完整检查的任务占比 | 与生成速度一起评估，防止以牺牲正确性换速度 |
| 人工修正量 | 为达到验收标准而进行的纠错次数和耗时 | 区分需求变化与生成错误 |
| 工程返工量 | 原型确认后，因遗漏行为或错误组件契约导致的返工 | 用于判断真实组件路线是否产生价值 |
| 后续修改可靠性 | 第二轮修改后原有相关行为仍通过且无关内容未受损 | 必须包含人工改过的目标代码 |

先建立基线，再根据试点决定具体改善目标。悬浮条使用占比、Prompt 数量、Sync 次数和代码行数作为辅助观察，不作为主要成功指标。

发布前必须满足：本次涉及的真实交互通过，保存重开一致，撤销与失败恢复可用，只读权限正确，编辑器主题和临时状态不影响业务结果。未通过的相关检查需要修复或缩小发布范围。

试点每轮至少包含创建、修改已有页面和工程更新三类任务中的适用项，覆盖产品、设计和前端角色。小样本先用于发现问题，不能直接推导全体用户收益。

## 首轮实施任务

首轮聚焦第一阶段，按以下顺序进入开发。角色表示所需职责，不预设团队人数或人员分配。

| 顺序 | 任务 | 主要职责 | 完成证据 |
| --- | --- | --- | --- |
| 1 | 固定业务样本和运行版本，走完现有流程 | 产品与前端 | 当前流程记录、基线、按影响排序的问题 |
| 2 | 修正样本暴露的组件契约与编辑状态问题 | 组件维护与编辑器开发 | 实际 Props、交互、保存重开与必要回归结果 |
| 3 | 重组样本涉及的属性面板和内容入口 | 交互设计与编辑器开发 | 同任务操作路径缩短，数据模型保持一致 |
| 4 | 将外壳主题改为明确作用域，完善基础键盘行为 | 编辑器开发 | 两种外观下的界面检查与画布隔离验证 |
| 5 | 完善选区操作、执行反馈与撤销保存状态 | Desktop 与编辑器开发 | 成功、失败、取消及保存失败的实际操作记录 |
| 6 | 完成整体验收并复测基线 | 产品、设计与前端 | 可比较的结果，下一轮按真实障碍排序 |

每项开发任务在编辑前明确可观测的通过条件；运行受影响的最小相关检查。需要触及已有 UI 改动时，先核对当前工作区，不将文档中的建议当成已有实现或验收结果。

## 暂缓投资及重新评估条件

| 暂缓事项 | 重新评估条件 |
| --- | --- |
| 任意 React 与画布实时双向同步 | 已定义可支持语法、文件所有权、冲突处理和可接受限制，并有真实用户需求 |
| 全面替换 DOM 或 iframe 画布引擎 | 性能测量证明现有架构成为主要瓶颈，局部优化不能解决 |
| 默认隐藏所有侧栏与全局毛玻璃换肤 | 用户任务测试证明可提高效率，且不降低定位、对比与可访问性 |
| 完整矢量工具与设计软件功能对齐 | 目标用户确实需要且现有外部设计工具输入无法满足 |
| 多模型管理和多 Agent 调度平台 | 单 Agent 流程稳定，任务确实可分割，并发收益可测且编辑冲突可控 |
| 每次编辑自动同步或部署 | 具备明确的内容所有权、发布策略、恢复能力及实际使用需求 |
