# 画布加载优化方案

日期：2026-10-30（Asia/Shanghai）  
状态：图标预览去重、运行时初始化去重及主进程统一身份校验已完成本地打包安装和功能验收，见 [图标结果](icon-preview-deduplication.md)、[运行时结果](runtime-initialization-deduplication.md)、[身份结果](identity-request-deduplication.md)。组件库远程版本加载与代码/模型持久缓存已完成源码及隔离验证，待配套发布及真实 App 验收，见 [缓存实施结果](library-versioned-cache.md)。其余项目仍为方案。范围以桌面 App 重新进入画布为主，浏览器单独评估；页面模型按需加载和组件库分包注册本轮不实施。  
目标：组件库可以独立发布；同一资源版本再次打开时直接使用本地副本，不向服务端检查资源是否过期；保留项目权限检查和平台组件库自动升级。

## 2. 实测依据和适用范围

基线见 [canvas-reopen-baseline.json](canvas-reopen-baseline.json)。测量使用 0.5.26 正式构建的原始 `app.asar` 代码和资源，在相同 Electron 44.5.1 的隔离窗口运行；不是直接附着生产进程。沿用正常网络链路和磁盘缓存，一次预热后，三次从项目列表重新进入「客服平台 · GP评论查询」，修订均为 146。视口为 1512×887，保留系统语言和项目保存视图；禁用诊断窗口的自动保存，未发生项目写入。计时不含 App 进程启动。

| 项目 | 实测 |
| --- | --- |
| 三次可编辑时间 | 4,743 / 4,750 / 3,871 ms，中位数 4,743 ms |
| 启动元信息 `editor-bootstrap` | 完整请求约 405–705 ms；逻辑响应约 69 KB |
| 项目模型及依赖 | 完整请求约 1,552–2,018 ms；解压后 6,140,190 B；额外网络诊断的 gzip 正文 895,750 B |
| Antd6 3.7.0 | 中位数 820 ms；缓存正文约 967 KB |
| Overseas 1.12.0 | 中位数 673 ms；缓存正文约 36 KB |
| Antd Icons 0.2.0 | 中位数 633 ms；缓存正文约 1.79 MB |
| React UI 0.2.0 | 中位数 678 ms；缓存正文约 132 KB |
| 四库请求整体窗口 | 并行约 747–1,083 ms，不能将四项时间相加 |
| 安装包资源 | 首屏前每轮 190 次本地处理，跨 iframe 累计约 42.8 MB；处理时间之和 576–678 ms，不等于串行阻塞时间 |
| 模型反序列化 / 首帧渲染 | 77–128 ms / 309–377 ms |

额外 Chromium NetLog 诊断确认四库请求带 `If-None-Match`，网络响应为 `304`，正文从本地 HTTP 缓存读取。Renderer/CDP 和 `fetch` 显示的 `200` 是缓存合并后的逻辑响应，不能据此认定组件库重新下载了全部正文。基线 JSON 中 `encodedDataLength` 是自定义协议向 renderer 交付的数据量，不是实际网络传输量；`cacheValidation` 单独记录底层状态及正文来源。

测量后，磁盘安装包被换成同为 0.5.26 的本地构建，启用了 `localCanvasLibraries`。该构建不能与上述正式构建混为一组。后续比较必须固定 `build.kind`、`rendererHash`、`desktopHash`、项目修订、自动升级后的依赖版本、目标画板和视口；不能仅比较 App 版本号或 Git commit。

三次样本不足以作线上 P95 承诺，也没有实施任何优化后的收益数据。阶段存在交叠，不能简单求和，更不能承诺资源缓存后画布必然秒开。

## 3. 组件库独立发布与版本一致性

### 3.1 当前链路与问题

现有 [publish-library.ts](../../../platform/wab/src/wab/server/db/publish-library.ts) 可以从精确 npm 版本或本地 `.tgz` 发布组件库，同时保存模型、浏览器注册脚本、服务端注册脚本和代码依赖快照。浏览器注册脚本通过 `/api/v1/hostless-libraries/:name/canvas?version=...` 下载，代码制品与发布版本绑定且不可覆盖。仅发布 npm 包不等于完成平台组件库发布。

原桌面本地构建通过 `localCanvasLibraries` 按库名返回安装包脚本，忽略请求中的 `version`，使业务模型升级后仍可能执行安装包旧代码。当前源码已从 [prepare-assets.mjs](../../../desktop/scripts/prepare-assets.mjs)、主进程和 [asset-handler.cjs](../../../desktop/src/asset-handler.cjs) 删除该覆盖，资产测试改为验证精确版本请求不会被本地脚本替换。

### 3.2 首批最小修改

1. 删除 `localCanvasLibraries` 在资源处理器、主进程传参和打包脚本中的强制覆盖逻辑，以及对应错误测试。托管库代码按服务端返回模型中的明确版本加载。
2. 保留安装包中的编辑器、Host、画布基础运行时和字体；不在这一批修改 Antd6/React 的共享实例和编辑器注册协议。
3. 项目消费的托管库若无法解析到明确依赖版本，加载应失败并给出可重试错误，不能悄悄请求 `latest` 或使用其他版本。组件库自身的编辑场景若需要最新代码，应单独解析具体发布版本，再进入同一加载流程。
4. 首批不增加“内置库版本匹配”的另一套加载来源。后续确需预置库时，只能把已验证的精确版本制品作为同一缓存的预填充数据，不能重新引入按库名覆盖。
5. 已部署的旧客户端需要一次 App 更新来修正加载器。此后，使用现有注册协议和共享运行时能力的 Props、Slots、事件、包装逻辑及样式更新，只需要平台组件库发布。

底层 Antd6 自身目前由 Host/画布运行时提供，构建器会将部分 Antd 导入指向这个共享实例。修改底层 Antd 版本、平台 SDK 或新增编辑器不认识的属性类型，仍可能需要 App 更新。本方案不承诺所有底层依赖都能热更新。

### 3.3 保留的自动升级策略

依据 [部署约定](../../../deploy/README.md#platform-component-library-upgrades)、[BundleMigrator](../../../platform/wab/src/wab/server/db/BundleMigrator.ts) 和 [升级实现](../../../platform/wab/src/wab/server/db/bundle-migration-utils.ts)：

- 启用 `autoUpgradeHostless` 且配置 `hostLessWorkspaceId` 后，平台库消费者在下一次打开、网站发布或导出等模型加载过程中升级到平台库最新版。线上实际开关、库归属和发布标记需在实施前只读核对，本方案没有变更线上配置。
- 发布平台库会更新版本标记；已打开编辑器收到版本变化后提示刷新，不在编辑过程中无提示替换全部组件。
- 普通 Studio 设计组件库继续接受更新的流程；已退出平台升级范围的库不自动迁移。已发布网站保持现有结果，重新发布后才更新。
- 当前自动升级没有“只升小版本”的筛选。新版删除的 Props 可能使旧设置被移除；发布前应检查真实消费者和丢弃参数，不能把大版本号视为自动阻断条件。

缓存不查最新版本，服务端模型决定本次加载版本：

```text
发布库新版本 → 服务端迁移项目依赖 → 模型引用新版本
                                      ↓
                       本地有该版本：直接读取
                       本地没有：授权下载并持久保存
```

因此，“资源命中不检查过期”和“平台库自动升级”可以同时成立。项目模型和升级决策仍会访问服务端；不能为了资源强缓存跳过它们。

### 3.4 同一组件库同时提供代码与组件定义数据

按用户要求，组件库远程化与依赖模型快照复用作为同一项改造交付。本文的“依赖模型”指服务端保存的组件库定义数据，包括组件身份、属性、Slots、默认配置及对象引用；不是组件实现 JS，也不是业务项目自身的页面配置。

同一次组件库发布绑定运行/注册代码制品和组件定义数据，两者作为同一个库发布版本的组成部分。客户端使用服务端已解析、已迁移后的依赖清单，分别标识代码制品和组件定义快照的实际摘要；不能混用新定义和旧代码。定义快照按第 5.3 节处理模型迁移后的内容身份，不假定 semver 下的模型永远不变。

首次取得缺失部分时下载并缓存代码与定义快照；再次进入或其他项目使用相同内容时，分别复用本地副本。统一版本不要求两份数据必须塞进同一个 HTTP 响应，也不要求命中一份后仍重下另一份。业务项目数据、权限及自动升级结果仍从现有服务端流程获得。

首次修正加载器、支持依赖清单和接入缓存需要一次 App 更新。完成后，在既有注册协议、模型格式和共享运行时支持范围内，组件实现和组件定义变化都通过平台组件库发布生效，不需要再次发 App。新增编辑器协议能力或更换内置共享运行时仍属于 App 更新范围。

## 4. 托管组件库免校验持久缓存

### 4.1 首批存储与读取

在桌面资源处理入口接入专用组件库磁盘缓存，仅处理受信 Studio 来源、允许的组件库制品路径和明确版本的 GET/HEAD 请求。普通 API、权限响应、业务查询和任意外部 URL 不进入这套永久缓存。

- 缓存身份包含服务来源、当前账号、组件库身份、具体发布版本，以及实际 renderer/运行时构建标识。优先使用包 ID/发布 ID；不得只用库名，也不得只用可能相同的 Git commit 来区分本地构建。
- 缓存内容为原始制品及必要响应元数据；window 注册包装继续由现有 Studio 加载器负责，不保存已经包装或执行后的注册表。
- 命中且本地数据完整时，直接响应本地文件，不调用 `remoteFetch`，不发 HEAD、条件 GET、ETag 或后台过期检查。
- 未命中时先通过现有服务端权限检查下载。只保存成功且完整的响应，使用临时文件和原子提交；并发请求共用一次下载。错误响应、登录跳转页和中断文件不能成为有效缓存。
- 未指定版本的可变地址不永久缓存；下载失败允许重试，不退回安装包旧代码。损坏或缺失视为未命中。
- 策略不使用时间 TTL。按容量清理未使用版本，正在加载/使用的条目不得被淘汰。缓存被用户清除或因容量淘汰后，后续允许重新下载，不能把“无过期检查”等同于永久占用无限磁盘。
- 账号切换时切换缓存命名空间，注销时清理对应账号私有缓存；不能用其他账号缓存绕过当前账号的首次下载授权。

已有制品 `digest` 覆盖整个制品对象，不是 `canvas` 字符串的哈希；不能直接拿它校验单份脚本。若协议提供独立脚本摘要，应由发布端生成并绑定版本。没有这项协议时，可以存储下载内容的本地摘要用于检查损坏，不能将其描述为服务端真实性认证。

### 4.2 权限边界

第一次下载仍由服务端鉴权，重新进入项目仍检查项目权限。免校验的已下载代码无法在权限撤销后靠资源接口即时收回，这与当前每次资源访问都鉴权的语义不同，必须在上线前接受这一产品边界。注销/账号隔离降低误用风险，但不等于能远程擦除已取得的文件。缓存不向 Electron 主进程执行代码，保留现有 renderer 沙箱与加载来源限制。

### 4.3 改动目标

| 位置 | 目标 |
| --- | --- |
| `desktop/src/asset-handler.cjs` | 移除按库名覆盖，接入明确版本的制品缓存 |
| `desktop/src/main.cjs` | 传入受信来源、账号和实际构建身份；处理账号切换和注销清理 |
| `desktop/scripts/prepare-assets.mjs` | 停止生成强制覆盖清单，不改变基础静态资源本地化 |
| `platform/wab/src/wab/client/components/studio/studio-bundles.ts` | 保留按项目依赖版本加载及内存请求去重，消除消费场景缺版本时隐式取最新的路径 |
| 桌面资源测试与 Studio 注册测试 | 验证版本一致、免校验、失败重试、多 window 注册、升级与撤销 |

## 5. 其他资源优化的重新评估

### 5.1 安装包静态资源：保持本地化，暂不再复制缓存

当前首屏所需 JS/CSS、Host 和本次用到的字体均由安装包提供；重开仍会读文件并在新 window 执行。42.8 MB 是跨上下文累计交付量，不是远端下载量。资源处理时间之和不是可直接节省的墙钟时间。

首批不把这些文件复制到额外缓存目录，不给全部 HTML/登录页设置永久 HTTP 缓存。若后续 CPU/I/O trace 证明本地读取或分配占关键路径，再对确定热点设置有容量上限的内存缓存，按实际构建标识失效。修改响应头后是否真的避免自定义协议调用，需要实测，不能仅凭 `immutable` 推定有收益。

浏览器部署已经对符合哈希文件名规则的静态资源配置一年 `immutable`；需要抓真实响应确认代理是否保留。由整个 commit 改为内容哈希主要改善跨发布/冷打开，不能解决当前桌面暖打开。HTML 入口保持可更新，避免永远停留在旧构建。

### 5.2 图片、字体、CSS 附属资源：有版本后按需纳入

应用安装包内资源保持现状。对其他项目确实远端加载的上传图片、字体、图标和组件库附属资源，优先使用内容哈希或不可变版本 URL，才能命中直接本地读取。发布制品应覆盖 CSS 的 `url()`、动态模块等实际依赖；不能只缓存一份入口 JS 就宣称所有资源离线可用。

同一 URL 可变的第三方图片、Google Fonts CSS、自定义 Host 及其资源不做无条件永久缓存。要实现免校验，需显式导入为固定资源快照，或由发布清单指定具体版本；这会改变内容更新方式，不作为首批通用拦截功能。本次样本不足以证明这些资源值得优先投入。

### 5.3 项目依赖模型：收益较高，需要服务端快照契约

完整项目响应包含依赖模型，当前重复响应解压后达 6.14 MB，是另一主要等待来源。实现中服务端仍返回最新项目修订、权限和迁移结果，通过当前请求的内容摘要协商返回快照清单及缺失正文；主进程在交付既有 `getSiteInfo` 消费者之前还原完整响应契约。命中不增加独立快照请求，详见 [缓存协议](library-versioned-cache.md#存储和网络契约)。

补充体积分解见 [canvas-model-breakdown.json](canvas-model-breakdown.json)：再次只读获取时项目已是修订 158，Antd6 已为 3.8.0；这是新快照，不能直接代替修订 146 的耗时基线。响应总量为 6,162,950 B，其中项目修订自身为 259,468 B（约 4.2%），依赖包为 5,899,198 B（约 95.7%）。

| Admin Templates 3.0.0 | 748,416 B | 13 | 0 |
| Overseas 1.12.0 | 55,396 B | 3 | 2,206 B，1 张 |
| React UI 0.2.0 | 34,978 B | 3 | 0 |

本项目自身只有 3 个本地组件定义，模型中的 `TplComponent` 直接引用 16 种 Antd6 和 3 种 Overseas 组件，却仍接收完整图标目录和模板依赖。该统计没有分析表达式动态引用、组件实现内部依赖，不能直接把其他定义判定为可删除。

这证明体积主要来自依赖库，不是业务页面自身。`CodeComponentMeta`、属性定义和组件定义本身也占用大量数据；响应没有包含组件库可执行 JS，该脚本随后另行加载。首次进入需要分别处理“依赖模型全量获取”和“库脚本全量注册”。

**不能只按 `pkgVersionId` 或 semver 缓存模型。** 当前 `getMigratedBundle()` 会对同一 `PkgVersion` 更新 `model`，还可能迁移其依赖。代码制品不可变不代表迁移后的模型也不可变。清单必须标识实际迁移、依赖解析完成后的内容，例如由服务端生成快照内容哈希，并绑定模型格式/迁移版本；当前项目接口返回该清单就是本次权威结果，不额外做客户端过期检查。

这项已与组件库代码远程化、持久缓存合并实现，采用项目/包请求内的快照清单与缺失正文协商、本地复用及完整模型响应还原。不得永久缓存整个可编辑项目、复用过期权限，或破坏自动升级与保存版本检查。

### 5.4 减少首屏加载范围

#### 图标预览：优先直接渲染已注册组件

Antd Icons 已有可直接渲染的官方 SVG 组件，独立生成缩略图不是必要条件。当前生成缩略图是为了复用只接收 `previewImageUrl` 的卡片通道；可以增加卡片内的组件预览区域，复用 `studioCtx.codeComponentsRegistry` 中按注册名取得的实际实现，不把全套图标再次打进 Studio 主包。

**已确认的预览优先级：**

| 条件 | 预览行为 |
| --- | --- |
| 注册元数据明确配置了有效的 `thumbnailUrl` | 优先显示该图片，继续支持外部 URL 和 data URL |
| 没有 `thumbnailUrl`，且条目有明确支持直接预览的图标实现 | 渲染已注册的实际 SVG 图标组件 |
| 普通组件没有预览图，也没有上述图标预览能力 | 显示默认占位，不自动运行任意业务组件 |
| 配置的图片加载或解码失败 | 有图标预览能力则回退实际 SVG，否则显示占位；避免反复请求失败地址 |

`thumbnailUrl` 保留现有可选注册字段的含义，同类图标库以后可直接使用；不新增第二套持久化预览配置。默认 SVG 跟随编辑器深浅主题和双色预览设置；显式指定的预览图片按原图显示，不对其任意换色。预览选择和失败回退不改写组件身份、注册元数据、业务 Props 或导出方式。

实现时使用加载注册的同一套 React/ReactDOM：平台库使用 Studio 的 `__Sub`，自定义 Host 注册使用父 Host 的运行时。不能假定两者是同一实例。只对可见卡片挂载预览，离开时卸载；不为每个图标创建 iframe，不一次挂载 848 个根。预览使用 UI 主题颜色及双色 Props，不改写注册元数据或业务实例属性。

Antd Icons 默认注册不再自动生成缩略图 SVG，目录也不再生成/携带 `catalog.json` 中仅供预览的 SVG 文本；仍允许显式配置 `thumbnailUrl`。保留名称、主题分类、官方独立实现及 import、所有 848 个图标，以及 `spin`/`rotate`/`twoToneColor` 契约。默认路径可以免去约 1.11 MB 图标模型的内联预览数据，也不新增 848 个缩略图资源请求。剩余约 184 KB 非图标缩略图仍可按下一节外置。

先发布支持上述预览规则的 App，再发布取消默认缩略图的图标库。验收完整 848 个图标的搜索/插入、可见卡片挂载与卸载、深浅主题、双色预览、外部 URL/data URL 覆盖、图片失败回退及旧项目自动升级。还需测量目录打开/滚动的 CPU 与内存，不能把模型减小直接等同于整体速度提升。现有内存构建对照仅验证“外置 URL”候选的大小，不能直接视作本方案最终产物或性能测试。

#### 非图标组件：缩略图发布为独立资源

1. 在组件库构建/发布时生成与当前内容相同的 SVG 文件，以内容哈希标识。可以复用 `server/cdn/images.ts` 的 SVG 上传能力和现有内容寻址资源路径；`thumbnailUrl` 保留原字段，只把 data URL 改成可访问的绝对资源 URL。不能用 canvas 域上的相对 `/assets/` 地址假定跨域资源存在。
2. 注册脚本不再携带整套预览 SVG 文本，使用缩略图 URL。模板、运行时 Props 和组件身份不变；图标默认按上一节直接渲染组件，显式配置图片时仍遵循图片优先和失败回退规则。
3. 发布前确保资源已上传且可读，再事务性发布相应库模型和代码制品。失败不得发布悬空缩略图链接，也不覆盖已有版本；已有项目通过原平台库升级机制取得新 URL。
4. 组件目录仅加载实际展示项的缩略图，结合现有列表/滚动容器和可见性机制，避免打开目录时一次发起 848 次请求。关闭目录不预取整套缩略图。文件按哈希持久缓存，重复进入不发资源过期校验。
5. 非图标组件缩略图沿用当前预览外观。图标的深浅/双色效果由实际组件的预览 Props 实现，移除专门解析图标 data URL 换色的路径，业务实例属性不受影响。
6. 非图标缩略图需验证内容、目录加载、失败反馈、缓存命中和版本更新；图标回归要求见上一节。

上线顺序先更新 App 预览通道，再发布相应库。当前旧图标卡片直接解析 data URL，不能让新版图标库改成外链后直接进入该通道；本方案选择直接组件预览，取消图标缩略图，避免增加这一外链解析流程。发布前仍需确认受影响客户端已经具备新预览能力。

最新模型中内联缩略图共约 1.29 MB：其中图标约 1.11 MB 可通过直接组件预览取消；非图标约 184 KB 外置后仍有短 URL。不能把逻辑响应减少量等同于相同数量的压缩网络流量或固定秒数收益。

#### Ant Design Icons：保留全部图标的构建优化证据

848 个图标当前具有两类不同体积：约 3.82 MB 是依赖模型的 JSON，约 1.79 MB 是浏览器注册 JS。JS minify 不会缩小已经存入数据库的模型对象图。

源码中 `import * as Icons` 加上 `Icons[icon.name]` 动态取值并遍历全目录，意味着所有图标都可达；不能期待编译器自动删除它们并仍提供完整库。可优先剥离的是 `catalog.json` 中仅供缩略图使用的 SVG 副本，而不是官方图标实现。

[内存构建对照](antd-icons-build-analysis.json) 保持相同生产模式、压缩配置和全部 848 个图标，只把缩略图目录改成外部哈希 URL：

| 指标 | 当前目录 | 外置缩略图的诊断构建 |
| --- | ---: | ---: |
| 注册 JS 原始大小 | 1,798,149 B | 1,133,479 B |
| 同一 JS gzip 大小 | 382,824 B | 245,938 B |

这是编译期可行性对照，不是产品实现或性能 A/B；诊断使用假定的资源 URL，没有上传文件、接入预览或执行运行行为验证。显示出约 665 KB 原始 JS、137 KB gzip 的可削减空间，实际成品还要计入正式 URL 和必要的资源加载逻辑。

初步不删除属性说明、组件身份、导入信息、默认样式或模型参数：这些参与搜索、属性编辑、插入、保存或导出。生产构建已经使用 minify/production define；移除磁盘上的 sourcemap 也不能直接推算正常用户加载会更快。进一步替换动态命名空间导入为生成的显式图标导入，可以帮助剔除无关辅助导出，但收益需单独测量，不能承诺按未使用图标裁剪整套编辑器目录。

#### 暂缓：组件库分包注册

分包可以按已有职责与依赖关系组织，例如图标按 Outlined、Filled、Two Tone，复杂组件按 Form、Table、反馈等组合；共享运行时保持一个实例，静态子组件和必要 Context 随所属组合一起准备。全部组件仍存在，区别是何时取得和注册对应代码。

当前注册同步要求完整注册表，直接少加载一包可能被误判为组件已删除。因此还需定义注册是否完成、缺失项何时加载、跨包依赖、插入和撤销行为，不能仅拆 JS 文件就上线。本轮不实施，也不把它作为缩略图外置的前置条件。

#### 排除：项目模型按页面加载

按用户要求，本轮不考虑这项大改动。保留全量项目的获取和对象图语义；“依赖模型快照复用”只改变重复数据从网络还是本地取得，不意味着只加载当前页面。

首屏后台工作仍按计时判断是否影响主线程；现有目标画板优先、其他画板延后机制应保留。延后渲染、减少传输和减少注册是不同成本。

### 5.5 重复请求与执行：不靠永久缓存解决

- 身份检查：主进程 `DesktopIdentity` 为灵动岛和草稿提供同一份服务端验证结果，并发共用任务，完成后在内存复用最长 30 秒。新文档导航丢弃完成结果，同文档画布路由复用身份；Cookie、登录、退出及设备撤销作废旧身份。草稿句柄在身份代次变化后重新校验，同账号可继续，其他账号拒绝。受测首次进入和重开均从四次降至一次；见 [身份去重实施结果](identity-request-deduplication.md)。本地打包安装验收通过，不据此推算固定秒数收益。
- 运行时源码：已由 `ensureCanvasRuntime(win)` 按目标 Document 共用初始化 Promise，加载中等待，已就绪跳过，失败可重试；组件库脚本不再携带运行时前缀。隐藏注册 frame、Preview 和画板分别初始化。实测结果与边界见 [运行时实施结果](runtime-initialization-deduplication.md)。
- React 实例、组件注册表、ViewCtx、DOM 仍需创建。保留整个编辑器实例可以减少重开成本，但涉及锁、未保存数据、后台连接和内存；不纳入本次资源缓存改动。

## 6. 实施顺序与验收

### 阶段 A：修复版本来源

已只读核对线上四库最新/历史制品、目录 `hasCodeArtifacts`、自动升级开关及平台工作区配置，见 [验证记录](library-versioned-cache.json)。当前最新版均有制品，早期历史存在缺口；自动升级不会删除发布历史。缺历史制品不能随意用最新源码补成旧版本。保持同一份共享运行时，取消本地覆盖，完成真实项目的画布、属性面板、Preview、表单、Table、Tabs、主题和弹层回归。

此阶段可能恢复当前本地构建被跳过的远端校验，不单独承诺提速。面向用户的优化版本应在阶段 B 完成并验证后发布，避免只修正确性却增加可感知等待。

### 阶段 B：组件库代码与定义快照的统一加载、持久缓存

与阶段 A 合并交付一次 App 更新。使用同一库的两个不可变版本验证：不重打 App，只发布新库，项目按原有策略自动升级后，元数据与实际执行脚本同时切换。第二次进入相同版本时，受测托管库的网络请求数为零，包括缓存校验；新版本首次只下载缺失制品。

同批实现第 5.3 节的组件定义快照清单和本地缓存：确认相同定义不再随项目接口重复传输，不同项目引用相同快照可复用；迁移后的新摘要会取得新快照。代码和定义更新必须共同验证，不能只证明脚本切换或只证明属性面板切换。

还需覆盖重启后的命中、并发下载去重、失败重试、损坏/淘汰后补下载、账号隔离、旧版本仍存在时加载指定版本，以及手动升级的撤销恢复。平台自动迁移与手动升级撤销是不同流程，不能把手动撤销当作平台旧模型能永久固定不升级的承诺。

### 阶段 C：其他热点

分开提交身份请求去重、运行时重复解析修复和组件目录预览优化；每项保留独立对照。依赖模型快照已并入阶段 B，须覆盖接口和迁移一致性测试。组件库分包注册暂缓，页面模型按需加载按用户要求排除。第三方通用资源镜像、浏览器 Service Worker、共享 Antd 运行时独立发布暂不进入这批改动。

### 回归和测量门槛

1. 每一项改动的模型版本、实际注册脚本版本、画布与 Preview 行为一致；组件 UUID、Props、Slots、交互和样式按原升级规则处理，不能声称任意库更新都零风险。
2. 覆盖服务端平台库升级、版本标记通知、已打开会话提示刷新、普通设计库接受更新，以及已发布网站重新发布前保持原结果。
3. 覆盖发布前消费者分析中的删除参数和阻断项；当前自动升级会跨大版本，资源缓存不得悄悄新增或取消升级筛选。
4. 固定构建、项目修订、升级后的依赖版本、画板、视口、语言和网络，至少做交替的前后重开测试，报告单次结果、中位数、资源请求数和正文传输量。单独检查首次缺缓存与重启后命中；功能发布验证与性能实验分开，不能阻止自动升级后又声称验证了自动升级。
5. 用主进程请求记录及底层网络状态确认托管库真正零请求；不能只看 renderer 的缓存标记。记录内存和磁盘增量；不把并行时长相加作为收益。
6. 源码验证：Desktop 494 项 Node 测试、WAB 8 文件 75 项测试及类型检查通过；实际 Chromium 协议/gzip、超过 8 KiB 的摘要正文、临时 PostgreSQL 发布和平台自动升级端到端通过。具体证据及待完成的真实 App 回归/A/B 见 [实施结果](library-versioned-cache.md)。

## 7. 上线前必须明确的边界

- 线上自动升级已确认开启，当前四库最新版代码可下载；历史制品缺口及缓存清理契约见实施结果。真实业务画布仍需配套发布后验收。
- 接受“已下载私有代码不再逐次资源鉴权”的语义后，才能启用对应账号的免校验缓存；不接受则该类私有资源继续走校验，不能宣称全部资源零请求。
- 缓存只优化资源取得，不替代项目权限、最新修订和实时状态请求。
- 底层 Antd 升级和新的编辑器协议能力仍可能要求更新 App；组件库独立发布范围以既有运行时能力为界。
- 对照测量前不能承诺节省固定秒数或实现秒开。首批可验证目标是版本一致、普通组件库独立发布、缓存命中后托管库资源零网络请求。
