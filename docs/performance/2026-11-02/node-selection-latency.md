节点选中与属性面板延迟：定位及优化方案

2026-11-02。本文记录诊断和方案分析数据；当前实现与测试结果见 [优化验证](node-selection-optimization.md)。

**结论**

已在当前安装包、当前项目复现主要开销：选中切换把属性控件全部卸载，随后同步重建，形成明显长任务。当前策略让选中反馈先发生，但没有减少面板工作量。内容编辑入口的 DOM 扫描、DOM 映射的祖先可见性检查和共享滚动条的尺寸／样式测量进一步占用主线程。

本组样本没有证明模型更新队列是主要原因；也没有证据支持优先优化撤销快照或所有画板的状态比较。

**实测**

一次普通原生点击，从 mousedown 到属性面板 DOM 齐备约 405.5ms，其中 pending 解除后的面板重建形成约 334ms 主线程长任务。这是单次复现，不能作为总体均值。

18 次精确选中测量中，每类节点各 3 次；以下为 pending 解除至面板 DOM 齐备的时间，包含当前同步渲染与提交，不能解释为纯 React render 时间：

| 节点 | 中位数 | 范围 |
| --- | ---: | ---: |
| 输入框 KeywordInput | 93.9ms | 88.4–118.2ms |
| 按钮 CreateTemplate | 222.4ms | 199.1–251.0ms |
| 表格列 IdColumn | 145.5ms | 138.4–151.6ms |
| 下拉框 CouponTypeInput | 161.4ms | 154.2–162.8ms |
| 表格 TemplatesTable | 156.5ms | 155.8–178.1ms |
| 文本 ListTitle | 110.6ms | 105.5–118.7ms |

同组 18 次 `scheduleSync()` 调用为 0，视图快照和历史记录方法单次最大约 0.1ms，`getSpotlightAndVariantsInfo()` 54 次累计约 1.3ms。同步 `changeSelection()` 包含反应式更新后的耗时为 25.4–58.5ms；真正 `setStudioFocusBySelectable()` 单次不超过约 1ms。不能把所有响应时间归因于“查找选中节点”。

**明确的代码问题**

1. `StudioCtx.tsx:1389` 的 `changeSelection()` 对有效切换设置 pending，rAF 后再通过 timer 解除。`style-tab.tsx:480` 的 `SelectionInspector` 在 pending 时返回空子树，销毁全部属性编辑器；解除后完整挂载。保留外层 Scrollbar 只能保留滚动容器，不能避免控件重建。`ComponentPropsSection.tsx:353` 又使用节点 uid 作为区块 key，部分编辑器即使保留外层也会重建。
2. `CanvasContentEditorControls.tsx:92` 观察整个画布 body 的子树、class/style/hidden 和文本变化。每次刷新在 React render 中同步执行 `getContentEditorTarget()`。`canvas-content-editor.ts:100` 遍历选中项祖先，解析渲染实例，并调用 `findClippedContent()` 遍历子树逐项读取 computed style、client/scroll 尺寸；入口只需要判断是否存在，却先收集全部裁剪区域。CPU profile 已命中这条链路。后续干净布局的定向调用为约 1.1–5.4ms，不能将它单独描述成数百毫秒根因。
3. `renderState.ts:463` 的 `shouldAcceptAsMappedDomNode()` 每次检查 DOM 时向上遍历全部祖先，重复读取 computed style 和 client 尺寸；DOM 查询、渲染注册重算和内容入口扫描都会经过它。CPU profile 中该函数累计叶节点采样约 371ms／18 次切换，不是单次耗时，也不能直接相加成一次点击的阻塞时长。
4. 同一 CPU profile 中，共享 Scrollbar 底层 OverlayScrollbars 的两个样式／尺寸读取函数累计叶节点采样约 1.27s。这证明滚动条测量也是热点，但没有证明应移除共享组件或是多个重复滚动容器。面板定向读回只有一个 `[data-overlayscrollbars]` 容器，应优先减少 DOM 替换和不必要测量。

**对照实验：直接取消 pending 并不可直接交付**

仅在隔离实例内临时让 pending 保持 false，对同样六类节点交替进行两轮基线、两轮实验，未启用 CPU profiler：

| 行为 | 样本数 | 面板 DOM 齐备中位数 | 同步 changeSelection 中位数 |
| --- | ---: | ---: | ---: |
| 当前实现 | 12 | 246.5ms | 32.0ms |
| 跳过空子树阶段 | 12 | 167.6ms | 167.4ms |

面板 DOM 较早齐备约 32%，但面板计算被搬进选中同步工作，约 167ms 后才能交还事件循环。它说明复用方向有价值，也说明仅删除 pending 会损害选中反馈。隐藏属性内容的 6 次诊断对照，同步处理中位数为 21.8ms，进一步支持优先处理面板工作量。

DOM 齐备和 rAF 回调不是实际合成帧呈现时间；长任务 observer 也不覆盖全部 debugger 触发的同步求值时间，因此不使用长任务数量推导总 CPU 节省比例。

**建议方案及顺序**

| 优先级 | 改动 | 收益依据 | 主要约束 |
| --- | --- | --- | --- |
| P0 | 拆开立即选中状态与面板使用的已提交目标，保留面板外层及可复用区块；先让选中框有绘制机会，再更新面板。只重建确实依赖节点身份的编辑器 | 全量重建是已复现的最大开销；取消空子树实验有明显空间 | 等待期间旧面板不可编辑；字段值和事件必须绑定正确节点；局部输入草稿需要明确重置。不能只删节点 key 或沿用旧 props |
| P0 | 面板先挂载当前可见、常用区块；其余区块按滚动接近、展开或下一批次挂载。复用共享 Scrollbar，稳定测量目标和必要 options/events 身份 | 当前面板会产生 71–184 个控件；大量工作一次性同步提交 | 不改变组件注册契约、已配置属性可发现性、展开状态和编辑入口；不能仅通过折叠已配置项隐藏问题 |
| P1 | 内容入口存在性检测在找到第一个裁剪区域后停止；真正进入内容编辑时才完整枚举。合并相同选中身份／同一布局状态的重复扫描，过滤无关 mutation | CPU profile 命中扫描路径，源码存在“只判存在却全量收集” | 继续支持嵌套滚动、Portal、隐藏内容和重复实例，不按组件名称加特殊分支；数据/尺寸变化后必须重新测量 |
| P1 | 同一 DOM 测量批次复用祖先可见性和尺寸检查，合并读取；保留零尺寸裁剪、隐藏标记过滤 | DOM 映射祖先检查为明确采样热点 | 只在有明确生命周期的同一测量批次共享结果，不能永久缓存布局；避免牺牲选中框正确性 |
| 后续 | 在实际录到队列等待后，再评估将连续纯选择合并为最新请求 | 本轮未复现此项为瓶颈，优先级低于以上工作 | 不能丢失 blur 提交、撤销停点、组件上下文切换或真实编辑 |

P0 的“延迟面板目标”需要面板读取一致的目标上下文。不能仅冻结 React children：其内部 MobX observer 仍可能直接订阅当前 ViewCtx 的焦点，提前执行旧面板的重活。先审计相关读取，使一次面板更新使用同一个选中目标和版本；旧目标退出后取消其待执行挂载，防止连续点击时积压旧面板。

不优先采用：把 rAF 改为固定几十毫秒防抖、把所有控件扔进一个 idle callback、仅加入 `useMemo`、用 worker 执行 DOM/React 工作、直接迁移整个 Studio 到并发 root。当前 `components/Shell.tsx:120` 使用 `ReactDOM.render`，不能假设加 `startTransition` 就获得可中断渲染。这些方案要么移动同一长任务，要么范围大于已证实的问题。

**实施验收建议**

先在固定修订、窗口、缩放和相同机器上分别测输入、选中框实际绘制、首批可编辑属性和完整面板，不用一个 pending 标志代替四项。每类至少 30 次，包含快速连续切换、同节点重复点击、树和画布选择、复杂表格、多画板、隐藏 Tab/弹窗、编辑属性后切换、undo/redo、预览与导出。CPU profile 单独录制，时延对比不启用 profiler。

可作为首轮目标而非已实现结果：普通选中到选中框实际绘制 p95 <50ms；首批可用属性 p95 <100ms；减少超过 50ms 的单次控件挂载任务。达不到时按区块定位继续减少同步工作，不增加等待掩盖问题。所有异步结果核对选择版本；只允许最新目标可编辑，业务 props、保存模型与 undo 语义保持正确。

本轮没有完成生产修复或功能回归，未承诺复杂页面和其他硬件上的固定提升比例。依据是同一项目的有限样本、CPU 采样、源码核查及临时 A/B。
