# 编辑器直接启动与画板提前准备：独立原型对照

后续已集成 [纯资源预取](resource-prefetch-validation.md) 和 [直接编辑器正式实现](direct-studio-validation.md)。本页以下记录仅针对当时的两个诊断原型，不是当前正式实现的验收结论。

2026-11-05。两个原型分别完成构建、完整类型检查和真实模型功能回放。**仅保留诊断结果，没有改动产品源码、替换已安装 App 或部署服务。组件库按需加载本轮仅评估。**

初轮观察：直接启动的首画板中位数少约 67–111ms；画板提前准备在 GP 稍慢、十画板稍快，没有一致改善。用户指出外部操作可能干扰后，新增三组更密集交错对照：基线 **1537.05ms**，提前准备 **1550.00ms**，相差 **12.95ms**。这不足以将初轮约 42ms 差值认定为稳定退化，也没有证明当前原型缩短总体等待。两项均未达到一秒可编辑目标。

逐轮脱敏数字、源码/制品身份和功能结果见 [指标 JSON](startup-architecture-experiments.json)。

## 两个原型实际改了什么

### D：内置 Host 与编辑器合并到同一 Document

原链为外层应用 → 内置 Host Document → Studio Document → 画板。原型改成外层应用 → 直接加载的 Studio Document → 画板；把相同内置 Host 的 sub runtime 放入 Studio Document，组件与业务画板仍按原逻辑执行。

原型新增独立的诊断 HTML，调整 Host window 的明确归属、注册表、字体观察与组件注册入口，以及顶层桥接的父窗口位置。原来的 iframe 布局初始化会访问同源父文档；直接文档的父页面跨域，因此由现有外层 iframe 布局负责位置，内层只设置自身 body 的裁剪。

外层 API 桥和原项目模型交接仍保留，模型、依赖版本、库注册与业务渲染工作不删减。这个实验只检验移除中间 Host 文档的净效果，不能声称已实现编辑器与外层应用完全合并、免除全部 RPC 或免除 Host 运行时。自定义 Host 没有迁移。

合入复核还发现一个具体的诊断实现差异：原 Host 从自身 Canvas 来源读取 `/static/sub/build/client.<hash>.js`，D 的 HTML 将它写成 `PUBLIC_URL` 下的绝对地址。即使字节相同，请求 URL 已改变；已有缓存无法保证复用，真实网络下首次打开可能增加资源取得成本。本地离线回放不覆盖这一点。正式实现应保留原 Host 资源 URL 和版本，而非将这个诊断细节直接带入产品。移除中间 Document 与空 Host 挂载本身没有新增模型重建或组件执行步骤，但不能因此保证所有冷缓存、网络和布局场景必然更快。

### P：项目初始化期间提前准备一个空画板

在内层 Studio 开始导入时，并发准备一个空的内置 Host iframe、基础 canvas runtime 和 ReactWeb bundle。之后目标 CanvasFrame 接管同一个 iframe 和 Document，再走原组件库注册与项目绑定逻辑。没有多启动一套业务编辑器，也没有预渲染业务内容。

接管使用状态保持的 `moveBefore()`；运行时断言 Document 身份和准备标记保持不变，避免通过重新加载 iframe 制造假并行。所用能力及 iframe 状态保持语义见 [Chrome 官方说明](https://developer.chrome.com/blog/movebefore-api)。本轮只验证当前 Electron 运行环境，不宣称 Web 跨浏览器支持。

提前创建的空画板只带 `canvas=true`，没有业务根；绑定时按原目标设置真实画板 hash、全局变体，再初始化 ViewCtx。精确组件库注册仍等待原模型路径，没有猜版本、裁剪契约或跳过编辑映射。

**P 是文档和基础环境的提前准备实验，没有实施轻量启动清单或完整组件注册并行。** 当前 Root 已经预取项目和依赖资源，新原型能重叠的剩余等待有限；不能把它解释成从完全串行到完全并行。

## 初轮计时

Apple M4、Electron 45.2.1。当前冻结源码 HEAD `3cbd431d3a126ab7e53091e3034644cddde0043b`，基线与两个候选分别独立生产模式构建。匹配既有内置 Host、runtime 与精确版本组件库资源。两个已有真实冻结项目载荷，每个项目、每个版本两个独立进程，每进程六次打开，排除前两次，保留八个暖样本。

GP 顺序为 A/D/P/P/D/A，十画板顺序 A/P/D/D/P/A。共 12 个进程、72 次打开、48 个暖样本。各版本项目模型与依赖 SHA256 一致。构建、类型检查、功能、正式计时分轮串行；正式计时无 debugger、trace、周期性内存采样或强制 GC。相同诊断输入保护阻止测试窗口中的真实键鼠、粘贴与拖放；没有控制其他用户应用、操作系统文件缓存、CPU 频率或热状态。

单位 ms，以下是内部首画布揭示标记的中位数，**不是屏幕合成完成或实际输入完成时刻**。

| 项目 | 基线 A | 直接启动 D | 提前准备 P |
| --- | ---: | ---: | ---: |
| GP 单画板 | 1629.80 | 1518.80 | 1671.40 |
| 十画板目标首画板 | 1427.95 | 1361.30 | 1396.05 |

十画板全部渲染中位数：A **4003.90ms**、D **3915.10ms**、P **3975.20ms**。GP 的基线进程中位数分别为 1699.70/1581.70ms，相差 118ms，大于 P 相对合并基线的 41.60ms 差值。不能据初轮单个合并中位数认定稳定变慢，也不能把 D 的观测改善外推为普遍收益。

## 外部负载质疑后的复测

同一基线和 P 的未变更 renderer，增加 ABBA、BAAB、ABBA 三个相邻分组。每进程四次打开、前两次预热后排除；共 12 个独立进程、48 次打开、24 个暖样本。没有改变渲染实现、强制 GC、删除慢样本或按 CPU 负载筛选数据。

每次打开额外读取系统 CPU 累计计数和 load average；进程启动记录 `pmset -g therm`。系统 CPU 忙碌度包含诊断 App 和其他应用，不能识别哪个用户操作造成干扰。`pmset` 未记录 warning 也不代表频率和温度严格受控。

| 指标 | A | P |
| --- | ---: | ---: |
| 首画布揭示中位数 ms | 1537.05 | 1550.00 |
| 暖样本范围 ms | 1518.20–1563.70 | 1537.20–1594.40 |
| 系统 CPU 忙碌度中位数 | 31.57% | 32.60% |
| 系统 CPU 忙碌度范围 | 29.63%–40.19% | 29.51%–39.93% |

按每组两侧的进程中位数平均后作差，P−A 分别为 **13.93 / 26.30 / 12.58ms**。本轮均未观察到 P 更快；样本仍少，环境没有完全隔离，不声明统计显著性或普遍退化比例。

复测阶段中位数如下；阶段含调度和并发工作，不相加当作纯计算成本或可节省时间。

| 阶段 ms | A | P |
| --- | ---: | ---: |
| 画板文档准备 | 101.75 | 60.90 |
| Host user body 等待 | 5.85 | 0.80 |
| 基础运行时 | 7.20 | 0.20 |
| 组件包准备 | 108.75 | 144.55 |
| 首次渲染 | 358.25 | 379.85 |

P 确实缩短了后续文档/基础运行时等待，但组件包与首次渲染阶段更长。它们仍在同一渲染主线程运行；“提前发起”不会让同步计算自动同时执行。原型还新增了模块加载、准备与接管协调。现有证据支持继续检查执行顺序和竞争，但**不能把增加的时间全部归因于原型自身，也不能归因于用户某次操作**；本轮没有取得针对该差值的新 CPU 栈归因。

最终表述应为：**当前 P 原型没有证明总体提速，原因尚未完全归因。** 初轮“慢了约 42ms”只是观察差值，不是已证明的代码退化。

## 不依赖计时数字的代码复核

用户提出可以依据明确的代码收益决定合入。复核后，当前 P 并不是纯粹删等待或复用已有工作，不能仅凭“并行”名称认定应当更快：

1. 外层 `Root` 已启动 `resolveProjectModel(opening)`，与 Host 初始化并行。P 在内层 Studio 导入时才启动，不能再省一次已经被原链并行覆盖的完整项目网络等待；模型解包仍为主线程同步工作。
2. P 的 `prepareCanvas()` 自行 `fetch`/`text` Host HTML；`StudioCtx` 构造函数仍无条件发起原有 `fetchHostPageHtml()` 预取。单画板通过接管分支绕开后者，留下无人消费的原预取。即使浏览器命中缓存或合并底层请求，两条 JS 读取路径仍存在，不能声称资源读取工作量不增。多画板的后台 frame 可能消费原预取，因此项目之间开销也不同。
3. P 先以 `canvas=true` 和临时尺寸启动文档，随后原子移动 iframe、更新尺寸/属性、替换为最终 hash 并额外派发 `hashchange`。原版在执行 Host 脚本之前就写入最终画板 hash。这些接管和状态协调步骤是新增工作，hash 事件还可能触发 Host Canvas Context 更新。
4. Host 脚本执行、模型对象构造与 React 渲染仍争用同一渲染主线程。提前发起可以隐藏 I/O 等待，但不能同时执行这些同步 CPU 工作；当前原型没有移除它们。

以上能说明为什么 P **可能没有收益或变长**，不能将某个毫秒差值精确归因到一行代码。当前不合入的依据包括确定的冗余和新增生命周期，而非只依据有噪声的计时。

更小的后续候选应从纯资源预取入手：启动预取与原消费者使用同一个 Promise，资源只读一次，保持组件执行、最终 hash 设置和真实画板创建顺序。它有更清楚的等待重叠路径，也不需要接管隐藏 iframe；仍应完成真实调用链和功能检查，不能因理论成立就跳过验证。本轮没有将此后续候选写入产品。

## 功能、画面与检查

最终三份制品分别在两个真实项目完成：首/中/末画板访问、重命名、真实 DOM 样式、画板位置、撤销重做、完整客户端保存及重开后模型/修订一致。GP 额外验证真实 Preview 业务分页及返回；十画板额外验证冷画板销毁后的撤销、重做、选择与样式恢复。D 的实际父页面为 TopFrame，证明中间文档已移除；P 的目标画板保留原准备 Document。三组完整注册均为 981 项，没有通过删组件取得成绩。

最终有效功能及计时轮 renderer error 为零，被阻断意外写入为零。每个正式初轮进程仍有七项既有 Dashboard 缩略图 fixture `undefined.map` 错误，单列保留；不宣称缩略图生成通过。所有 HTTP/WebSocket 为离线夹具，保存只在隔离进程中确认，没有真实 API/IAM、原生草稿 IPC、业务后端或线上数据库保存验收。

已查看三个版本的最终十画板截图。滚动条显示状态存在截图时刻差异，追加只读 DOM 探针确认 Document 可视尺寸、画布滚动尺寸相同，原共享滚动容器继续隐藏原生滚动条；未断言像素级一致或所有交互等价。

D、P 各自完整 `tsc --noEmit --incremental false` 通过，没有抑制错误或降低配置。初次诊断源树缺少工作区依赖目录与本地 SDK 声明，修正诊断链接后重新构建并对最终三份制品重新完成六组功能验收。初次 D 构建插件的产物结构错误及随后跨域布局失败均保留记录，不进入正式计时。旧编辑器 PID 在正式返回 Dashboard 的断言中退出；没有新的内存专项对照，不报告峰值或常驻内存收益。

## 组件库按需加载的实际范围

现有 [Antd6 构建](../../../plasmicpkgs/antd6/rollup.config.mjs) 已提供 `skinny` 按组件入口，因此多数组件的业务实现可以保留。但 [registerButton](../../../plasmicpkgs/antd6/src/registerButton.tsx) 仍把组件实现和注册元数据放在同一模块，[registerAdditional](../../../plasmicpkgs/antd6/src/registerAdditional.tsx) 还包含多个组件；[内置 Host](../../../platform/sub/src/index.tsx) 又全量导入 Antd6。仅改 `registerAll()` 或加动态 import，不能保证省掉整个 Antd 初始化。

可以区分两档：

- **按整库缩减单个画板的执行范围**：保留 Studio 隐藏注册 iframe 的完整契约，只让画板执行自身确实需要的库。范围较小，但全局注册成本仍在，需覆盖全局 Context、函数、嵌套组件与动态引用。
- **同库内按组件加载**：拆开完整契约与实现加载状态、重组组件/共享运行时的构建入口、处理传递依赖，并让编辑器区分“未加载”和“真正不存在”。这是注册、打包和编辑器协作的较大改造；契约必须来自原注册源码，保留动态控制，不维护另一套手写属性模型。

本轮没有修改以上组件库/注册源码，也没有为按需加载增加并行契约或兼容层。
