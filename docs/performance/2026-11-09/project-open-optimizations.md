**启动引用修复。** Root 直接创建 `NonAuthCtx`，InitializedApp 将 App 关联到同一个上下文，随后沿用 `loadAppCtx()` 的一次性交接与清理。Root 的 Loadable 结果因此不再通过另一份输入对象持有已消费的模型 Promise。初始化失败时原启动数据仍保留供重试；模型补齐继续与入口初始化重叠。

真实 renderer 的 React 根状态读回确认：基线在就绪后仍有 `initialProjectModel` 和 `initialProjectInfo`，修复后两者均为空。新增回归测试在原实现上触发对象所有权断言失败，修复后通过，覆盖失败重试后成功释放。

独立诊断进程按 A/B/B/A 检查，每项目每侧两个进程。GC 后的编辑器 isolate 堆中位数：GP **124.54→120.09 MiB**，十画板 **247.86→243.28 MiB**，差值分别约 **4.46 / 4.58 MiB**。这是整个被测 isolate 的堆，不是某个 iframe 的私有 retained size。只有这组归因诊断调用 GC，产品代码和自然内存对照均未调用。

**对照方法。** 从当前未提交工作区冻结源码，HEAD 为 `a475f219bfae530ba61900e8e5b310020cbb8292`。Apple M4、24 GiB、macOS 26.6.2、Electron 45.2.1 / Chromium 156.0.8078.75、React 19.3.1。四份独立生产模式诊断构建使用相同 Host、基础 canvas、ReactWeb 运行时及精确版本库资源；公共运行时哈希一致，修复产品文件与验证构建输入一致。

使用既有 GP 单画板与复杂十画板真实模型离线夹具。复杂样本来自真实发布 Site，接口修订 0 是夹具外壳；不是当前线上项目的完整响应录制。HTTP、Socket 和保存由私有后端回放，不包含线上 API/IAM、原生草稿 IPC 或业务网络延迟。

**组件库选择的范围与结果。** Studio 的隐藏注册文档保持完整契约；业务画板根据现有模型中的组件引用、Slot 内容、全局 Context、库声明依赖及函数/代码库选择执行范围，仍使用原注册源码和精确依赖版本。没有拆分 Antd Host 或维护另一份组件属性模型。

GP 初始库安装从 4 个降到 2 个，十画板合计从 40 次降到 29 次。GP 加载时间基本持平，十画板全部渲染观察到约 135 ms 改善；活动总工作集分别少约 19 / 41 MiB。安装次数减少不能直接当成时间收益。候选尚未产品化，完整自定义 Host 和任意动态引用没有纳入本轮覆盖。

**离屏创建与缓存预算的范围与取舍。** 原型只调整自由画板布局：按视口及四分之一邻近范围延迟首次创建，保留已访问、选中、内容编辑和镜像目标；布局仍保留全组尺寸。另在现有 Arena 回收器增加 12 个逻辑画板的诊断预算，当前和固定 Arena 受到保护。它不是全局内存硬上限，也不是产品默认设置。

总览中两侧均有 10 个 ViewCtx，候选没有省去初始化，活动工作集反而观察到约 **76 MiB** 增加；没有将小幅耗时变化宣传成稳定提速。该资源差异未作函数级归因，现阶段按回退处理。

恢复单画板视口时，较晚取样的 ViewCtx 为 **10→2**，总工作集少约 **107 MiB**。随后实际缩放总览，两侧均验证十画板全部渲染；从缩放动作到就绪的检测中位数为 **1663→2029 ms**，候选约多 **366 ms**。这部分初始化被延后，没有消失。

缓存预算另作完整 ABBA，每进程四次打开、前两次预热后排除，每臂四个暖样本。每次在十画板总览后访问四个组件 Arena，再返回原画板。存活 ViewCtx 为 **14→4**，但自然总工作集没有稳定下降：对照暖样本范围 **1681.5–1845.5 MiB**，候选 **1811.8–1860.3 MiB**；不将逻辑对象数下降当成 RSS 节省。重入原画板的就绪检测中位数从 **54→387 ms**，约多 **333 ms**。这也不等于操作系统输入延迟。

第 3 项已放弃，不再推进或启用。单画板视口虽有内存收益，总览资源回退、延后加载及重入成本不足以支持采用；以上测量保留作决策依据。
