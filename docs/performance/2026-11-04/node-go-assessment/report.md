# Desktop 剩余 Node 模块迁移评估

结论：不建议全部迁移 Go。MCP 已移出 Electron；剩余模块主要共用一个 Electron 主进程，迁移单个函数不能再省掉一套 Electron/V8。下一步优先隔离同步图形计算、减少存储数据转换。Go 存储进程是有条件的候选，当前证据不支持直接重写所有模块。

本轮只新增诊断程序与报告，没有修改产品实现、正常用户数据或已安装 App。

## 方法与边界

- 环境：Apple M4、macOS arm64、Node 24.20.0、Go 1.26.5。
- [生产函数对照原始数据](benchmark.json)：23 个场景，主线程和 Worker 各一个新进程，每进程一次冷调用、三次暖调用；串行，无强制 GC。暖值取三次中位数。主线程和 Worker 使用相同生产实现；Worker 计入输入/输出 structured clone 和首次创建成本。
- 每次调用在计时外校验输出摘要；导出校验全部落盘文件内容。23 个场景均一致。PDF 另复用生产的 load/copyPages/save 流程，仅比较页数及字节长度，未覆盖字体、图片、表单或视觉一致性。
- 主线程延迟用提前启动的 1ms 心跳记录，扣除名义间隔；每个子进程先用 100ms 同步阻塞做正向控制，实测检测到 99.1–101.6ms。这里是任务执行期的最大调度延迟，不是 UI 帧率，也不是 Electron 端到端操作耗时。
- 数据是合成夹具，覆盖普通和较大输入；未访问 NAS、正常 profile 或真实登录。操作系统文件缓存不受控。独立 Node 运行不能替代 Electron 打包后的原生模块和窗口交互验收。
- RSS 是各测试进程的工作集，包含同进程 Worker，与物理 footprint 不同；没有强制 GC，不能把 RSS 差值直接当成产品内存收益。主进程 heapUsed 也不包括 Worker 的 JS 堆。

### 位图和矢量

`raster-vector.cjs` 的 PNG 解码与 ImageTracer 都同步运行；`controller.cjs` 直接在 Electron 主进程调用。1024² 已是产品允许的上限，实测确实存在约 0.4 秒的连续阻塞。Worker 能保持同一算法、SVG 输出与协议，本夹具全部摘要一致。改成 Go 需要移植 ImageTracer 或替换算法，不能假定轮廓、调色板、透明度、路径简化与 SVG 一致，因此先做 Worker 的风险更低。

`vector.cjs` 使用 Paper.js 的贝塞尔布尔运算。两路径首次调用主线程耗时 338.7ms、延迟 341.3ms，而暖调用只要 2.7ms；首次模块加载比普通计算更值得隔离。64 路径暖操作从 32.2ms 延迟降到 2.8ms，但总耗时从 31.8ms 增到 44.2ms。换 Go 几何库还要验证曲线、孔洞、方向、相切、自交和浮点容差；本轮没有声称完成这一兼容性证明。

Worker 也有成本：1MP 描摹末轮 RSS 为当前 263.7MiB、Worker 315.1MiB。它改善响应性，不等于降低内存；生产候选应按需创建、限制并发并在空闲时销毁，不能为每个 MCP 连接各建一个 Worker。这里尚未验证 Worker 销毁后的 Electron footprint。

### 草稿与资源缓存

草稿 IPC 已传 JSON 字符串，但主进程 handler 仍先 `JSON.parse`，store 再 `JSON.stringify`。写入链路可把字符串一直送到后台，由后台验证和落盘，仅返回小回执。读取若仍返回完整对象，会再次触发大量对象复制；本次 Worker 暖读取 90.5ms，主线程延迟 25.1ms，均差于原实现。应评估字符串或可转移字节直达消费端，而不是原样搬函数。

目录冷读 8 份草稿：当前 201.3ms / 最大延迟 70.1ms，Worker 184.7ms / 1.4ms；暖目录已通过摘要缓存降到约 0.3ms。若迁移存储所有权，必须保留队列顺序、序号保护、账号/项目授权、配额、fsync、原子替换与 previous 恢复，不能只移植文件读写。

资源缓存磁盘格式把正文转 base64，嵌入 JSON，并对包含 base64 的 JSON 计算校验摘要；读取反向操作。32MiB 正文会变成约 42.7MiB 的 base64 文本，增加主线程转换与临时分配。优先候选是原始二进制正文配小元数据，保留身份隔离、发布版本与完整性检查；协议和文件格式的改造本身有收益，不依赖 Go。Worker 不是自动省内存方案，例如 32MiB 写入末轮 RSS 当前 520.1MiB、Worker 554.9MiB。

Go 可作为后续统一后台存储的候选：由一个 App 所有的按需进程集中处理缓存和草稿，走私有 pipe/stdin，不开 HTTP 端口、不要求 MCP 客户端释放。要先证明数据传输和恢复语义，再决定是否值得引入另一套进程生命周期。当前不建议为每类存储或每个连接新增 Go 常驻进程。

### Go JSON 原型

另做了独立、仅标准库的 Go 原型，对同一 12.61MiB JSON 做“解析为通用对象树，再序列化”，与 Node 使用相同的长度前缀 STDIO 传输；两种 runtime 按 ABBA 各启动两次，每次一冷三暖，返回完整结果并在计时外验证语义一致。见 [原始数据](json-runtime.json)。

| 指标 | Node | Go |
| --- | ---: | ---: |
| 暖处理往返中位数，6 次 | 53.2ms | 121.6ms |
| 末轮子进程 RSS，两进程中位数 | 246.9MiB | 170.0MiB |
| 同一可执行文件重复启动到 ready 中位数 | 29.8ms | 8.9ms |

该通用对象树实现中 Go 处理往返约为 Node 的 2.29 倍，RSS 较小。Node V8 原生 JSON 与 Go 标准库的对象分配、键排序等行为不同，不能从语言名称推断 JSON 吞吐；这不代表所有 Go JSON 方案的上限。Go 诊断二进制为 2,096,786 字节，gzip 为 894,894 字节；它不包含完整存储功能，不能当成最终存储进程的包体预算。

刚构建的 Go 文件第一次执行曾观察到 675.1ms 到 ready，尚未归因；[首轮数据](json-runtime-first-launch.json) 保留该现象。重复启动表不包含这一首次执行成本，不能据此保证首次安装启动在 9ms 内。此实验未测完整草稿、Electron IPC、耐久性与协议兼容，也不能把 Go 子进程少用的 RSS 当成 App 净节省——Electron 主进程仍然存在。

### RPC、更新、图片与 Electron 边界

- RPC 普通小响应暖往返约 0.5ms，无需重写服务端。发现 `requestRpc()` 这个 Node 客户端每收到一块数据就对整个累计字符串做 `Buffer.byteLength`，出现重复扫描。8MiB 响应暖往返 1039.3ms；同一服务端配诊断用分块累计客户端为 14.9ms。两者所有结果摘要一致。这是线性累积方式可解决的问题。生产 MCP 的 Go 客户端已使用有界 `io.ReadAll`，不经过该 Node 客户端；受影响调用点主要在 `diagnose-inspection.cjs`、`install-local.mjs` 和测试。这里不是当前 Go MCP 的吞吐测量，也未改动这些调用点。
- 更新下载的网络、文件流与流式哈希已经异步，且使用 Electron session 的 fetch。需要关注的是同步 gunzip/JSON 和规划；65536 块的大包可放后台。没有测真实网络下载，不能把表中 blockmap 数字当成下载加速。
- Sharp 已使用原生 libvips。2048² 预览暖压缩 114.9ms，但主线程延迟只有 1.6ms；首次有约 20.6–43.4ms 模块加载阻塞。更换 Go 不会自动替代既有原生图像核心，反而需要新的编码实现/依赖及画质对照。
- 截图、打印 PDF 的页面渲染、窗口、原生菜单、剪贴板、登录/cookie、Electron session.fetch 和 protocol handler 依赖 Electron/Chromium。保留 Node 控制层；把外围包装函数改 Go 仍离不开这些能力，也省不掉浏览器进程。PDF 仅合并步骤是独立计算候选，表中未包含 Chromium 渲染。
- MCP 配置读写（JSONC/TOML/YAML）和图片服务请求也有 Node 代码，但前者是设置操作、后者主要编排网络与既有 Sharp。仅作调用路径审查，未做代表性性能基准，当前没有支持迁移的证据。配置编辑还需保留注释及现有格式行为。

## 建议执行顺序

1. **先做图形 Worker**：描摹和 Paper.js 按需后台执行，沿用算法和输出协议；验证打包后三平台、取消/退出、空闲销毁、并发限制与复杂图形保真。首要收益是避免主进程连续阻塞，不承诺节省内存或所有输入都更快。
2. **再改存储数据路径**：缓存减少 base64/大 JSON 转换；草稿写入保留字符串、读取避免完整对象中转；保留摘要缓存及耐久性/授权不变量。之后在同一协议下复测 Node 后台与 Go 存储进程，再决定语言。
3. **低成本修正 Node RPC 客户端累计方式**：收益明确，主要改善诊断脚本；保持响应大小限制、取消与错误语义，无需服务端 Go 重写。
4. **暂缓代码导出、普通 PDF 合并、Sharp、下载网络及 Electron 控制层迁移**。大 blockmap/PDF 在真实频率证明有价值时复用后台计算能力。

评估已完成；上列产品优化尚未执行，不把诊断原型视为已集成能力。

## 启动、包体与验证

描摹、Paper.js、Sharp 和 PDF 的重依赖已经按使用加载。表中“冷调用”是功能首次调用，不是 App 启动；迁移不能直接承诺改善 Desktop 启动时间。图形后台化主要避免首次导入及计算阻塞窗口所属主进程。

剩余功能迁移 Go 后，Electron/Chromium/V8 仍须随 App 分发，不能重复套用 MCP 去掉独立 Node runtime 的包体降幅。完整 Go 图形、存储及 PDF 实现尚不存在，也未做发布包 A/B，本轮不编造它们的包体或 App 内存收益。唯一实际测出的新增 Go 文件大小是上述 JSON 诊断原型。

实际完成的检查：

- 23 个场景的主线程/Worker 对照检查通过；JSON 原型两轮 ABBA 的返回值语义检查通过。
- `node --check` 两个新增诊断脚本、`go vet desktop/tests/performance/json-runtime.go` 均通过；Go 原型已实际构建并执行。
- 相关生产测试 69 项通过，0 失败：`node --test desktop/tests/vector.test.cjs desktop/tests/drafts.test.cjs desktop/tests/image-preview.test.cjs desktop/tests/code-export.test.cjs desktop/tests/local-rpc.test.cjs desktop/tests/raster-vector.test.cjs desktop/tests/library-cache.test.cjs desktop/tests/update-download.test.cjs`。
- 未改生产代码，因此未执行整包发布或替换已安装 App；Go 其他目标平台、Electron Worker 原生依赖和真实项目端到端验证留在实际实施时完成。

## 复现

从仓库根目录运行，性能采集与构建/其他性能测试分轮串行执行：

```sh
node desktop/tests/performance/node-candidates.cjs /tmp/node-candidates.json
go build -trimpath -ldflags='-s -w' -o /tmp/plasmic-json-diagnostic desktop/tests/performance/json-runtime.go
node desktop/tests/performance/json-runtime.cjs /tmp/plasmic-json-diagnostic /tmp/json-runtime.json
```

诊断脚本与原型都不被发布入口导入。产品候选的功能验证还需使用真实 Electron 与实际项目载荷。
