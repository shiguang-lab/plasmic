## 开销归因与继续优化方向

骨架本身有较多占位节点，以及 `background-position` 渐变动画；它不是无绘制成本的基线。独立 trace 仅用于诊断，未计入正式成绩；从首个 `studio-entry` 到 `canvas-revealed` 的观察窗口内，S/C 分别记录 Paint 事件 108/65 次、UpdateLayoutTree 323/295 次、Layout 210/211 次。C 另有 70 次图片解码，S 为零。窗口长度不同、事件存在嵌套，这些计数不能相加成为关键路径耗时或当作帧率，但支持“应比较整个加载展示的净成本，而非只统计新增图片解码”。

正式样本中，GP 首次画布渲染阶段中位数 S 为 391.55ms、B 为 412.70ms、C 为 392.10ms；候选没有消除业务渲染长任务。顶层探针窗口最大长任务中位数 S/B/C 为 GP 352.5/377.5/352.5ms、十画布 144/154.5/153ms。加载总时间改善也不等于所有主线程任务变短；阶段存在嵌套，不直接相加归因全部差值。

后续候选按以下顺序验证，**本轮尚未实现或验证这些新方案的收益**：

1. 在外层启动画面覆盖宿主期间，不仅停止动画，还跳过隐藏的静态 SVG 子树及遮罩字符串构建。利用现有宿主揭示确认恢复本地加载，覆盖初始化失败、重试、后续画布加载和预览路径，避免以永久删除反馈换取数据。
2. 小范围验证静态品牌遮罩加 `transform` / `opacity` 的构造原型，尝试减少逐帧 WebP 解码。是否保留所需构造细节、是否真正由合成线程推进，必须用主线程阻塞捕获和 trace 验证。[Chrome/web.dev 动画指南](https://web.dev/articles/animations-guide)说明了优先限制到合成属性的依据，不能仅凭 CSS 动画认定已加速。
3. 若需要精确保留沿路径构造，试验 Worker + OffscreenCanvas，以共享品牌路径绘制，流光继续使用已验证的原生合成方案。[MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)说明了 Worker 绘制能力；线程启动、绘制、纹理上传和资源释放仍有成本，必须与骨架同轮验证，不能提前承诺更快。

每个候选继续看首次打开、热加载中位数/P90和全部画布完成时间；不以动画流畅度替代加载门槛，不把初始成本转移成首次编辑或首次预览卡顿。
