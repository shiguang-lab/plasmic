# 保留构造与流光的加载动画优化

后续构造阶段实现、真实加载差异与取舍见 [构造阶段对照](loading-construction-compositing.md)。

2026-11-04。用户选择保留构造与流光效果。本轮保留原 SVG 构造算法，将等待流光移到静态 Logo 遮罩下的 HTML 图层，并限制构造属性更新频率。没有将动画改成呼吸、旋转或静态图。完整证据见 [脱敏数据](loading-animation-compositing.json)。

## 卡顿来源与实现

上一轮轻量版的流光仍是 SVG 内部带 clipPath 的矩形。虽然使用 Web Animations，实际仍发生 SVG 重绘。在独立 Chromium 探针中，主线程阻塞时该流光的捕获画面停止变化；只看到“active accelerated transform animation”的图层原因，不能证明整条可见渲染链路已独立于主线程。

现在由静态 CSS mask 保留 Logo 的精确轮廓，HTML 渐变条使用 transform/opacity 动画扫过它。遮罩取自共享 branding 路径，无额外网络资源。扫光宽度、范围、透明度和 2400ms 周期对应原效果；构造仍约 3192ms，等待动画提前声明延迟，构造完成不再重新创建流光。

构造保留原路径流动、线框与填充曲线。在最初属性不变的阶段不重复写 DOM，后续 mask 更新限制在约 60Hz。高刷新率屏幕上的原生路径运动保持自身时间线；构造结束后仍停止 JS 帧循环并释放临时路径。减少动态效果设置与卸载清理继续生效。

[浏览器动画指南](https://web.dev/articles/animations-guide)建议优先采用 transform/opacity 并验证实际渲染阶段。本轮还验证了真实捕获表面，未仅凭 API 名称判断流畅性。

## 等待阶段的独立对照

macOS arm64、Electron 45.2.1、可见隔离窗口，读取实际构建 HTML 和对应动画源码。按旧/新/新/旧顺序，各窗口进入等待阶段后采样。此轮无并行构建、测试或项目打开计时。

| 指标 | 轻量版原实现 | 最终实现 |
| --- | ---: | ---: |
| 900ms 等待窗口 Document TaskDuration，两次 | 45.25 / 55.04ms | 2.18 / 2.13ms |
| 主线程阻塞约 1200ms，100ms 间隔捕获的不同画面数 | 1 / 1 | 9 / 9 |
| 构造结束累计 setAttribute 调用，本机高刷新率场景 | 2350 / 2350 | 1048 / 1060 |
| 等待期间新增 JS 动画帧请求 | 0 / 0 | 0 / 0 |

TaskDuration 是该独立文档的主线程任务时间，不是全应用 CPU、GPU 或耗电。捕获画面数不是显示 FPS、合成器呈现时间或操作系统输入延迟。结果说明最终等待流光能在此环境下随合成继续变化；不承诺所有平台和负载下恒定帧率。

**构造中的 SVG 描边和揭示仍有绘制成本。** 主线程完全被占用时，这些细节仍可能暂停；本轮没有声称整套构造已移出主线程。采用保留原构造、优化等待图层的范围，避免为了动画增加新的渲染架构。

## 未采用的候选

曾将构造的填充、遮罩和透明度全部改为原生时间线。它可以减少 JS 帧请求，但独立 GP ABBA 中首画布揭示约从 1597→1687ms，且部分 SVG 揭示仍依赖主线程绘制。因此该候选未保留，相关动态 mask 矩形、时间线及测试已移除；不能将其“零 JS 帧循环”的探针成绩当作最终方案。
