# Studio 加载、内存与渲染复核

基线为 0.8.1 源码 `dea1f05d1`。桌面启动对照使用 Electron 45.2.1 和相同的本机 0.8.0 renderer 资源，仅替换 Desktop 源码。其他项目分别通过 Node 24.20.0、Vitest 和 jsdom 验证。逐次读数见[原始数据](optimization-comparison.json)。

## 1. 恢复上次项目

旧流程完成会话恢复和项目预检后才发起 Studio 导航。新流程同时加载本地 Studio 文档和入口模块，并执行会话恢复及原项目预检。顶层 renderer 在预检完成后才能读取项目数据。预检决定返回 Dashboard 时，Desktop 销毁预备的项目文档。原生回归覆盖成功、403、404、禁止重复请求，以及确认项目不可用后再次启动的路径。

两份冻结业务项目使用同一套实际 renderer 资源、私有离线接口回放和 700 ms 项目响应延迟。每个项目按 ABBA 两轮顺序运行，每侧四个全新进程及 profile。计时从进程脚本开始记录，到原生导航事件或顶层 `studio-ready` 标记结束。每次启动各请求一次项目数据。表中为 p50，单位 ms。

| 业务模型 | 到项目导航，前 → 后 | 到 Studio 就绪，前 → 后 |
| --- | ---: | ---: |
| 1,420 个模型对象 | 898 → 173 | 3,161 → 2,362 |
| 10,746 个模型对象 | 916 → 173 | 3,170 → 2,351 |

另以真实 Electron、最小 HTML 和 400 ms 预检延迟隔离调度，每侧六次。项目文档请求 **567 → 147 ms**，模型 IPC 读回 **673 → 619 ms**。本地资源和模块准备越多，越能利用原有等待窗口。业务项目对照的固定延迟仅用于比较调度，实际收益取决于会话、接口和本机执行耗时。 [Desktop 启动](../../../desktop/src/main.cjs) · [原生回归](../../../desktop/tests/workspace-startup.cjs)

### 服务端启动上下文

当前项目响应仍汇总项目模型、依赖和应用上下文。鉴权身份和应用上下文原本各触发一次个人工作区初始化，每次都经过用户锁与数据库读取。两者现在等待同一次初始化。服务端回归确认，调用数 **2 → 1**，工作区与偏好读取都等初始化完成，匿名、分支和失败语义继续通过现有测试。该结果为调用计数，线上 DB 延迟与依赖模型迁移耗时仍需服务端阶段采样。 [启动上下文](../../../platform/wab/src/wab/server/routes/project-startup.ts) · [工作区回归](../../../platform/wab/src/wab/server/routes/project-startup-workspace.test.ts)

## 2. Desktop 组件库缓存

精确包版本的已发布代码和按 ID 寻址的不可变模型现在跨 renderer 构建复用磁盘缓存。服务端发布逻辑拒绝覆盖同一版本的已有代码制品。来源、账号、授权代次、资源身份和内容校验继续生效。启动诊断增加独立的资源缓存命中字段。新目录首次填充后可跨构建复用，已有构建目录随原配额淘汰流程清理。

用五个 512 KiB 依赖模型并行读，模拟 120 ms 远程响应。每侧两次独立运行，每次切换八个构建。首个构建负责填缓存，后七个构建各进入统计一次。两侧均读回完整字节。

| 指标 | 前 → 后 |
| --- | ---: |
| 后续构建每轮远程下载 | 35 → 0 |
| 后续构建每批读取 p50 | 145.4 → 4.3 ms |
| 八个构建后的缓存文件数 | 40 → 5 |
| 八个构建后的缓存体积 | 20.01 → 2.50 MiB |

实际网络收益取决于构建更新、资源复用和授权等待。文件写入后的配额扫描仍处于冷读路径，当前优先消除整批重复下载。 [磁盘缓存](../../../desktop/src/library-cache.cjs) · [版本和账号隔离回归](../../../desktop/tests/library-cache.test.cjs)

## 3. 增量保存的模型对象保留

`FastBundler` 在删除不可达序列化条目后，曾继续从地址索引强引用对应实例。现在移除该强引用，在撤销记录或其他持有方仍持有实例时继续支持按地址读取。重新挂回模型时恢复强索引。GC 后清理弱引用与 UID 记录。回归覆盖删除、部分服务端更新、按同一地址重挂、撤销与依赖管理。

同一 Node worker 按 ABBA 运行。每次循环插入 120 个节点并走增量序列化，再删除并序列化，连续 100 轮。只在内存诊断时调用 GC，实际操作计时排除这些调用。

| 指标 | 前 → 后 |
| --- | ---: |
| 最终序列化记录 | 3 → 3 |
| 强地址索引记录 | 12,003 → 3 |
| 诊断 GC 后仍能取回的已删除节点 | 12,000 → 0 |
| 诊断 GC 后堆增长 p50 | 5.04 → 1.57 MiB |
| 200 次增量序列化总耗时 p50 | 98.5 → 102.3 ms |

堆增长是整个测试进程的差值。新增弱引用管理在这组密集删除中增加约 3.8 ms，收益是回收同一会话内已经脱离模型和撤销记录的对象。Electron 业务项目长期驻留和其他保留链需要单独采样。 [删除路径](../../../platform/wab/src/wab/shared/bundler.ts) · [模型身份回归](../../../platform/wab/src/wab/shared/bundler.test.ts)

## 4. Antd6 Table 和通用重复渲染

原 Table 在普通设计画布渲染时枚举整个数据集及子行，即使受控展开键明确为空。现在只在编辑展开内容、或确实需要默认全部展开的行键时枚举。正常分页、编辑插槽、预览事件和控件原有展开规则由 Antd6 全套回归覆盖。

jsdom 夹具固定每页 10 行，每侧 20 次暖态列标题更新。资格函数调用包含原生 Antd 的可见行判断。

| 数据总量 | 访问的记录数 | 展开资格回调次数 | React 更新 p50 |
| ---: | ---: | ---: | ---: |
| 1,000 | 1,000 → 10 | 1,020 → 20 | 2.35 → 2.52 ms |
| 10,000 | 10,000 → 10 | 10,020 → 20 | 1.57 → 1.07 ms |

实质变化是常规编辑的工作量随当前页增长。简单谓词下，墙钟时间变化较小，1,000 行样本还略有增加。任意模板的通用重复渲染仍构建完整集合，现有局部探针记录 2,000 项约 30 ms。通用优化需要按真实的滚动容器、Grid/Flex 布局和 Slot 行为分场景验证。 [Table 实现](../../../plasmicpkgs/antd6/src/registerTable.tsx) · [既有通用重复测量](../2026-11-11/code-bottleneck-analysis.md)

## 5. 多画板总览与图形内存

每张画板仍以独立文档加载组件库、创建 React 树并维护画布索引。前一轮离屏创建候选的双场景结果可解释取舍：单画板视口工作集少约 107 MiB，十画板总览工作集多约 76 MiB，切到总览约多 366 ms。此次还运行 20 轮原生进出画布，旧 renderer 均退出，Dashboard 保留。继续收紧缓存只会影响一部分活动画板，且可能增加恢复等待。

更大的候选是低倍率总览的静态画板与编辑目标的交互画板分工。该方案需要先验证缩放过程中焦点、选区、缩略图更新和 MCP 定位一致。上轮本机约 518 MiB 的 GPU footprint 是进程级数据。独立确认总览、Preview、动态岛和缩略图对应的 IOSurface 前，无法量化静态总览会释放多少图形内存。本轮保留当前画板策略。 [离屏对照](../2026-11-09/project-open-optimizations.md) · [原生 renderer 回收回归](../../../desktop/tests/studio-window-native.cjs)

## 6. Dashboard 缩略图

六项队列和生命周期测试确认，Dashboard 隐藏后取消排队，只允许已经运行的一项完成。退出窗口、导航或账号失效会回收正在运行的任务。冷缓存仍需要客户端 codegen、逐画板渲染和栅格化。把已运行任务一律取消会让返回列表时重新生成，收益取决于点击时任务进度和跨端复用率。可复用的修订预览产物还需确定生成时机、访问控制和依赖变化的失效规则。本轮没有改动队列与渲染策略。 [缩略图契约](../../../platform/wab/src/wab/client/components/dashboard/preview/README.md) · [队列测试](../../../desktop/tests/dashboard-preview.test.cjs)

## 验证记录

- WAB 定向 7 个文件、58 项通过。另复跑 Bundler 回归和诊断探针，4 项通过。WAB 类型检查通过。
- Antd6 全量 32 个文件、331 项通过。第一次并行运行有 AppShell 和 RangePicker 两个超时，用两个 worker 重跑全部通过。
- Desktop 定向 Node 测试 73 项通过。原生授权、403、404、资源缓存、启动日志和 20 次 renderer 回收通过。
- 拒绝访问的原生复测曾捕获一次销毁中的 renderer 收到空数据后又发请求。改为结束该 IPC 后连续复测授权、403 和 404 各三轮，未出现重复请求。
- 原生业务项目对照使用冻结的 0.8.0 renderer，验证的是 Desktop 改动。服务端、Bundler 与 Table 另用当前源码测试。线上服务部署、发布后真实升级及用户环境耗时仍需验收。
