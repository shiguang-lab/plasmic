# 项目启动 GET 耗时调查

调查对象：Studio 0.5.31，提交 `f7bf66b40620d0f9dadcbee356ddbc6721d4ddbc`；「客服平台 · GP评论查询」，修订 158。结果见 [JSON](project-startup-get-investigation.json)。本次未修改正式业务代码或部署配置。

## 结论

值得优先评估资源引用生成时的重复 JSON 处理，并修正权限检查去重键的默认参数。个人工作区检查虽然重复，单独合并没有测出稳定的请求耗时收益，不作为独立提速重点。这些工作针对服务端开销，不能承诺画布因此秒开。

## 测量范围

- 正常登录账号通过公开 Studio 地址发起 7 次真实项目 GET，包含 `includeStartup=true`。首个请求单独记录，后 6 次完整响应中位数 **680.4ms**，范围 **635.9–1018.4ms**；逻辑 JSON 正文 **335,435 B**，不代表压缩传输量。
- 使用正式 Server 镜像和线上数据的一次性数据库副本，逐步记录现有路由、事务、SQL、目录查询和 JSON 处理。基本打点批次预热后 7 次中位数 **287.2ms**，范围 **270.4–313.4ms**。
- 副本诊断不含常规 HTTP JWT 验证、公网链路、Nginx/gzip 和画布渲染；不能用两组中位数之差直接认定纯网络耗时。方法耗时存在重叠，不能相加。
- 参数、模型内容仅用于指纹判重，不写入报告。后续对照增加了指纹开销，与基本打点批次分别统计。对照按成对交替顺序运行，剔除首对预热，每种模式 10 个样本。
- 每个副本请求执行 **94 条数据库命令**，包括事务起止；不是 94 条独立业务查询。项目数/修订数在实验前后均为 **89 / 3444**。

## 1. 库模型被重复解析、再序列化

[BundleMigrator.getMigratedBundle](../../../platform/wab/src/wab/server/db/BundleMigrator.ts) 为迁移和升级检查解析库模型；随后 [dependencyModelResources](../../../platform/wab/src/wab/server/routes/dependency-model-resources.ts) 调用实体 `toJSON()`，再次解析同一模型，再序列化、计算摘要、生成资源引用。

[实体 Base.toJSON](../../../platform/wab/src/wab/server/entities/Entities.ts) 的 `normalizeJson()` 会对 `model` 字段执行 `JSON.parse`。SQL/内容指纹证实当前图标、Antd6、模板等同一份模型在这两个阶段各解析一次。基本打点批次每次约 18 次 JSON 解析、累计处理约 944 万字符，解析中位数约 **60.4ms**，序列化约 **20.3ms**；这些数字包含所需处理，不能全部视为可省时间。

5 个库的原始模型合计 **4,616,187 B**。对这 5 份实际模型做局部 CPU 对照：

| 资源正文和元数据准备方式 | 中位数 | 范围 |
| --- | ---: | ---: |
| 当前：实体转 JSON、模型序列化、计算摘要 | 50.94ms | 48.56–70.76ms |
| 候选：复用已有 JSON 正文、仅规范化元数据、计算摘要 | 5.62ms | 5.36–9.03ms |

此语料下，模型正文摘要、元数据摘要全部一致。约 **45ms** 是局部 CPU 实验差值，不是完整项目请求或画布打开的实测提速。正式实现仍需覆盖各模型读取入口和迁移后的资源身份，保留当前鉴权、自动升级及不可变资源规则。

建议仅优化资源引用生成阶段，避免为一个本来已有 JSON 正文的库重复构造模型对象；不增加客户端库存摘要，不合并或新增接口，也不缓存可变项目、权限或 latest 结果。

## 2. 权限检查去重键把同一默认条件分成了两份

[DbMgr.checkProjectPerms](../../../platform/wab/src/wab/server/db/DbMgr.ts) 的执行函数声明 `includeDeleted=false`，但 memoize 的键生成函数没有同样的默认值。因此省略第五参数与明确传 `false`，业务含义相同，却分别生成包含 `null` 和 `false` 的键。

实际调用链包含：

1. 项目读取通过 `getProjectById()` 传入明确的 `false`。
2. 修订读取经 `checkProjectBranchPerms()` 省略该参数，造成去重失效。
3. 权限集合读取还走资源批量检查。SQL 和参数指纹确认，同一目标项目的部分元信息、工作区、团队及权限查询重复了 3 次；不同组件库的必要查询已单独区分。

仅在副本诊断中，将省略参数规范为 `false` 后调用原有权限检查：数据库命令由 **94 → 89**，完整响应字节摘要保持一致。对照中位数 **326.4 → 309.5ms**，范围分别为 **270.6–348.5ms / 260.0–329.6ms**，存在重叠，不作固定延迟收益承诺。

这是现有去重键的修正候选，不需要跳过权限检查或引入跨请求权限缓存。正式实现应验证不同项目、权限级别、`includeDeleted=true` 的隔离。

## 3. 个人工作区确有重复，但单独合并不见明显收益

[getSelfInfo](../../../platform/wab/src/wab/server/auth/routes.ts) 和 [getAppCtxData](../../../platform/wab/src/wab/server/routes/appctx.ts) 均调用 `ensurePersonalWorkspace()`。同一启动事务中发生两次 advisory lock、个人团队存在性查询及邀请查询。

副本中仅共享这项检查的进行中任务，命令数 **94 → 91**，返回字节摘要一致；请求中位数 **312.4 → 313.1ms**，没有测出稳定改善。它发生在并行启动分支，减少命令不必然缩短关键路径。不建议为了提速单独推进这一项。

## 其他观察与边界

- 每次请求有 7 次相同的 hostless 版本标记读取，以及 7 组事务起止，其中包含项目读取事务及各模型的迁移/自动升级检查。它们参与保证库版本新鲜，不能直接删除。是否按同一次请求共享需另行验证发布并发和升级一致性，本次不列为直接修改项。
- 暖请求的依赖读取/检查仍占一部分服务端处理，即使客户端库资源已缓存，服务器也仍会检查版本并准备资源引用。这里的优化与客户端缓存生效并不冲突。
- 首个公开请求为 1.81 秒，未控制服务端、操作系统及链路缓存，不作为完整 App 冷启动成绩。
- 本次只形成调查结果。源码中的默认参数和模型资源生成方式均未修改；副本内候选实验不代表已经实施或发布。
