# 画布列表打开：五项候选独立验证

最终只保留组件库读取去重。模型传输虽提速，但连续快速重开的峰值内存回退重复出现，已从产品源码撤回；其余三项未显示稳定的整体收益，未写入产品源码。当前源码已完成相关单元测试和完整类型检查，最终原生验收及内存结果见下表和 [指标 JSON](canvas-open-candidates.json)。没有替换正常使用的已安装 App。

## 方法与结果边界

使用真实 GP 保存修订 158，以及 Admin Templates 3.0.0 发布 Site。复杂样本包含 4,644 个主模型对象、13 个组件、22 个画板，本次打开的总览组有 10 个画板；发布包只去除外层 ProjectDependency，Site 保持原样，诊断响应修订 0 不是线上修订 113。GP 连同依赖共 22,883 个模型对象。这些不是 demo。

原生 Electron 从真实列表卡片的点击处理器进入编辑器，返回列表后重开，使用实际 Desktop 文件缓存和摘要校验。所有 HTTP/WebSocket 在隔离 profile 中由 fixture 接管，保存仅在测试进程中确认。**不包含线上接口、认证恢复、原生草稿桥及业务网络的耗时，不是线上端到端成绩。** `reveal` 和 `rendered` 是内部标记，不等于物理屏幕呈现或精确可操作时刻。

基线与各候选均从同一冻结的当前工作源码构建；每次只覆盖一个候选，使用匹配且未变更的安装版 canvas runtime。每个计时进程打开六次，前两次预热，后四次统计；计时、功能、内存、输入代理分别串行执行，未同时构建或开启 CPU profiler。另构建两项组合版本验收；发现传输方案的内存回退后撤回传输，再单独验收最终只含去重的版本。此基线与之前安装版 renderer 不同，不能把旧报告中 1.574 秒到组合候选 1.028 秒的差值归给最终交付。

## 独立候选的处置

单位毫秒，表中为复杂样本两轮四次暖打开的中位数。前后基线控制的首画板中位数约 1,117–1,148，全部画板约 3,299–3,322；小幅波动不能当作确定收益。

修正边界后的独立去重构建另跑一次：首画板 1,168、全部画板 3,347，资源读数仍一致。所有独立候选均在 GP、复杂 Site 上完成原生功能验收；被拒绝的原型仅留在私有诊断目录。

**已撤回模型传输原型。** 原来已从缓存读取并解析过的依赖模型对象，通过 Comlink 再做整图交接。原型只在已标记的 getSiteInfo 回应中，用该响应已有的不可变 JSON 正文传输依赖模型，在接收端解析；外部 API 仍返回原来的 Bundle 结构，主模型字符串和其它元数据保留原有传输。弱引用按已授权的响应对象关联正文，所有正常资源请求、账号隔离和摘要校验仍执行；没有新增按资源 ID 复用的跨账号缓存。

独立试过整份响应 JSON 字符串、UTF-8 ArrayBuffer、复用依赖资源原有正文三种实现。它们均通过原生功能验收，但快速重开时的自然 GC 峰值较高；缩小序列化范围仍未消除回退。诊断 GC 后占用接近基线，说明当前证据涉及分配/回收时机与工作集压力，不能据此证明永久泄漏，也不能因此忽略实际峰值。三种实现全部撤回。没有引入产品强制 GC 或为了成绩放慢正常重开。

**组件库去重的具体实现与修正。** 只跳过同一 Document 已安装的精确版本，仍保持各画板独立注册及注册表刷新。初版专项测试发现两处实现边界：库作者编辑自己的库时仍需刷新发布版本；异步等待期间 Site 版本变化不能丢失已安装记录。现已保留作者刷新，并在等待前记录本次所需标识，补充版本切换、失败重试和等待期间版本变化的回归测试。修正后的八个专项测试全部通过。这属于原型实现问题，资源去重本身可以在现有功能约束下成立。

## 功能与内存验收

每个独立候选分别在两个真实模型上验证：切换首/中/末画板；正常重命名及撤销/重做；修改样式并核对实际 DOM computed style；画板位置编辑及撤销/重做；撤销后完整模型与原始模型一致；完整客户端保存、重新加载后模型和修订完全一致。复杂样本额外访问七个已有组件画板，使旧 ViewCtx 销毁，再验证撤销、选择与实际样式恢复；GP 进入真实 Preview，切换表格第二页，确认数据变化后返回。

组合候选再次通过上述两个模型的全部场景，renderer error 为空。最终只含去重的版本另行复验。保存只验证真实客户端路径及离线确认，不冒充线上数据库保存或发布验收。Dashboard 原生缩略图 prepare 在基线和候选均存在 unresolved modelResourceId 导致的 `undefined.map` 错误；未掩盖该错误，未将缩略图生成功能宣称为通过。该已知基线问题未归因于本次修改。

每个内存进程自然连续打开六次，最后返回列表后才执行诊断 GC。单位 MiB；工作集为所有 Electron 进程 RSS/working set 之和，包含共享页重复计数，**不是系统实际物理内存**；堆指标来自主 WebContents 的 V8 isolate。

所有构建的自然 GC 峰值波动都较大。传输方案两轮的峰值和回收后工作集均高于前两轮基线；后续更高的基线也说明不能把全部峰值差额归因于它。当前证据不足以证明永久泄漏，也不足以把提速方案的内存压力验收为无回退，故保守撤回。需要更稳定的分配/回收归因后再考虑。

最终去重的两轮回收后占用与各自相邻基线接近或更低，未见持续占用增长；其自然峰值仍分别高约 611 / 276 MiB，低于基线轮次之间约 1,079 MiB 的波动量，不能宣称峰值内存不变或下降。本次保留依据是实际少读 2.11 MiB 正文、完整功能验收及无持续堆增长，**不报告内存节省**。

idle 候选另测八次 Layers 控件事件及两次 rAF 的往返时间：基线中位数 46.8ms、最大 167.0ms，候选中位数 39.8ms、最大 210.1ms。该指标不是操作系统输入延迟，也不能用这一小批数据证明响应收益。deadline 无法抢占主线程已有的长任务，因此未因一次中位数下降保留该方案。

最终实际工作目录运行八个相关测试文件，共 **47 个测试通过**；`tsc --noEmit --incremental false` 完整检查通过。四个撤回候选的专项测试共九个通过。保留版本测试覆盖资源命中及错误分类、精确版本去重、库作者刷新、重试、版本变化、画板生命周期、冷撤销与保存状态；撤回原型的四个传输测试还验证了真实 MessageChannel 往返。使用生产构建配置的隔离 Studio 构建通过。

## 为什么仍然约一秒

已撤回的组合候选中，复杂样本的一个实际暖打开（第四次打开，非拼接中位数）：从点击到 Host 中 Studio 模块开始约 294ms，模块导入约 105ms；模型交接等待约 16ms，unbundle 65ms；首画板约 673ms 开始加载，Host 文档约 102ms，runtime 与组件包约 64ms，首次渲染约 137ms；1.019s 才记录 reveal，十画板在 3.204s 全部 rendered。上下文、路由与调度还有部分重叠，不能把所有阶段简单相加。

磁盘缓存不会保存每个新 Document 的已运行 JS、编辑器对象图和已渲染 DOM。传输原型虽减少模型交接等待，但内存门槛未通过；最终只减少重复字节读取，等待仍主要是 Host 启动、模块执行、对象图重建及各画板注册/渲染。其余候选未通过收益/资源回退门槛，因此没有为了接近“秒开”而改变画板隔离、减少业务渲染或保留一整套隐藏编辑器。

复测入口及环境开关见 [诊断说明](../../../desktop/tests/performance/README.md)。原始项目、profile、完整日志和未保留的原型仅保存在私有临时目录；仓库只保留可复用诊断入口与脱敏指标。
