# Forms

## Forms and state

Use real labeled inputs, Selects, Buttons and feedback. Modals/Drawers keep the full source page behind them, close unrelated menus, and retain a reachable footer. Keep destructive or unauthorized actions gated according to the source. Loading, failure, success and recovery states belong to the actual flow; do not manufacture generic state boards or placeholder future features.

Editable business forms use the registered Antd6 Form with real Form Field/Form.Item instances and their label/children Slots. Give each field its actual name and validation rules through the installed contract; let Form own required indicators, punctuation, error state, error messages and field values. A literal `*` in label text or a separate red error div is not required-field validation. Derive initial values at Form/Item level without competing control value bindings. Use required and whitespace rules for required text when blank-only values are invalid; choose other rules from the requirement. Submit through the supported Form action/validated event or await its registered validateFields action before a mutation. Rejected validation keeps the Modal open, identifies the field, and performs no mutation.

Field-label explanations belong in the real Form.Item `tooltip` prop/Slot. Keep the label plain and let Form.Item place its native help icon beside the label; do not build a separate Tooltip/button beside the control or type an `i`/question mark as an icon. Advanced Form Fields expose editable tooltip content; simplified Form fields expose tooltip text in their field configuration. Read the installed contract first. If tooltip is absent, update the registration and published library before using it, rather than inventing a substitute prop.

### Field instruction placement

Decide instruction placement before choosing a Slot. These are field-specific instructions, not the form’s horizontal/vertical layout. Use the requirement, actual control width, expected text length and measured space at the target viewport; do not automatically place every instruction below the input or rely on a fixed character-count threshold.

| Condition | Placement and component contract |
| --- | --- |
| Short, supplementary instruction next to a compact control, with enough width for the complete control, 12px gap and complete instruction | Place after the control in the same row; vertically align with the control. Use registered Typography.Text with `type=secondary` inside that field’s content region. |
| Long, multi-line, important explanatory text; narrow/multi-column area; a full-width control; or inline text would crowd, truncate or wrap awkwardly | Place below using the Form Item `description` Slot/text configuration, which maps to native `extra`. Align its left edge with the control column. |
| Optional label definition/background that is unnecessary while entering the value | Use the real Item `tooltip`. Keep essential format/range information visible. |
| Validation failure | Keep the native error below the control, independent of the instruction position; show one actionable error at a time. |

Ant Design Form.Item `extra` has no native placement switch; do not invent an `extraPosition` prop or move its internal DOM with absolute positioning, transforms or selectors. For inline instructions, use supported component composition. The installed Antd6 Form Field wrapper forwards value/events to its first direct control; for a simple compact field, retain that control as the first child and add one secondary Typography.Text sibling after it in the same `children` Slot. Use native Form `styles.content={display:"flex",alignItems:"center",gap:12}` when all fields in that Form support this composition; it styles the control content region, so errors and below-control extra retain their native layout. This prop is form-wide: inspect every field, and do not apply it to unrelated full-width or stacked fields. If a Flex/Space wrapper is necessary, use the native outer labeled Item and nested `noStyle` named Item pattern: only the inner Item owns the field name/rules/value, the control is its direct child, and the outer Item owns label/required/error layout. Read and verify that exact installed contract. Never place a Flex between a named Item and its bound control without an appropriate nested Item. Native React code generation must use Ant Design’s [complex form control](https://ant.design/components/form/#components-form-demo-complex-form-control) pattern rather than assuming the Plasmic wrapper’s forwarding behavior is an Ant Design default.

Below-control instructions use the wrapper’s `description` (editable Slot in advanced mode, text in simplified mode). Native extra starts below the control/error area and uses the theme’s secondary text color/font/spacing. Inline instructions use the same secondary hierarchy, a 12px control-to-text gap and complete readable text. Keep exactly one instruction at the chosen location; remove obsolete standalone siblings and bottom extra when moving to inline. Do not use `help` for persistent instructions because it replaces native errors. Do not move instruction text into the input’s suffix: suffix belongs inside the control. When available width no longer accommodates the full instruction, choose below rather than shrinking the control, clipping text or forcing nowrap.

Record `description`, `descriptionPlacement` (`below` by default or `afterControl`) and, for inline text, `descriptionNode` in the independent field inventory. These are acceptance expectations, not new component props. Read back native ownership and secondary Typography, then verify actual normal, empty, invalid and corrected states: one error below the control, persistent instructions at the approved location, no duplicate text, no crowding/overlap, and no vertical shift of inline text when an error appears. Recheck after save/reopen. A correct Slot or screenshot of the initial value alone does not pass this acceptance.

Show one actionable validation error per field at a time. Use native `validateFirst=true`, with required/blank checks first, format/type/range checks next and business/remote checks last. The Antd6 Form Field wrapper defaults to this ordered short-circuit behavior and exposes the actual prop; Ant Design itself defaults to collecting errors. Do not hide the second error with CSS or slice displayed messages after all rules run. Inventory the expected `validateFirst`, instruction text and placement, verify saved props/Slots, then test an empty value, a nonempty invalid value and a corrected value: exactly one native field error in each invalid state, persistent instructions remain visible, and correction removes the error.

Set Form `layout` explicitly from the task and available space. A compact field on a wide PC page can use horizontal label/control alignment with a content-sized label area; dense data entry, long labels or narrow/multi-column regions may use vertical layout. Neither direction is a universal Ant Design requirement. Preserve a layout explicitly chosen by the user. Align native description/errors with the control and verify label, control and instructions together; do not inherit large label spans from a generic form template without checking actual geometry.

For a single horizontal field, prefer native content-sized label columns (`labelCol.flex="none"`, `wrapperCol.flex="1"` in the installed contract). Do not reserve a fixed label width for an absent Tooltip or a template's longer fields. Multiple stacked fields may share a label width to align their controls; choose that width from their actual longest label, required indicator, punctuation and configured Tooltip. Left-aligned fixed-width labels leave unused space after the colon, so verify the rendered colon-to-control distance instead of accepting the column width alone. Preserve native label punctuation/spacing; do not compensate with empty nodes, negative margins or internal component CSS overrides. Measure normal, required, configured/empty Tooltip and validation-error states after save/reopen.

For full-project generation or a form inventory audit, inventory every project Page, business Form and field across inactive Tabs and Modals before editing. Pages without business Forms still declare `forms: []`. Record field keys, labels, required/whitespace/business rules and tooltip content independently of the generated output. Run `python3 scripts/verify_forms.py <expectations.json> <mcp-read.json> --overview <mcp-overview.json>` against full public MCP readbacks and again after save/reopen. The overview must cover the entire project. This mandatory gate rejects missing/extra Pages, Forms or fields, unowned editable controls, competing values, label stars, separate field-help Tooltip/buttons/icons, manually bound field-error blocks and advanced validators stored as literal strings. Declare genuinely standalone controls, such as a separately validated SQL editor, in each Page's `standaloneControls: [{nodeName: "SQLEditor", reason: "Separate SQL validation workflow"}]`; entries must be named, unique, used and outside business Forms. SearchForm Items retain their own control ownership. The static scan checks model patterns and contracts; runtime validation still requires preview acceptance. Move existing controls into real Item children Slots to preserve their UUIDs and applicable interactions. For a field with adjacent actions, keep the actual control as the Item's direct first child; use a nested noStyle Item when a layout wrapper is required. Replace manual error state and value-based submission handlers with Form values and validation, update affected references, then remove obsolete wrappers, label stars and tooltip buttons.

For a Modal with one routine confirmation action plus cancel, keep the component's default footer and locale-owned button text. Omit okText/cancelText and custom footer children; do not recreate the two default buttons just to attach events, loading or disabled state. Bind onOk/onCancel and use the real confirmLoading/okButtonProps/cancelButtonProps contracts for submission state. A source-required specific action/risk label may override supported button text while retaining the native footer. A custom footer is appropriate when the required workflow has multiple distinct operation actions (for example draft/save/publish). Follow [buttons and action bars](../design/actions.md#buttons-and-action-bars) for their order, types and availability. An explicit user requirement overrides this default. Remove obsolete custom buttons, label stars, manual field-error nodes/state and their handlers when replacing them.

An empty footer Slot is still an explicit override and can hide the native footer in preview. Restore defaults through changeElement resetProps after deleting custom footer children; do not insert an empty footer Slot or use footer=null for a default-footer Modal. Reset obsolete okText/cancelText/hideFooter overrides too. Empty-slot cleanup must distinguish removal of unused example content from restoration of a component default. Check actual runtime buttons after that cleanup. When editing node names, recheck registered Form ref actions in submit/cancel handlers so renamed forms remain callable.

Spacing between adjacent components has one owner. When the last Form.Item already supplies its theme margin-bottom, a following Alert/help block must not add another margin-top or parent row-gap on the same boundary. Preserve native Form.Item spacing and set the extra wrapper gap/margin to zero for that composition. If a different composition intentionally transfers spacing to the parent, remove the matching child margin instead of stacking both. Verify the rendered control/error-to-next-block distance in normal and validation-error states; checking Alert's margin alone misses parent gap and Form.Item margin.

Form/Modal acceptance records model and runtime checks separately: verify the delivered Form/Item ownership, field names/rules and plain labels; verify a default footer has no custom button/text overrides. In real preview, empty and blank-only required inputs must show native field errors without closing or creating a record. Correcting the value must permit one submission; during processing check loading, control/button disabling and duplicate-submit prevention, then verify success and cancellation/reopening reset behavior according to the requirement. When the Modal footer is outside Form, do not assume browser implicit Enter submission works: verify the supported input Enter event reaches the same Form validation and duplicate-submit guard as onOk, preventing the default event if needed. Inspect required indicators, label-to-control spacing and reachable default footer in editor and preview, and recheck persisted structure after save/reopen. A visible asterisk, working success path or valid model alone does not pass form acceptance.

For each field tooltip, verify the native icon is in the label, hover opens the expected content, the control remains usable, and clearing tooltip removes the icon. Recheck editor, actual preview and saved readback. Do not force persisted open state for inspection. Verify required indicators and tooltip coexist without duplicate marks or a second label model.

Verify dynamic initial values and custom rules execute in preview: a nested `{{ ... }}` binding inside `initialValues` or `rules` must be a native expression, not literal text. For a uniqueness rule, test both an existing key and a distinct key; for a numeric range, test valid integers, decimals and out-of-range values. When a footer submits through a Form ref, test a form remount or reopening with another record so stale refs cannot silently bypass validation or submission.

### Modal form layout

Choose Modal width and Form columns together from the field inventory. Do not make every Modal multi-column. A short, simple form usually starts at 480–560px with one column. A 640–800px Modal can use two columns when its actual body width, padding and column gap leave roughly 240px or more of usable width per field and the longest labels/values fit. These are starting points, not component defaults or a substitute for preview inspection. Do not use three or more columns in an ordinary confirmation Modal without an explicit dense-entry requirement.

| Field content | Default allocation |
| --- | --- |
| Long business names, generated/editable Keys, URLs or addresses | Full row |
| Textarea, code/rich-text editors, upload lists and complex nested fields | Full row |
| Short enums such as type/status/scenario, short numbers, single date/time | Half row when the label, control, help and error all fit |
| Person/entity Select, multi-select, date range | Decide from the longest expected content; use a full row when a half row would truncate or crowd it |
| Switch/Checkbox and fixed read-only metadata | Compact related group or information row; avoid a large empty control area |

Input component type alone does not determine column span. Pair related short fields; make an unpaired final field span the row or choose a narrower single-column Modal. Do not leave an unexplained empty half-row beside an editable field. A full-row Key with an adjacent regeneration action must reserve action space without wrapping or overlapping it.

The Form and every intermediate field-layout wrapper must fill the Modal body width through explicit width:100% or verified stretch alignment, with min-width:0 on grid/flex children. In particular, a full-width Form with align-items:flex-start does not make an un-sized child wrapper full width. Use equal columns, a 16px column gap and explicit full-row spans. Prefer a full-width Antd6 Flex column and Row/Col for mixed full-row and paired fields, using the real registered gutter/span contracts and full-row allocation for long fields. Verify actual component geometry rather than assuming native CSS grid properties apply to Row/Col. Controls fill their allocated cells. Preserve native Form.Item vertical spacing; do not add parent row-gap on top of it. Keep each real control directly in its Item children Slot even when the Items are arranged in a grid.

For Antd6 Row/Col layouts, verify real gutter/span props and rendered column widths, full-row fields and ownership; the optional CSS-grid row check below does not validate Row/Col props. Form field/validation checks still apply to every layout.

For authored CSS-grid rows, record optional Form layout expectations as `layout: {container: "NewGroupFields", modalWidth: 640, columns: 2, columnGap: 16, rows: [{container: "NewTypeScenarioRow", fields: ["NewTypeField", "NewScenarioField"]}]}` and each field's `span` (1 or 2) in the independent field inventory. `verify_forms.py` checks the Modal width, the vertical container and paired rows fill the Form width, the paired row columns/gap, its complete field group and full-row/half-row placement against the saved model; a mismatch must fail the generation check. Run it before delivery and after save/reopen. This structural check does not measure rendered geometry. In actual preview inspect every affected Modal at the target viewport: controls reach their intended column edges, the longest realistic labels/values and adjacent actions fit, validation errors expand without overlap, and the native footer stays reachable. Capture the opened Modal, not just the background page or hidden editor node. Update the generation source and delivered model together when fixing a layout failure.


## Focused form edits

For a local field/validation/layout change, inspect the entire affected owning Form and relevant hidden branches against the current requirement, preserving unrelated Pages. Check control ownership, values/rules, submit/ref actions and actual error/save/reopen behavior. Run the full-project verifier only with a complete reviewed inventory and overview; do not trim the overview or claim a full-project pass from a partial check. Full regeneration continues to require the complete inventory gate above.
