# Plasmic 页面到项目代码

用户明确要求官方 CLI sync/watch/export/codegen 或元数据时，使用已解析资源中的 [official CLI](../official-cli.md) 分支；无需执行本页的原生实现、Desktop 读取和工程验收步骤，除非任务另外包含这些工作。

本页用于 Plasmic 设计对应应用代码的原生生成、修改、修复及一致性验收；只读审查执行相关读取和验证，不修改产物。遵循目标工程规范，不调用 `export_code` 或引入同步配置、托管渲染。

## 必读规范

`context resolve --mode codegen` 返回必读规范；数据/交互规则按需读取。

- [页面读取与实现依据](../model-reading.md)：读取真实模型与当前实现，确认目标 API。
- [项目代码规范](../codegen/project-code.md)：组件契约与复用、目录职责、类型、样式、宿主集成。
- 涉及数据或提交时，先读[Service 与模拟数据](../codegen/services.md)；查询、表单、弹层或权限另读[交互规范](../codegen/interactions.md)。静态布局不添加这些能力。
- [代码验收规范](../codegen/acceptance.md)：设计到代码的一致性、行为、视觉、构建与交付证据。

## 1. 确认页面和目标项目

读取需求、仓库规则、依赖与锁文件、入口、路由、Provider、公共组件、请求和权限封装。区分现有应用与独立项目的菜单/登录/顶栏责任；沿用实际依赖和命令，不机械复制原型外壳。

若用户明确要求新建独立项目且未指定技术栈，默认 React + TypeScript + Ant Design 6 + Vite，使用当前可安装且互相兼容的稳定版本并提交锁文件。普通页面生成不升级现有工程的组件库。不预建微前端、权限平台、请求框架或通用页面引擎。

## 2. 读取真实设计

通过 Desktop MCP 定位指定项目，读取 `get_app_state` 和操作 schema，执行 `identify`、`read`。按[页面读取规范](../model-reading.md)取得完整模型与依赖契约。记录项目/页面 UUID、路由、可用 revision 和资源 releaseId；缺 revision 明确标记。

模型与组件契约定义结构和行为，截图和布局核对视觉。从页面根与引用组件盘点范围内的页签和业务区块，包含非活动页签、隐藏分支及关闭的弹层。将盘点结果带入第 3 步的原型清单。只读时保持原型初值和保存状态。涉及原型修改，先按 prototype 工作流完成、保存并验证，再读最终设计。

在冻结实现契约前，通过 [`readComments`](../desktop-mcp.md#comments) 读取当前项目/分支中目标页面和相关本地组件定义的未解决注释。指定线程按 `threadId` 读取；已解决线程在用户指定或需要追溯决策时读取。按 `nextOffset` 读完相关范围，用节点 UUID 和 variant 对齐到页面区域与状态。页面过滤不会包含引用组件定义上的注释。操作不可用或读取失败时，说明注释覆盖缺口，继续不依赖该资料的工作。

## 3. 核对原型清单并建立实现契约

在任务说明中确定需求与设计版本、实现及验收范围。来源冲突说明采用依据；影响业务语义且无法裁定时澄清，继续独立工作。记录组件/文件、API、行为、反馈责任与模拟边界。

写代码前，将原型清单记入现有任务说明。逐项对照源模型及适用的预览证据，确认每个范围内的页签及其业务区块。没有页签的页面直接列业务区块。每项记录页面与页签路径、区块、原型定位（节点 UUID 或其他可定位证据）、组件职责和影响验收的关键结构（如内容归属与顺序、表格行列、操作位置），以及适用的进入条件、状态和预期结果。原型不可达、结果截断或关键结构未确认时，在对应项标明缺口，补读后再实现依赖该信息的部分。可继续实现已核实且独立的区块。

将相关注释中已确认的业务规则、接口约束、交互状态或验收条件纳入实现契约，记录线程 ID、目标和采用结论。未决讨论不能直接变成需求，线程已解决也不能证明目标代码已实现。把采用的内容落实到实际逻辑和验收用例；无需把讨论转成界面文案或源码注释。生成、修复或验收代码本身不授权在 Studio 发帖、回复或变更线程状态。

把演示注释当作可复现的场景。例如，同一查询入口用两个测试账号触发「正常」和「已锁定」时，保留“查询结果的状态决定页面呈现”这一规则；账号只是测试数据。用目标工程现有的 mock 或测试数据复现两条路径，禁止把演示账号写进生产分支判断。若测试数据或入口不同，在验收说明中给出目标工程可运行的对应步骤。

按[组件库索引](../libraries/index.md)及[组件契约与复用](../codegen/project-code.md#组件契约与复用)核对两端真实 API。业务接口先发现资料，再依 Service 规范确认缺口或推导临时契约；未知组件 API 不自行推导。

原型清单以业务区块为粒度。涉及非直接转换的项补记契约依据、理由和未解决差异。

同时按[逐场景截图验收](../codegen/visual-acceptance.md)建立对应的变体、隐藏/条件状态和面板清单，核对来源补充场景，确定两端可复现的视口、数据、权限及入口。使用完整设计采集生成待填截图记录，保留模型自动发现的场景；缺少必要环境或 fixture 时标记未验证。

## 已有代码的局部更新

局部更新按受影响的页面/子树、状态、查询及组件依赖核对和更新原型清单，核对实现与需求差异。只改职责所属文件，保留无关逻辑和接入方式，不重生成整页或按设计节点重组工程。源设计变化后重读受影响输入并更新对应项；验收覆盖改动及共享消费者，无需重跑无关页面。

## 4. 生成并接入真实项目

按规范实现类型、必要 service、页面/私有组件、样式与词条，并接入真实路由。将原型声明式状态和交互翻译成类型化 React 状态、Form 与事件处理函数；写 JSX 和实际业务逻辑，不把 Studio 模型 JSON、表达式解释器或注册元数据作为产品运行依赖。

逐项按原型清单实现。每完成一项，回填实际渲染位置和对应文件，按[一致性核对](../codegen/acceptance.md#设计到代码的一致性)检查关键结构与适用行为、视觉。数据流程同时实现 service 和模拟，沿用已有网络 mock，否则提供本地模拟；按 Service 规范验证闭环并区分真实联调。

## 5. 执行验证

按[代码验收规范](../codegen/acceptance.md)完成工程检查、真实入口行为与视觉验收，记录证据及限制。

逐场景进入设计和实际应用并截图对比，保留差异、修正和新截图复验记录。运行 `verify_codegen_visual.py check` 校验完整场景和两端证据、当前设计及代码版本；失败或未执行时不得声明视觉验收通过。实现后设计审查再核实来源覆盖和截图判断。

## 6. 实现后审查与交付

按[实现后审查](../codegen/review.md)为适用方向分别委派独立 subagent；不可委派时当前会话逐方向审查。主 Agent 汇总核实并修复，交回受影响方向复核；按验收规范报告各方向、证据与未解决项。生成不自动发布或部署。
