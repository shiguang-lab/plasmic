# Admin design rules

Adapted from pen-antd-kit standards manifest 11.0.1: foundations/environment-layout, patterns/admin-app-shell, list-query, tabs, table-data, table-columns, forms-overlays, and quality/review-checklist. These are design conventions, not Pen APIs or component identifiers.

## Templates and layout components

Before composing admin pages, read [admin templates](admin-templates.md) and the [bundled catalog](templates/admin/catalog.json). Select page, section and overlay compositions by the requirement; inspect their live models through Desktop MCP. Record the selection or the unmet scenario in the task plan. Templates supply design structure; current requirements define business fields, data, actions and routes.

Reuse registered components. Prefer Antd6 Flex for directional layout, Row/Col for column grids, Space for inline actions and Card for business surfaces. Read their real Props and Slots before insertion; use AppShell for the shell and SearchForm for filters. Native semantic nodes remain appropriate for headings/text and necessary semantic grouping. Do not recreate existing controls, shells, filter grids or layout components.

## Editor node naming

Use English PascalCase (UpperCamelCase) for editable node names, independent of the business UI language: `AppShell`, `PageBody`, `StatusFilter`, `ExportModal`. Preserve established component/acronym spelling such as `AppShell`, `SQL` and `ID`. Do not use lowerCamelCase, Chinese names, hyphens, underscores, library prefixes or temporary identifiers for instance names.

Choose names in this order:

- For a page-level structural component that has one instance in its owning page/component, prefer its actual registered display name: `AppShell`, `SearchForm`, `Tabs`, `Steps`, `Form`. In particular, every standalone page's single shell is `AppShell`, not `OverseasAppShell` or a page/product-prefixed variation. Count authored instances in the owning tree, including inactive Tabs and overlays; do not infer uniqueness from the current visible screen. A component appearing once is not by itself a reason to erase a useful business action or field name.
- For business controls and content regions, use their verified action, field or content role: `CreateGroup`, `StatusFilter`, `DetailSummary`, `ListToolbar`. An icon-only control uses its action; a decorative icon retains its actual component name, such as `ArrowLeftOutlined`.
- When multiple instances need distinction, add a stable business scope/role to the component name: `AllGroupsTable`, `MyGroupsTable`, `SelectionRecordsSearchForm`, `ApplicationRecordsSearchForm`, `ExportModal`. Do not add page prefixes to already unique structural components. Avoid redundant type suffixes when the name already explains the business action and Studio displays the type.
- Native layout wrappers use their semantic or layout role, such as `PageBody`, `DetailHeader` or `MetricGrid`. Nodes without meaningful business context use the actual registered display name or PascalCase layout/tag name. Do not invent a function for a spacer or create wrappers solely to carry a name.
- Repeated template instances may share a stable template name. Do not append row numbers, mock record names, random IDs, stale `Copy` suffixes or arbitrary numeric suffixes. Resolve authored-name collisions with meaningful scope, and read back the applied name after renaming.

| Actual node and purpose | Preferred editor name |
| --- | --- |
| Single standalone page shell | AppShell |
| Single page-level query form | SearchForm |
| Two query forms in record Tabs | SelectionRecordsSearchForm / ApplicationRecordsSearchForm |
| Dropdown offering group creation choices | CreateGroup |
| Button opening that creation menu | CreateGroupTrigger |
| Select filtering by status | StatusFilter |
| Tables in All/Mine scopes | AllGroupsTable / MyGroupsTable |
| Native wrapper arranging list actions | ListToolbar |

Set names during generation using `data-plasmic-name`; keep `data-plasmic-component` as the real component identity. Rename existing nodes through MCP `changeElement.name`, which uses Studio's rename operation to maintain state/expression references. Preserve node UUIDs, slot names, business prop names, state identity, event/action keys, routes and interactions. Implicit state references may change when the node name changes; inspect readback instead of manually replacing arbitrary expression text. Node names are editor metadata, not UI labels or routing keys. Do not rename registered components, imported library definitions or slots to implement instance naming. On copy/reuse or functional changes, update obsolete names to match the destination purpose.

Acceptance: read every changed node, including inactive Tab/overlay children and copied nodes, and compare PascalCase, uniqueness scope and semantic naming against its actual component/content/action. Every standalone page must have exactly one shell instance named `AppShell`. Inspect the editor tree/selection label, save/reopen, and confirm names persist, UUIDs remain, references resolve and affected interactions still work. A formatting check or successful `validate` alone does not establish semantic correctness.

## Viewport and shell

Use the live Studio `Desktop` device preset by default for PC requirements (currently 1440×1024); discover it through MCP `read.devicePresets` rather than assuming 1920×1080. Explicit user dimensions take precedence. Keep only Desktop preview columns in Pages and one overview Arena for the requirement; its artboards reference the existing routed Pages. Do not deliver per-page duplicate Arenas, test pages or mobile/tablet frames. Do not generate mobile breakpoints or responsive overrides for PC-only scope. For a fixed design viewport W×H, keep the preview/artboard dimensions W×H and use `height: 100vh`, `minHeight: 0`, `maxHeight: 100vh`, `width: 100%` and `minWidth: Wpx` on the Page root, with AppShell height 100%. A live preview window may be shorter than the design viewport; the root and shell must fit that preview viewport rather than trigger outer document scrolling. Percentage widths alone can shrink inside the global theme wrapper. Confirm the rendered shell starts at (0, 0), fills the preview viewport and keeps its header fixed while content scrolls. Use the AppShell content region as the single vertical scroll owner; Tables grow naturally with their rows and pagination. Do not set Table scroll.y, fixed body heights or nested vertical scroll containers unless the requirement explicitly requests a bounded table viewport. Keep pagination reachable by scrolling the content region; do not enlarge the artboard. Preserve horizontal Table scrolling and fixed columns when the column widths require it. If the host owns navigation, do not duplicate it. For a standalone admin preview use the registered `plasmic-overseas-app-shell` component and its Page body slot; never duplicate its layout markup. The shell owns the outer 16px padding, so the slotted business container must not add another outer padding. Its geometry is: 239px white sidebar, 64px brand/header, header horizontal padding 24px, content background neutral and padding 16px. The page body fills available width and has no forced white background; SearchForm and business cards own their own surfaces. Avoid another enclosing card. Use product branding and menu evidence from the original design. Configure AppShell menuItems once as the complete nested navigation tree with href routes; put detail and creation routes under their parent with hidden=true when they must not appear in the sidebar. AppShell derives breadcrumbs and selection from Plasmic pagePath, including all menu ancestors. Never pass a separate per-page breadcrumb list or render it again in business content. Do not add a decorative title/description block by default.

Use Antd6 tokens for color, typography, borders and radius. Blocks gap 16px; inline actions gap 8px; drawer footer gap 12px. Card titles 16px/600, counts secondary. The current Antd6 registration spells default control size `medium`; inspect the actual contract rather than passing Antd5 `middle`. Table defaults to `large`.

### Card ownership

Use the registered `plasmic-antd6-card` for a business surface with card appearance: a list containing toolbar/Tabs/Table/pagination, grouped form information, a detail information panel or a metric card. Read the installed Card contract before generation. A background, border, radius and padding on a native section/div do not fulfill this requirement. Use registered Antd6 Flex, Row/Col and Space for layout without a card surface; native main/section/div remain appropriate when semantic grouping is needed; SearchForm and AppShell keep their own surfaces, without an extra Card around them. Avoid nested cards unless the source explicitly requires separate surfaces.

Place business nodes in Card's children Slot; keep Tables inside their existing Tab content slots. Use title and extra slots only when the design calls for a Card header; do not add a header solely because Card supports one. Appearance comes from Card's theme and supported props. With the current contract, use size=medium and variant=outlined; configure body padding through styles.body rather than a padded outer section. A plain information/form/metric card typically uses 16px vertically/20px horizontally. This is not a universal Card padding preset: Tabs and Table spacing ownership below takes precedence. Layout components inside children may provide gap or columns but must not repeat the surface or body padding. Card grows with its content; the AppShell remains the vertical scroll owner.

When Tabs is the first content and its tab bar already supplies top spacing, set Card body and all intervening wrappers' paddingTop to 0. Do not reintroduce that space as margin, a translated/absolute offset or an empty header. When the last Panel content is a Table whose pagination already supplies bottom spacing, set Card body, Panel and intervening wrappers' paddingBottom to 0; do not add fixed-height slack or a spacer. For the current Antd6 list composition, styles.body.padding is `0 20px`: Tabs owns the top and Table's pagination margin owns the 16px bottom gap. Keep left/right Card body padding 20px. Do not modify Tabs internal label padding or Table pagination margin to compensate for an outer spacing error. For other compositions inspect the actual component spacing and assign each edge to one owner.

For Cards containing mixed Tab panels, assign bottom spacing per panel. A Table panel may rely on its pagination margin, but a Descriptions/form/text panel has no such owner: when Card body paddingBottom is 0, give that panel one 16px bottom padding. Put this padding outside conditional sections so hiding a type-specific section does not remove the gap. Do not add padding to Descriptions internals or increase the Card padding globally, which would double the spacing on Table panels. Check every panel and relevant visibility state, including a missing pagination footer, by measuring its final visible content to the Card inner bottom.

After save/reopen, measure Card inner body → every wrapper → Tabs top and Table bottom → wrappers → Card inner bottom. Top offsets must be 0 when Tabs owns top spacing, and external bottom offsets must be 0 when Table owns bottom spacing. With the current bordered Card, the outer 1px border is not body padding. Check the pagination's own bottom gap separately (currently 16px). Reject an extra 16px outer gap even when total spacing looks balanced; verify both model padding and rendered geometry.

Record the planned Card names and contents in the generation input and acceptance matrix. Readback must show real Card instances and the intended business nodes inside their children Slots; reject native substitutes, empty Cards with sibling content and imported sample children. When migrating an existing surface, insert Card, move existing content with moveElement to preserve UUIDs/state/interactions, then remove the obsolete native surface. Check complete-page geometry and save/reopen persistence. Use verify_slots.py with the intended Card markup to check component identity and content ownership, in addition to screenshot review.

### Overview metrics and information cards

Before generation, record each field's source, role (label/value/unit/comparison/section heading), applicable types, empty-state meaning and action destination in the task plan. Choose the composition from these roles and the available content width; do not derive it from a previous generated screenshot. Business field names, mock values and page-specific card arrangements stay in the task workspace.

Use registered Card instances and their supported body styles, with editable children Slots. Use Statistic for emphasized numbers, readable text for dates and Badge/Tag for applicable states. A metric label is secondary text, not a section heading. For a compact desktop metric row without a source-specific typography decision, use these **project defaults**, not purported universal Ant Design defaults:

| Role | Default font size / line height | Treatment |
| --- | --- | --- |
| Metric label | 14px / 22px | Regular, secondary color |
| State value | 20px / 32px | Regular, semantic indicator |
| Date/time value | 18px / 32px | Complete required precision |
| Emphasized number | 24px / 32px | Real Statistic content styling |
| Comparison/context | 12px / 20px | Secondary, readable full meaning |
| Information section heading | 16px / 24px | Weight 600, normal tracking |

Honor explicit design/theme choices instead. Check actual inherited styles and the installed prop/Slot contracts; never invent a prop to force this typography. Native editable text must not acquire incidental editor padding that shifts label/value starts. Keep intended inner spacing in one owner. For plain metric Cards use body padding `16px 20px`, label-to-value gap 8px and sibling gap 16px, unless the source requires another density.

Build a label and a natural value region. A single-line composition with the defaults above derives its height from 22px label + 8px gap + 32px value + vertical body padding and actual borders; do not emit that sum as height/min-height. Equal height alone is not a quality target. Do not use arbitrary body min-height, empty spacers or unrelated card stacks to stretch sparse metrics. Align comparable labels and value regions, while retaining intentional differences between numeric, date and state typography.

Choose comparison placement before insertion. A short comparison may share the value row when the complete number, unit and comparison fit at the target width. Its Tooltip must expose baseline/direction/unit meaning, support hover and keyboard focus, and preserve required primary values in the visible UI. If content cannot fit, allow a natural extra line or choose fewer columns according to the source; reassess the density of the whole row. Never truncate required values or hide required business fields just to retain a compact height. Test the longest source-relevant value/label and comparison, including wrapping; a short mock value is insufficient.

Information cards grow with their own content. Top-align asymmetric columns; check both the parent grid and the component instance for stretching/height. Put actions in a genuine Card header's extra Slot or beside an inline summary heading/in natural content flow. A lone link must not expand and center across a sparse card. Keep summaries read-only when a separate view action is required. Preserve source-required repeated metrics while explaining each region's role, such as quick count/comparison versus snapshot time, mode or scope.

Derive all regions from consistent data/state. Do not invent comparisons without a baseline or success results for pending/failed operations. Distinguish an absent first snapshot from a retained historical snapshot during a later operation, using the requirement's actual semantics. Hide inapplicable type-specific fields without leaving an empty grid column.

**Acceptance gate:** compare each card with the independently source-derived checklist in editor and real preview at the requested viewport, then repeat after save/reopen. Record expected and measured label/value starts, label-to-value gap, body edge padding and each value region's bottom-to-Card-inner-bottom distance (exclude the border). Explain any space beyond intended padding from actual content/structure; matching card heights is not a pass. Inspect glyph spacing, prominence, wrapping, action placement and the complete region screenshot. A working Tooltip, valid model or successful save cannot pass this visual gate.

Cover populated values, legitimate zero/empty data, absent comparison baseline, type-specific hidden fields and longest relevant content where applicable. Exercise Tooltip hover/focus and actual summary actions. Record model, geometry, visual review and interaction conclusions separately. Fix the generation source when a rule fails, rather than declaring acceptance from a one-off model patch.

## Query and list structure

Query → list toolbar/Tabs → Table → pagination. Use Overseas `plasmic-overseas-search-form` for every list query region. Read its installed contracts; install/upgrade Overseas if SearchForm is absent. Use the four-column default (colSpan=6) and minRows=1: three visible fields and actions in column four. Inspect Item span overrides too; a date range must not retain span=8 from a previous three-column layout unless that wider field is explicitly required. For exactly three ordinary fields, the default composition has no overflow row and needs no expand/collapse control. Add editable `plasmic-overseas-search-form-item` nodes in its children Slot; configure a unique name, label, span, initialValue, clearValue and validation per Item. Place exactly one Antd6 control in each Item's children Slot and edit placeholder/options/date mode on that control. Use extraActions for additional buttons and labelContent/help for custom content. Insert/delete/move/change real Item/control nodes; never construct a native query grid or store React controls in fields JSON. SearchForm owns query/reset/expand buttons and shows all fields in the editor; runtime collapse retains values. SearchForm labelWidth is an optional component prop: when unset, each label follows its own content width. During generation, inspect all labels in the form, including initially collapsed fields, custom label content, required markers and punctuation. Choose and explicitly configure one shared labelWidth using the longest rendered label at the actual font size, including the actual font width, required/help markers, the generated colon and its native margins, with enough space for every label to fit on one line; do not assume a universal fixed width or put that design choice in the component default. Verify that the chosen width leaves usable control space at the target viewport. If a label changes, reassess the whole form width. The editor's forced expanded display must show 收起, an upward indicator and aria-expanded=true; preview uses the actual collapsed state. Verify both modes, including control start positions for short/long labels, full one-line label text with no clipping or ellipsis, consistent colon-to-control spacing for both short and long labels, clearing labelWidth to restore content widths, and the transition in both directions. Labels use plain text without manually appended colons or spaces; Form owns punctuation and its native spacing. Do not patch individual labels with spaces or CSS offsets to compensate for a narrow label column. Keep applied values distinct from drafts. Bind onSearch(values)/onReset(values) to applied filters and return to page one; reset restores defined defaults/clear values. Set marginBottom=0 when the parent supplies spacing. Do not fabricate a filter prohibited by the requirement.

Business actions such as create, import or launch belong to an editable business toolbar, distinct from SearchForm's query/reset/expand controls. When that toolbar is displayed above a SearchForm, align its actions to the content region's left edge using normal flex flow (`justify-content: flex-start`), with an 8px action gap and 16px separation from the filter row. The button's outer left edge aligns with the SearchForm's inner content edge, not with the label glyphs or the input after labelWidth. Do not push a lone business action to the far right. This is the admin query-region convention; page-header actions, Modal footers and the SearchForm's own action column retain their respective component/layout contracts. Preserve an explicitly approved ordering of toolbar and filters, and derive actions and permissions from the current requirement.

Use Tabs for data scopes such as All/Mine. Each Tab's content slot owns its Table, pagination and state. Shared primary action belongs in Tabs extra; one primary page action. Do not draw tab labels above a sibling table. Remove outer top padding when Tabs already supplies it. Preserve the registered Tabs motion defaults: animated=true, animateTabBar=true and animateTabContent=false. Do not disable all animation merely to switch Table content immediately; the ink bar and content animation are independent controls. Only override these defaults for an explicit requirement. In live preview, switch tabs in both directions and verify the animated ink-bar class, correct indicator bounds and matching content, then recheck after save/reopen. Static screenshots alone do not prove motion.

Use real Antd6 Table columns and render slots. Status uses Badge preset plus business text; Tag is for categories. Place operations last and fixed right, size the column to visible actions, filter by permissions before collapsing secondary actions into Dropdown. Truncated text must expose its complete content through an actual Tooltip on hover or keyboard focus, only when it overflows. Browser title attributes and detail/copy actions do not replace this Tooltip. Preserve complete source values and meaningful 0/false. Wide content scrolls horizontally within the table, never widens the viewport.

For PC pointer interaction, ordinary Dropdown menus use hover: row ActionGroup More, creation menus, header language and account menus. Keep the Ant Design enter/leave delays so moving from the trigger into its menu does not close it; selecting a menu item executes the action and closes the menu. Select, Cascader and date pickers remain click-operated form controls, and Popconfirm remains an explicit click confirmation. Use click for touch requirements or an explicitly click-operated interaction; contextMenu is reserved for an actual right-click requirement. Do not carry click overrides from an earlier prototype into ordinary PC menus. Read each component's live contract: Dropdown exposes trigger="hover"; ActionGroup uses dropdownProps.trigger=["hover"].

For Dropdown changes, verify opening without clicking, moving into the menu, leaving both trigger and menu, item selection and disabled items. Confirm hovering never performs the business action, and opening More does not open a confirmation. Test the actual registered Dropdown, ActionGroup and header menus; capture the visible menu and confirm its state after selection or leaving. Recheck the delivered props after save/reopen, including explicit click overrides.

Default page size 20 with options 20/50/100 unless the requirement says otherwise. Sample rows and total must agree, ideally at least three pages for pagination testing. Let the Table grow naturally; scroll the AppShell content region to reach pagination. For a Table inside a Modal, bound and scroll the Modal content region instead of the Table body, keeping the title and footer reachable. Verify 20/50/100 rows, expanded/collapsed filters and All/Mine scopes: the whole business region moves vertically while shell navigation stays fixed, with no second Table body scrollbar. Do not force a tall empty card; leave bottom spacing 16px once.

### SearchForm acceptance

Inventory every generated SearchForm by Page and Tab, including initially inactive Tabs. Record the expected grid, effective Item spans, shared labelWidth, business-action placement and relevant collapsed state independently of the generated output. Read back every instance and inspect its editor and real-preview layout at the requested viewport. Measure column widths/row positions, label and native punctuation fit, usable control space, and business-button alignment with the filter content edge (within 1 CSS pixel). Three ordinary fields in the default four-column layout must leave query/reset controls in the fourth cell on the same row, without an unnecessary expand control. Exercise query/reset separately from the business action; verify the action opens its intended destination and preserves required permission/disabled behavior. Recheck changed regions after save/reopen. Record model, geometry, screenshot and interaction outcomes separately; unvisited Tabs or unmeasured criteria stay unverified and cannot receive a blanket page-level pass. Model validation, slot/route checks and Skill format validation do not establish this visual acceptance. Correct both the generation source and delivered model when a rule fails.

## Table column widths

For tables, record each field's purpose, longest common real value, required complete boundary value, width and overflow policy in the sidecar acceptance report. Retain the requested App viewport and verify the actual component metrics; do not copy widths from a differently sized reference composition.

Use these starting widths in pixels: short IDs/counts and type/scenario 96–128; status and people 128–176; timestamps 160–192; names 200–280; keys/code 240–320; notes 280–360. Keep ID/count/time/enumeration/status values complete. Name/key/people may ellipsize with an actual overflow Tooltip; details or copy are additional ways to access the value. Set the real Table.Column ellipsis prop instead of shortening data or merely styling a span. Verify actual overflow and the visible Tooltip with complete text before claiming success; configuration alone is insufficient. Short or empty content must not create redundant popups.

When a column needs an editable display/Tooltip template, use its “Convert to editable template” action with ellipsis enabled. The resulting registered Tooltip has onlyWhenOverflow=true, editable children/title Slots, and bindings in the column's real render scope (cell, row, index, column). Edit these actual nodes; do not add a parallel tooltip configuration schema or copy a row's static text across all rows. A custom title may combine current-row fields; keep display and title bindings consistent with the intended complete content. Selecting the Tooltip or its title reveals the overlay for editing without persisting an open state. Verify at least two distinct rows, text/template content, 0/false/empty values, resized columns, and save/reopen. Check that selection reveals do not force popups in preview or exports and that hovering/focusing never runs row actions.

Pass complete permission-filtered items to registered `@react/ui` ActionGroup and let it fold them. Set max=3 consistently unless the user specifies another limit; when folding occurs, More consumes one of those three positions. Rows with fewer authorized actions naturally show fewer controls. Measure the widest visible ActionGroup for valid rows in the current role, add actual left/right cell padding, and round up for the fixed-right operation column. Exclude hidden menu widths. An existing width is not evidence that it still fits after replacing the action component.

Fix widths for short fields, status, time and operations; assign remaining container space only to the main text column. For Antd tables, one column without an explicit width can absorb that remainder. Make the scroll content width agree with the fixed widths plus the main text baseline, so the browser cannot proportionally expand fixed columns. Preserve widths when the sum exceeds the viewport; verify horizontal scrolling and the fixed-column boundary. Static Pen full-column views are a source presentation convention; in the interactive App verify every column by scrolling and retain measurements and screenshots in the acceptance evidence.

After save/reopen, read both column props and rendered header/cell widths. Check All/Mine use the same definitions, the operation width equals measured content plus padding, remaining space only enlarges the text column, the longest status and timestamps fit, ellipsis preserves complete values, and the horizontal track/fixed columns/pagination remain usable. Report these as individual checks with evidence, not a generic screenshot approval or model-validation result.

## Forms and state

Use real labeled inputs, Selects, Buttons and feedback. Modals/Drawers keep the full source page behind them, close unrelated menus, and retain a reachable footer. Keep destructive or unauthorized actions gated according to the source. Loading, failure, success and recovery states belong to the actual flow; do not manufacture generic state boards or placeholder future features.

Editable business forms use the registered Antd6 Form with real Form Field/Form.Item instances and their label/children Slots. Give each field its actual name and validation rules through the installed contract; let Form own required indicators, punctuation, error state, error messages and field values. A literal `*` in label text or a separate red error div is not required-field validation. Derive initial values at Form/Item level without competing control value bindings. Use required and whitespace rules for required text when blank-only values are invalid; choose other rules from the requirement. Submit through the supported Form action/validated event or await its registered validateFields action before a mutation. Rejected validation keeps the Modal open, identifies the field, and performs no mutation.

Field-label explanations belong in the real Form.Item `tooltip` prop/Slot. Keep the label plain and let Form.Item place its native help icon beside the label; do not build a separate Tooltip/button beside the control or type an `i`/question mark as an icon. Advanced Form Fields expose editable tooltip content; simplified Form fields expose tooltip text in their field configuration. Read the installed contract first. If tooltip is absent, update the registration and published library before using it, rather than inventing a substitute prop. Persistent instructions belong in field help/description, not a label tooltip.

Inventory every project Page, business Form and field across inactive Tabs and Modals before editing. Pages without business Forms still declare `forms: []`. Record field keys, labels, required/whitespace/business rules and tooltip content independently of the generated output. Run `python3 scripts/verify_forms.py <expectations.json> <mcp-read.json> --overview <mcp-overview.json>` against full public MCP readbacks and again after save/reopen. The overview must cover the entire project. This mandatory gate rejects missing/extra Pages, Forms or fields, unowned editable controls, competing values, label stars, separate field-help Tooltip/buttons/icons, manually bound field-error blocks and advanced validators stored as literal strings. Declare genuinely standalone controls, such as a separately validated SQL editor, in each Page's `standaloneControls: [{nodeName: "SQLEditor", reason: "Separate SQL validation workflow"}]`; entries must be named, unique, used and outside business Forms. SearchForm Items retain their own control ownership. The static scan checks model patterns and contracts; runtime validation still requires preview acceptance. Move existing controls into real Item children Slots to preserve their UUIDs and applicable interactions. For a field with adjacent actions, keep the actual control as the Item's direct first child; use a nested noStyle Item when a layout wrapper is required. Replace manual error state and value-based submission handlers with Form values and validation, update affected references, then remove obsolete wrappers, label stars and tooltip buttons.

For a Modal with one confirmation action plus cancel, keep the component's default footer and locale-owned button text. Omit okText/cancelText and custom footer children; do not recreate the two default buttons just to attach events, loading or disabled state. Bind onOk/onCancel and use the real confirmLoading/okButtonProps/cancelButtonProps contracts for submission state. Custom footer/text is appropriate when the required workflow has multiple distinct operation actions (for example draft/save/publish), rather than a routine confirm/cancel pair. An explicit user requirement overrides this default. Remove obsolete custom buttons, label stars, manual field-error nodes/state and their handlers when replacing them.

An empty footer Slot is still an explicit override and can hide the native footer in preview. Restore defaults through changeElement resetProps after deleting custom footer children; do not insert an empty footer Slot or use footer=null for a default-footer Modal. Reset obsolete okText/cancelText/hideFooter overrides too. Empty-slot cleanup must distinguish removal of unused example content from restoration of a component default. Check actual runtime buttons after that cleanup. When editing node names, recheck registered Form ref actions in submit/cancel handlers so renamed forms remain callable.

Spacing between adjacent components has one owner. When the last Form.Item already supplies its theme margin-bottom, a following Alert/help block must not add another margin-top or parent row-gap on the same boundary. Preserve native Form.Item spacing and set the extra wrapper gap/margin to zero for that composition. If a different composition intentionally transfers spacing to the parent, remove the matching child margin instead of stacking both. Verify the rendered control/error-to-next-block distance in normal and validation-error states; checking Alert's margin alone misses parent gap and Form.Item margin.

Form/Modal acceptance records model and runtime checks separately: verify the delivered Form/Item ownership, field names/rules and plain labels; verify a default footer has no custom button/text overrides. In real preview, empty and blank-only required inputs must show native field errors without closing or creating a record. Correcting the value must permit one submission; during processing check loading, control/button disabling and duplicate-submit prevention, then verify success and cancellation/reopening reset behavior according to the requirement. When the Modal footer is outside Form, do not assume browser implicit Enter submission works: verify the supported input Enter event reaches the same Form validation and duplicate-submit guard as onOk, preventing the default event if needed. Inspect required indicators, label-to-control spacing and reachable default footer in editor and preview, and recheck persisted structure after save/reopen. A visible asterisk, working success path or valid model alone does not pass form acceptance.

For each field tooltip, verify the native icon is in the label, hover opens the expected content, the control remains usable, and clearing tooltip removes the icon. Recheck editor, actual preview and saved readback. Do not force persisted open state for inspection. Verify required indicators and tooltip coexist without duplicate marks or a second label model.

Verify dynamic initial values and custom rules execute in preview: a nested `{{ ... }}` binding inside `initialValues` or `rules` must be a native expression, not literal text. For a uniqueness rule, test both an existing key and a distinct key; for a numeric range, test valid integers, decimals and out-of-range values. When a footer submits through a Form ref, test a form remount or reopening with another record so stale refs cannot silently bypass validation or submission.

### Modal form layout

Choose Modal width and Form columns together from the field inventory. Do not make every Modal multi-column. A short, simple form usually starts at 480–560px with one column. A 640–800px Modal can use two columns when its actual body width, padding and column gap leave roughly 240px or more of usable width per field and the longest labels/values fit. These are starting points, not component defaults or a substitute for preview inspection. Do not use three or more columns in an ordinary confirmation Modal without an explicit dense-entry requirement.

| Field content | Default allocation |
| --- | --- |
| Long business names, generated/editable Keys, URLs or addresses | Full row |
| Textarea, code/rich-text editors, upload lists and complex nested fields | Full row |
| Short enums such as type/status/scenario, short numbers, single date/time | Half row when the label, control, help and error all fit |
| Person/entity Select, multi-select, date range | Decide from the longest expected content; use a full row when a half row would truncate or crowd it |
| Switch/Checkbox and fixed read-only metadata | Compact related group or information row; avoid a large empty control area |

Input component type alone does not determine column span. Pair related short fields; make an unpaired final field span the row or choose a narrower single-column Modal. Do not leave an unexplained empty half-row beside an editable field. A full-row Key with an adjacent regeneration action must reserve action space without wrapping or overlapping it.

The Form and every intermediate field-layout wrapper must fill the Modal body width through explicit width:100% or verified stretch alignment, with min-width:0 on grid/flex children. In particular, a full-width Form with align-items:flex-start does not make an un-sized child wrapper full width. Use equal columns, a 16px column gap and explicit full-row spans. Prefer a full-width Antd6 Flex column and Row/Col for mixed full-row and paired fields, using the real registered gutter/span contracts and full-row allocation for long fields. Verify actual component geometry rather than assuming native CSS grid properties apply to Row/Col. Controls fill their allocated cells. Preserve native Form.Item vertical spacing; do not add parent row-gap on top of it. Keep each real control directly in its Item children Slot even when the Items are arranged in a grid.

For Antd6 Row/Col layouts, verify real gutter/span props and rendered column widths, full-row fields and ownership; the optional CSS-grid row check below does not validate Row/Col props. Form field/validation checks still apply to every layout.

For authored CSS-grid rows, record optional Form layout expectations as `layout: {container: "NewGroupFields", modalWidth: 640, columns: 2, columnGap: 16, rows: [{container: "NewTypeScenarioRow", fields: ["NewTypeField", "NewScenarioField"]}]}` and each field's `span` (1 or 2) in the independent field inventory. `verify_forms.py` checks the Modal width, the vertical container and paired rows fill the Form width, the paired row columns/gap, its complete field group and full-row/half-row placement against the saved model; a mismatch must fail the generation check. Run it before delivery and after save/reopen. This structural check does not measure rendered geometry. In actual preview inspect every affected Modal at the target viewport: controls reach their intended column edges, the longest realistic labels/values and adjacent actions fit, validation errors expand without overlap, and the native footer stays reachable. Capture the opened Modal, not just the background page or hidden editor node. Update the generation source and delivered model together when fixing a layout failure.

### Heading typography

Use a registered component's actual heading Slot when the heading belongs to that component, such as Descriptions title, Card title or Modal title. Keep text editable and let the installed Ant Design theme own its typography and internal spacing. Do not nest a styled native heading inside the Slot or place a duplicate heading beside it to imitate the component. Use a native semantic heading for a separately composed page/section heading; choose its level from document hierarchy, not the desired font size. Different heading roles retain their own scale; do not apply one font size to every title.

For a Descriptions group heading, use the registered Descriptions `title` Slot with editable text. Let the component theme own title typography and title-to-fields spacing; do not imitate it with a separate native heading immediately above an untitled Descriptions. Keep spacing between groups on their containing layout.

For native semantic headings, explicitly set `letter-spacing: normal` unless the approved design specifies tracking. Plasmic's default heading theme can retain negative letter spacing after the font size is reduced; changing font size/weight/line height alone does not reset it. Inspect actual Chinese and Latin glyph spacing in editor and preview, not only the heading container's bounds. Resolve font family, size, weight, line height and margins against the approved hierarchy and actual inherited theme; account for theme defaults beyond the overridden properties. Avoid adding custom tracking just to make a heading visually larger.

Before acceptance, inspect all generated page, section and component headings at the target viewport in editor and live preview. Check actual glyph spacing, title-to-content separation, sibling consistency and long-text wrapping. Save/reopen and verify heading ownership and explicit overrides. Record model checks and rendered observations separately; do not mark a preview check passed when it was not executed.

### Component behavior contracts

Use the installed Ant Design version's defaults for component behavior. Keep registration hints and runtime defaults consistent; a hint is not an injected value. Business conventions such as 20 rows per page belong in the page's explicit props. Do not seed a different current step, force Tree expansion or Avatar overflow, or leave Badge demo children/counts in status rendering.

Modal OK invokes its callback without closing automatically. Bind a real validation/save flow and explicitly change the open state only after success; invalid input or failed saving must leave the form available for correction. Cancel/close must clear the open state. Form disabled must remain effective, including ConfigProvider inheritance; temporary submission disabling must restore on both success and failure. Await validateFields and stop the mutation on rejection. Custom exact-length rules must actually reject invalid values. When concurrent submissions are explicitly permitted, submitting remains true until all finish.

Invalid-input acceptance requires a visible inline field error as well as blocked saving. Required text rejects whitespace-only values; correcting it clears the error. A dialog that simply remains open without explaining the invalid field does not pass validation-feedback acceptance.

Table selection must persist without a state binding, and controlled selection must follow the bound keys. Clear selection and radio/checkbox modes must work. Pagination initializes its derived indexes from current/default props without emitting a business onChange; changes after user interaction update both page and index values. Numeric input state is numeric; Checkbox Group state is an array.

Preserve explicit false, zero, empty string and null according to each native prop's contract. Tooltip empty/null title disables its fallback. Select honors custom filtering, server-side filterOption=false and suffixIcon=null; labels may be React nodes or numbers. ColorPicker updates its value on change while preserving the separate completion callback. Date ranges honor default dates when uncontrolled, respect controlled values and allow typing by default; read-only is explicit. Do not inject global date-picker CSS from each component instance. Upload reads files locally as base64: done means local reading completed, not server upload success. Multiple selection preserves order; maxCount retains the newest files.

Modal footer=null hides its footer; zero and responsive width values must pass through. Mask visibility and outside-click closing are separate settings; an explicit close setting must work with boolean and object masks. RangePicker inherits disabled from ConfigProvider when omitted, honors an explicit disabled=false, and applies single-side flags only without a whole-control override. A whole-range allowEmpty=false must not enable an endpoint through leftover split flags.

Merge native semantic classNames (including function forms and nested popup classes) with Studio scope/reset classes; neither may overwrite the other. Preserve independent root, input, popup, body/container and panel classes. Avoid leaking editor-only styling props into native DOM attributes. Test portal overlays and controls with both class sources present.

Select single/multiple/tags and TreeSelect single/multiple/checkable values may be scalars, arrays or labeled objects. Their registered state and event types must represent those modes; tags supports multiple initial values. Native Menu onSelect receives an info object containing key and selectedKeys, not a bare key. Rating symbol slots accept single nodes, arrays and text; hover events receive the numeric rating. Progress's omitted type is line, so step colors must work without explicitly setting type; preserve an explicit zero success segment. ActionGroup uses Antd6's medium size spelling.

When changing a wrapper, test omitted props, explicit overrides and controlled/uncontrolled use against the same installed Ant Design version. Exercise validation failure, rejected/thrown save, retry, duplicate submission, disabled controls, selection, clearing and event timing where relevant. Run the package's behavior tests and registration/build checks. For affected prototype flows, exercise live App interactions and record screenshots plus observations; screenshots do not prove callback order, validation blocking or state recovery. Keep component examples and capability-test pages out of the deliverable.

### Feedback and row confirmation

Read the live feedback contract before binding callbacks. The Antd6 ConfigProvider global action `showMessage(type, content, duration)` supplies themed Message feedback; generated previews must bind `$globalActions` for custom callbacks too. ActionGroup row items can declare `confirm` with title/description/okText/cancelText; `onAction` fires only after confirmation. Verify these behaviors in real preview, since valid expressions and successful model validation do not prove runtime feedback.

Choose feedback from its purpose and the requirement. Copy, ordinary save, delete and status-change completion use a short Ant Design Message/toast; they must not insert a persistent page-top success Alert or change the list geometry. Use inline field errors for validation. Alert belongs to persistent contextual information, actionable failures or a result that the user must inspect. Notification is for longer asynchronous or cross-page information. Record exceptions explicitly when the requirement prescribes another behavior.

Use registered Popconfirm for single-row delete, enable/disable and other actions whose consequence fits a short sentence. Anchor it to that row's action control or ActionGroup, including actions selected from More; close the menu and keep the source list visible without a modal mask. Include the object, consequence, cancel and an action-specific confirm label; apply danger to destructive confirmation. Execute the mutation only on confirm. Cancel/outside dismissal must not change the record, and must clear pending confirmation so another row works. Never replace these row confirmations with Modal. Modal remains appropriate for source-required preflight results, input forms or substantial impact/diff review.

Acceptance must exercise repeated copy, automatic message dismissal, and unchanged filter/Table/pagination positions; verify the copied row and total rather than the toast alone. Exercise row confirmation through More, cancel and confirm, check that no mutation occurs before confirmation, and inspect the popover anchor, viewport bounds and absence of a modal backdrop in a screenshot. Recheck another row, permission gates and save/reopen. Component props and model validation alone do not pass these checks.

Do not allocate a separate return row or show a permanent “Back” / “返回列表” label by default. The AppShell breadcrumb already communicates hierarchy; do not repeat it in the business header. An explicit user-approved design may prescribe another arrangement. Apply this rule when generating the page, including read-only details; an older prototype's separate return row is not an instruction to retain that layout. Pattern reference: [Ant Design PageHeader examples](https://4x.ant.design/components/page-header/). This is a composition rule, not a claim that the installed Antd6 library exposes PageHeader: use the actual registered Card/Button/Tooltip/icon contracts and prefer registered Antd6 Flex/Space for the header layout; do not invent a PageHeader component or add a parallel header schema.

Use a 20px/600 title with 28px line height, a 16px ArrowLeftOutlined icon and an 8px icon-button/title gap as the default admin hierarchy. Put the independently registered `@ant-design/icons` instance in the Button icon Slot, with no visible text child; do not substitute Unicode arrows or copied SVG paths. Keep a real button hit area of at least 32×32px, hover/focus feedback and a keyboard-accessible action. Wrap it with a registered Tooltip naming the verified destination in the business page language, such as “返回列表”, and set an accessible name through a supported prop/HTML attribute. Read those live contracts before insertion; do not assume a prop exists. The destination label stays available through Tooltip and assistive technology even though it is not permanently displayed.

Let the title grow and wrap with min-width:0; keep the return icon aligned with the first title line, and prevent type/status from shrinking or overlapping it. Secondary metadata starts below the heading row. Derive its column arrangement and left alignment from the current requirement and user-approved design; keep those task-specific choices in the source inventory. The official PageHeader content starts at the content area's left edge ([official styles](https://github.com/ant-design/ant-design/blob/4.24.16/components/page-header/style/index.less)). When the user chooses title-aligned fields, leave the return control in a separate left gutter, derive the metadata inset from the actual return control width plus the heading gap, and verify the rendered field/title edges. Do not describe this inset as the official default or change the row/column arrangement to resolve an alignment issue. Default metadata uses 14px/22px text, 24px column and 8px row gaps, with 12px separation from the heading. Test representative long names in the complete page. Prefer wrapping; if the approved design truncates the title, expose the complete value through an actual overflow Tooltip.

Preserve the list's applied filters, scope/tab, page/page size and scroll position when returning from a record, where these states exist. Derive the route/state handoff from the actual flow and supported contracts; do not add mock query parameters or a second persisted state schema. Direct entry must still have a working parent destination. Explicit unsaved-change requirements for editable details take precedence over immediate navigation.
