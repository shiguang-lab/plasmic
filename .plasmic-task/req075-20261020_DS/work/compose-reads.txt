# Badge

Library: [Ant Design v6](../index.md).

| Registered component | Registration key |
| --- | --- |
| Badge | `plasmic-antd6-badge` |
| Badge.Ribbon | `plasmic-antd6-badge-ribbon` |

## Generation rules

Use Badge `status` (a supported semantic preset) plus `text` for lifecycle/processing status. Categories choose text or Tag under the [Tag/text rules](tag.md#tag-or-text); an enum alone does not require either Badge or Tag. Read the installed `status`/`text` contract and keep status meaning consistent with the business value. Do not leave demo children/counts in status rendering.

### Status columns and row mapping

Badge exposes only the upstream Ant Design props — `status`, `text`, `count`, `dot`, `color`, `size`, `overflowCount`, `showZero`, `children`. Never add or rely on a non-official prop such as `value`/`options`: the registered contract must stay identical to the official component.

A per-row status therefore maps the row value inside the binding expressions, not in a custom prop:

| Prop | Requirement |
| --- | --- |
| `status` | Expression that maps the row state to one of `success`, `processing`, `default`, `warning` or `error` |
| `text` | Expression that renders the row's visible status label |
| Column declaration | `statusMap` `{value: {status, label}}` recording the mapping the expression renders, covering every state |

A literal `status`/`text` in a status Column gives every row the same presentation and fails generation. A standalone status Badge may use a literal preset `status` plus literal `text`. Every state shows complete visible text; color never carries meaning alone.

### Count, dot and Badge.Ribbon

Count and dot are distinct from a text status. Read overflowCount/showZero and the supported size/color contract; zero is displayed or omitted intentionally rather than through a truthy fallback. Place a count on the actual related child control/content and avoid duplicating the same count in an unrelated decorative badge.

Ribbon owns its children, text/color and start/end placement. It is a surface annotation, not a substitute for an inline status or an authorization state. Keep complete readable business text and a single surface owner.

# Button

Library: [Ant Design v6](../index.md).

| Registered component | Registration key |
| --- | --- |
| Button | `plasmic-antd6-button` |

## Generation rules

### Types and labels

Each action group has at most one primary action, derived from the user's main task in that region. Coordinate with the existing one-primary-page-action convention: do not independently promote every Card, row or auxiliary operation. A group with no dominant action may use only default buttons. Loading/disabled are states of the intended type, not new hierarchy roles; a disabled screenshot alone cannot prove the enabled hierarchy.

| Meaning | Button treatment |
| --- | --- |
| Main task completion | `primary`; use the actual theme/contract, not a hand-painted brand color. |
| Secondary business action | `default`; use `text` for low-emphasis auxiliary actions where the owning pattern supports it. |
| Cancel/back in a completion footer | `default` by default; a verified native/approved pattern may use `text`. Ordinary cancellation does not use `primary` or `danger`. |
| Add an item inside a collection | `dashed` when the owning component/pattern calls for it; not a generic secondary-action style. |
| Navigation | Real supported Link/href navigation; a visual `link` Button type alone does not establish routing semantics. Table action appearance follows its ActionGroup contract. |
| Destructive/risky change | Use the supported `danger` treatment for verified destructive consequences, such as deletion or revoking access. Publish/go-live is not automatically danger. Confirmation and default focus follow the actual risk/requirement; a protective confirmation may emphasize cancel when that is the recommended choice. |

Use concise action/result labels consistent with the surrounding instructions and actual event: distinguish save, submit for approval, run, publish, cancel editing, return and stop a running task. Do not use a generic submit label for an operation described elsewhere as a run/test, or claim a close action stops backend work. Routine Modal labels follow its [footer contract](modal.md#footer). Do not manually insert spaces into two-character Chinese labels; preserve native typography/spacing.

Visual `type` and native `htmlType` are separate contracts. Only the intended validated form submission uses submit semantics; cancel, navigation and auxiliary operations must not accidentally submit or reset the Form. Follow the installed Form/ref action contracts, including footer actions outside Form; do not wire both native submission and a click handler to perform the same mutation twice.

Use [action-bar composition](../compositions/action-bars.md) for contextual order, alignment, grouped availability and combined Preview acceptance.

A Button that opens menu choices follows [Dropdown trigger appearance](dropdown.md#trigger-appearance), including its trailing indicator and separation from any leading action icon. A direct-action Button keeps its ordinary action treatment.

# Card

Library: [Ant Design v6](../index.md).

| Registered component | Registration key |
| --- | --- |
| Card | `plasmic-antd6-card` |
| Card.Grid | `plasmic-antd6-card-grid` |
| Card.Meta | `plasmic-antd6-card-meta` |

**Hard constraints** (always delivered with any section):

- Use Card only for an independently justified business surface (record `condition`); never around SearchForm, AppShell, Steps or every section, and avoid nested Cards.
- Initial data-props: `{"size":"medium","variant":"outlined","styles":{"body":{...}}}`; never the legacy `bordered` prop or a padded native wrapper.
- A headerless Card supplies explicit empty `title` and `extra` Slots in the initial markup.
- A Tabs-first list Card uses body padding `0 20px`: Tabs owns the top edge, Table pagination owns the bottom edge. See [Card ownership](#card-ownership).

## Plan decisions

Declare these native props in each planned instance before markup. `prepare_plan.py scaffold` writes `"__DECIDE__"` (or the baseline) for each; selection preflight rejects pending or missing values. `null` means deliberately unset and is accepted only where marked.

| Registration | Prop | Decision |
| --- | --- | --- |
| `plasmic-antd6-card` | `size` (baseline `"medium"`) | Current contract baseline. See [rule](#card-ownership). |
| `plasmic-antd6-card` | `variant` (baseline `"outlined"`) | Current contract baseline; never the legacy bordered prop. See [rule](#card-ownership). |
| `plasmic-antd6-card` | `styles.body.padding` | Explicit body padding assigned to one edge owner, for example 0 20px for a Tabs-first list Card. See [rule](#card-ownership). |

## Generation rules

### Card ownership

Use the registered `plasmic-antd6-card` for a business surface with card appearance: a list containing toolbar/Tabs/Table/pagination, grouped form information, a detail information panel or a metric card. Read the installed Card contract before generation. A background, border, radius and padding on a native section/div do not fulfill this requirement. Use registered Antd6 Flex, Row/Col and Space for layout without a card surface; native main/section/div remain appropriate when semantic grouping is needed; SearchForm and AppShell keep their own surfaces, without an extra Card around them. Avoid nested cards unless the source explicitly requires separate surfaces.

Card-scoped actions belong in the Card `extra` Slot, right-aligned in the header — for example `格式化` and `校验` acting on this Card's SQL editor, or a disclosure such as `查看 SQL ›`. Do not insert a separate button row above the body when the Card already has a header: the row wastes a full line and separates the actions from the content they control. Keep a body toolbar when the actions belong to a wider region (multiple Cards or Tabs), when the Card is headerless (use Tabs `extra` or an in-body toolbar aligned with the region), or when the same row also carries filters or search fields. Card `actions` is the footer contract, not the header slot.

Place business nodes in Card's children Slot; keep Tables inside their existing Tab content slots. Use title and extra slots only when the design calls for a Card header; do not add a header solely because Card supports one. Appearance comes from Card's theme and supported props. With the current contract, use size=medium and variant=outlined; configure body padding through styles.body rather than a padded outer section. A plain information/form/metric card typically uses 16px vertically/20px horizontally. This is not a universal Card padding preset: Tabs and Table spacing ownership below takes precedence. Layout components inside children may provide gap or columns but must not repeat the surface or body padding. Card grows with its content; the AppShell remains the vertical scroll owner.

For a headerless Tabs/list Card, clear the header Slots in the **initial** insertHtml: supply `<slot name="title"></slot>` and `<slot name="extra"></slot>`. Omitting a Slot retains its registered default; the current title default is `Card title`, even with hidePlaceholder=true. “No header” therefore requires explicit empty Slots, not just body padding. Include these empty Slots in the intended markup and verify saved readback has no header children; hiding a retained sample title with styles.header.display=none does not clear it. When a Card header is required, supply its source-derived title instead (16px/600, with counts at secondary hierarchy).

When Tabs is the first content and its tab bar already supplies top spacing, set Card body and all intervening wrappers' paddingTop to 0. Do not reintroduce that space as margin, a translated/absolute offset or an empty header. When the last Panel content is a Table whose pagination already supplies bottom spacing, set Card body, Panel and intervening wrappers' paddingBottom to 0; do not add fixed-height slack or a spacer. For the current Antd6 list composition, styles.body.padding is `0 20px`: Tabs owns the top and Table's pagination margin owns the 16px bottom gap. Keep left/right Card body padding 20px. Do not modify Tabs internal label padding or Table pagination margin to compensate for an outer spacing error. For other compositions inspect the actual component spacing and assign each edge to one owner.

Write this padding explicitly in the Card's initial data-props, including in ad hoc build scripts: `{"size":"medium","variant":"outlined","styles":{"body":{"padding":"0 20px"}}}`. Omitting styles.body does not mean "no padding"; the Card falls back to its default body padding and pushes Tabs down. Do not use the legacy `bordered` prop. `verify_slots.py` checks the planned markup itself: its `tabsCardPolicy` rejects a Tabs-first Card (Tabs as first component content, through native wrappers) whose planned styles.body has no zero top edge, or that lacks empty title/extra Slots. A missing plan is not accepted because the readback matches it.

For Cards containing mixed Tab panels, assign bottom spacing per panel. A Table panel may rely on its pagination margin, but a Descriptions/form/text panel has no such owner: when Card body paddingBottom is 0, give that panel one 16px bottom padding. Put this padding outside conditional sections so hiding a type-specific section does not remove the gap. Do not add padding to Descriptions internals or increase the Card padding globally, which would double the spacing on Table panels. Check every panel and relevant visibility state, including a missing pagination footer, by measuring its final visible content to the Card inner bottom.

After save/reopen, measure Card inner body → every wrapper → Tabs top and Table bottom → wrappers → Card inner bottom. Top offsets must be 0 when Tabs owns top spacing, and external bottom offsets must be 0 when Table owns bottom spacing. With the current bordered Card, the outer 1px border is not body padding. Check the pagination's own bottom gap separately (currently 16px). Reject an extra 16px outer gap even when total spacing looks balanced; verify both model padding and rendered geometry.

Record the planned Card names and contents in the generation input and acceptance matrix. Readback must show real Card instances and the intended business nodes inside their children Slots; reject native substitutes, empty Cards with sibling content and imported sample children. When migrating an existing surface, insert Card, move existing content with moveElement to preserve UUIDs/state/interactions, then remove the obsolete native surface. Check complete-page geometry and save/reopen persistence. Use verify_slots.py with the intended Card markup to check component identity and content ownership, in addition to screenshot review.

### Card.Meta, Card.Grid and action Slots

Meta owns its title/description/avatar inside the Card. Grid is a real Card subregion with its children/hoverable contract; it is not Row/Col Grid or a reason to nest another surface around every item. Use either structure only for the actual content arrangement and keep complete labels/values in their supported Slots.

Card actions are editable Slot children converted by this wrapper to the native actions array. Cover, extra and actions have different roles; do not repeat a page's primary action in each Slot. Verify real permission-dependent actions, long Meta text, cover sizing, loading-to-content and Grid boundaries. Hoverable presentation alone does not make the Card navigate or provide a keyboard action.

# Dropdown

Library: [Ant Design v6](../index.md).

| Registered component | Registration key |
| --- | --- |
| Dropdown | `plasmic-antd6-dropdown` |

## Generation rules

For PC pointer interaction, ordinary Dropdown menus **must use the hover generation baseline**, including creation, language and account menus. Keep Ant Design enter/leave delays so moving from the trigger into the menu does not close it; item selection executes the action and closes the menu. Use click only for an explicit click/touch requirement and record its [source-backed override](../../../design/component-policy.md#protected-configuration); contextMenu requires an actual right-click requirement. Availability of the trigger Prop is not permission to choose click for convenience. ActionGroup's equivalent protected property is dropdownProps.trigger=["hover"].

Read the live contract: Dropdown exposes trigger="hover". [ActionGroup](../../react_ui/components/action-group.md) has its own dropdownProps mapping. Select, Cascader and date pickers remain click-operated form controls; Popconfirm remains an explicit click confirmation.

Preserve a source-defined grouped create menu as one Dropdown trigger with its ordered menu choices. Discover `children`, `menuItems`/`menuItemsJson`, `useMenuItemsSlot` and `onAction` from the installed contract; a list of possible destinations is not permission to replace the menu with sibling Buttons. Shared tabbed-list actions follow [the Tabs extra ownership rule](../../overseas/compositions/search-table.md#query-and-list-structure).

### Trigger appearance

Use a stable trigger treatment for each interaction role. For an ordinary hover/click Dropdown opened by a **text Button**, always show one trailing registered `DownOutlined` indicator. Keep it present in both open and closed states and when permission filtering leaves only one menu choice. A leading action icon, such as `PlusOutlined` for creation, does not replace this indicator. A direct-action Button without a menu has no dropdown indicator. Icon-only More triggers already communicate a menu; shared ActionGroup/AppShell controls keep their own native indicators without an additional one. An actual contextMenu/right-click entry does not require this button treatment.

The current Dropdown wraps its children; it does not append a trigger icon. For a create menu, place the registered PlusOutlined in Button.icon with iconPlacement=start, then the label and registered DownOutlined in Button.children, using native Space to arrange them. If only the trailing indicator is needed, Button.icon with iconPlacement=end is also valid. Read the actual [Button](button.md) and [icon](../../antd_icons/index.md#icon-usage-and-acceptance) contracts; use editable registered icon nodes and currentColor, not Unicode, copied SVG or a new showArrow/dropdownIcon property. Native Dropdown.arrow controls the popup's small pointing triangle, not the Button indicator; it is not a substitute and must not be added when the installed contract does not expose it.

The trigger opens choices through its configured trigger; a menu item executes the chosen business action. Use a split-button composition only when the source has a separate immediate default action plus alternative menu choices and the installed library supports that composition. Do not introduce a default creation action merely to obtain a chevron.

In the source-reviewed intent, retain Button as Dropdown.children, a leading action icon in Button.icon, and the trailing indicator after the text. Verify exactly one indicator in the saved model and visible pixels, correct placement/currentColor, and no duplicate indicator after open/close or save/reopen. Static node checks do not establish CSS visibility or runtime behavior.

`menuItemsJson` uses the native Menu item `key`, including nested children, and `onAction(key)` returns that key. `value` is not an item identity. Set distinct stable keys for business branches, e.g. `[{"key":"create","label":"新建"}]`; do not compare callbacks against labels or infer an omitted key. Read the live recursive item schema. Slot mode uses registered MenuItem keys. Verify each callback branch separately, including disabled items; opening the menu does not prove routing. Internal destinations follow [source and interaction rules](../../../requirement-alignment.md#source-and-interaction-rules).

Imported library definitions can retain older persisted defaults. Public `default` reports that stored definition; `registration.defaultValue` reports the current literal registered insertion default when it differs from the stored value. New HTML instances materialize changed current registered defaults without rewriting imported definitions or existing instances; explicit props win. Build the actual source menu with explicit keys rather than retaining any sample actions. Inspect the saved instance and each runtime branch; a newer registration does not repair an old instance containing `value`.

For Dropdown changes, test the configured trigger: hover menus open without clicking and stay open while moving into the menu; explicit click/contextMenu interactions use their corresponding trigger. Check dismissal, item selection and disabled items. Confirm hovering never performs the business action, and opening More does not open a confirmation. Test affected Dropdown, ActionGroup or header menus; capture the visible menu and confirm its state after selection or dismissal. Recheck delivered props after save/reopen against the reviewed trigger.

# Form

## Generation rules

Read the installed Form contract before changing values, validation or submission. Read [Form Field](form.md#formitem) for field controls and [form composition](../compositions/form-layout.md) for page layouts. Every Form inside a Modal additionally reads [Modal form layout](../compositions/form-layout.md#modal-form-layout), which owns width, field columns, label placement and header copy for that composition.

**Reading scope**

The [rules card](../../../planning.md#rules-card-and-read-ledger) delivers Generation rules for composition and the whole document for acceptance; a focused edit uses `scripts/read_reference.py` with these `--section` selectors. Read all sections whose conditions apply; an unknown field/flow scope requires discovery before exclusion.

- Every business Form: `values-and-validation`, `events-and-ref-actions`, `acceptance`, `simplified-and-advanced-modes`.
- Any Form before markup: [form layout](../compositions/form-layout.md#layout-ownership) `layout-ownership` (label direction and column pairing are decided first; a non-default direction needs cited or measured evidence).
- Full-project generation or inventory audit: `project-inventory-and-acceptance`; a focused edit instead reads `focused-form-edits`.
- Every editable field: [field semantics](../selection.md#field-semantics), `validation-order` and `label-and-control-layout`.
- Field-label help being added, changed or present in generated fields: `label-help`.
- Visible field instructions being added, moved or present in generated fields: `field-instructions`.
- Repeated fields or grouped paths: `formlist-and-form-field-group`.
- Hidden, conditional or dependent fields: `conditional-and-dependent-fields`.

Section reads retain Form.Item ownership; use `--section formitem` for all field subsections.

### Values and validation

Editable business forms use the registered Antd6 Form with real Form Field/Form.Item instances and their label/children Slots. Read the registered rule shape: this wrapper uses rule objects such as `{"ruleType":"required"}`, not raw Antd `{required:true}`. Overseas SearchForm.Item has its own rule contract; do not copy between them. Give each field its actual name and validation rules through the installed contract; let Form own required indicators, punctuation, error state, error messages and field values. A literal `*` in label text or a separate red error div is not required-field validation. Derive initial values at Form/Item level without competing control value bindings. Use required and whitespace rules for required text when blank-only values are invalid; choose other rules from the requirement. Submit through the supported Form action/validated event or await its registered validateFields action before a mutation. Rejected validation keeps the Modal open, identifies the field, and performs no mutation.

Form disabled must remain effective, including ConfigProvider inheritance; temporary submission disabling must restore on both success and failure. Await validateFields and stop the mutation on rejection. Custom exact-length rules must actually reject invalid values. When concurrent submissions are explicitly permitted, submitting remains true until all finish.

Verify dynamic initial values and custom rules execute in preview: a nested `{{ ... }}` binding inside `initialValues` or `rules` must be a native expression, not literal text. When uniqueness is required, test an existing key and a distinct key; for a numeric range, test its valid and invalid boundaries, including decimals according to the business rule. When a footer submits through a Form ref, test a form remount or reopening with another record so stale refs cannot silently bypass validation or submission.

Generated/dependent values follow [business outcome cases](../../../design/component-policy.md#business-outcome-cases): read native Form values/refs, implement the source calculation and test changed inputs, repeated actions and conflicts. Required-only rules/help text do not implement that behavior.

When correcting an existing Form, move controls into real Item children Slots to preserve UUIDs and applicable interactions. Replace manual field-error state and value-based submission handlers with native Form values and validation; remove obsolete wrappers and handlers. For adjacent controls/actions follow the direct-control and nested noStyle Item rules in [Form Field](form.md#field-instructions).

### Events and ref actions

Read the component's registered `refActions` and ordered `args` before invoking a Form ref. `args: []` means no parameters; missing `args` means the signature is unknown. Ref keys use camelCase node names, such as `$refs.createForm` for `CreateForm`. A footer calls the verified submit action; only the validated Form event performs the business mutation.

Read the registered Form event argument names/types and use the returned submit argument; do not invent a separate data context for submitted values. When renaming a Form, reread submit/cancel ref bindings so the renamed Form remains callable.

Navigation after successful validation uses the native navigation interaction on Form onFinish, deriving its destination from validated values. The submit button calls Form submit and has no unconditional href. Discover the current schema; if this native action is unavailable report the blocked operation without upgrading the editor as part of a design task.

Use the [submission example](../../../desktop-examples.md#form-submission-and-record-context) for destination checks. Reopening another record requires verified reset/set-fields behavior; changed initialValues alone do not prove Form state resets.

### Project inventory and acceptance

Derive expected Forms and fields from the submitted business workflow before generation. The absence of Form nodes in output cannot justify a notApplicable gate or moving submitted fields into standalone-control exemptions. Those exemptions cover independently owned controls such as query inputs/SQL editing, not a missing business Form. Full suites use explicit per-Page inventories, including empty lists only where the reviewed source has no submitted field group.

Prefer `{"path":"/records","forms":[...]}` for each Page in reusable inventories. The gate resolves the exact `pageMeta.path` from overview to the current UUID. A unique `name` or explicit `componentUuid` also works; if multiple selectors are supplied they must agree. Missing, ambiguous, empty or duplicate resolutions fail; a miss does not silently fall back to an old UUID. Omit UUIDs from inventories shared across projects. Semantic keys such as `list` require an explicit path/name mapping. See [unified verification](../../../verification.md) for collecting evidence and running all applicable gates.

For full-project generation or a form inventory audit, inventory every project Page, business Form and field across inactive Tabs and Modals before editing. Pages without business Forms still declare `forms: []`. Record field keys, labels, required/whitespace/business rules and tooltip content independently of the generated output. Run `python3 scripts/verify_forms.py <expectations.json> <mcp-read.json> --overview <mcp-overview.json>` against full public MCP readbacks and again after save/reopen. The overview must cover the entire project. This mandatory gate rejects missing/extra Pages, Forms or fields, unowned editable controls, competing values, label stars, separate field-help Tooltip/buttons/icons, manually bound field-error blocks and advanced validators stored as literal strings. Declare genuinely standalone controls, such as a separately validated SQL editor, in each Page's `standaloneControls: [{nodeName: "SQLEditor", reason: "Separate SQL validation workflow"}]`; entries must be named, unique, used and outside business Forms. SearchForm Items retain their own control ownership. The static scan checks model patterns and contracts; runtime validation still requires preview acceptance.

Run the component-specific Form/Item and Modal checks as applicable. Review the combined region in editor and real Preview: label/control/instruction alignment, native errors, validation expansion and reachable footer at the requested viewport. Save/reopen and reread model ownership and bindings. Record model, geometry and runtime outcomes separately.

### Focused form edits

For a local field/validation/layout change, inspect the entire affected owning Form and relevant hidden branches against the current requirement, preserving unrelated Pages. Check control ownership, values/rules, submit/ref actions and actual error/save/reopen behavior. Run the full-project verifier only with a complete reviewed inventory and overview; do not trim the overview or claim a full-project pass from a partial check. Full regeneration continues to require the complete inventory gate above.

### Form.Item

Installed Form Field/Form.Item contracts own field names, rules, labels and controls.

#### Label help

Field-label explanations belong in the real Form.Item `tooltip` prop/Slot. Keep the label plain and let Form.Item place its native help icon beside the label; do not build a separate Tooltip/button beside the control or type an `i`/question mark as an icon. Advanced Form Fields expose editable tooltip content; simplified Form fields expose tooltip text in their field configuration. Read the installed contract first. If tooltip is absent, report the missing public contract and leave that requirement unresolved; an ordinary design task does not update registrations or publish libraries.

For each field tooltip, verify the native icon is in the label, hover opens the expected content, the control remains usable, and clearing tooltip removes the icon. Recheck editor, actual preview and saved readback. Do not force persisted open state for inspection. Verify required indicators and tooltip coexist without duplicate marks or a second label model.

#### Field instructions

Triage every piece of field copy before choosing a Slot or a component:

| Question | Decision |
| --- | --- |
| Does the user need to perceive this text at all, or is it requirement/implementation description? | Not user-facing: render nothing. Record the text in the field's `excludedCopy` with its source quote so the omission is reviewable. |
| Must it be visible while entering the value (format, range, constraint)? | User-facing now: use an inline instruction for a short note beside a compact control, or `description` for one short line below. |
| Is it background, definition or rationale the user opens on demand? | User-facing on demand: use the label `tooltip`. Never paste it as a persistent description. |

Record the decision as `copyTriage` on the field — `perceive-now`, `perceive-on-demand` or `not-user-facing` — and keep it consistent with what the model renders: a `description` requires `perceive-now`, a `tooltip` requires `perceive-on-demand`, and `not-user-facing` may render neither and must cite the excluded text. A tooltip adds a help icon to the label, so the measured shared label width must include that icon.

Decide instruction placement before choosing a Slot. These are field-specific instructions, not the form’s horizontal/vertical layout. Use the requirement, actual control width, expected text length and measured space at the target viewport; do not automatically place every instruction below the input or rely on a fixed character-count threshold.

| Condition | Placement and component contract |
| --- | --- |
| Short, supplementary instruction next to a compact control, with enough width for the complete control, 12px gap and complete instruction | Place after the control in the same row; vertically align with the control. Form.Item `extra` has no native placement switch: do not invent `extraPosition` or reposition internal DOM. The Antd6 wrapper forwards value/events to its first direct control. For compact inline instructions, keep that control first and add registered secondary Typography.Text in the same `children` Slot. Native Form `styles.content={display:"flex",alignItems:"center",gap:12}` applies form-wide; verify every field supports it and that errors/extra retain their native layout. Do not apply it to unrelated full-width/stacked fields. Verify the installed contract. Never put Flex between a named Item and its control without the nested Item. Native React codegen follows Ant Design’s [complex form control](https://ant.design/components/form/#components-form-demo-complex-form-control), not the wrapper’s forwarding behavior.

Below-control instructions use `description` (advanced Slot, simplified text), mapped to native extra below controls/errors with theme secondary typography. Inline instructions use the same hierarchy, a 12px control-to-text gap and complete readable text. Keep one approved instruction; remove obsolete siblings/extra when moving it. Persistent instructions must not use `help`, which replaces errors, or input suffix. If space is insufficient, place instructions below rather than shrinking controls, clipping text or forcing nowrap.

Record `description`, `descriptionPlacement` (`below` by default or `afterControl`) and, for inline text, `descriptionNode` in the independent field inventory. These are acceptance expectations, not new component props. Read back native ownership and secondary Typography, then verify actual normal, empty, invalid and corrected states: one error below the control, persistent instructions at the approved location, no duplicate text, no crowding/overlap, and no vertical shift of inline text when an error appears. Recheck after save/reopen. A correct Slot or screenshot of the initial value alone does not pass this acceptance.

#### Validation order

Show one actionable validation error per field at a time. Use native `validateFirst=true`, with required/blank checks first, format/type/range checks next and business/remote checks last. The Antd6 Form Field wrapper defaults to this ordered short-circuit behavior and exposes the actual prop; Ant Design itself defaults to collecting errors. Do not hide the second error with CSS or slice displayed messages after all rules run. Inventory the expected `validateFirst`, instruction text and placement, verify saved props/Slots, then test an empty value, a nonempty invalid value and a corrected value: exactly one native field error in each invalid state, persistent instructions remain visible, and correction removes the error.

Follow [layout ownership](../compositions/form-layout.md#layout-ownership): wide page forms default to horizontal labels, narrow Modal/Drawer forms to vertical. Record mandatory `formLayout` and a concrete `layoutReason` for exceptions before generation. `verify_forms.py` checks explicit native layout and width ownership even without Grid expectations. Align native descriptions/errors with controls; verify actual geometry instead of inheriting template label spans.

For one horizontal field, use native content-sized label columns (`labelCol.flex="none"`, `wrapperCol.flex="1"`) when supported. Do not reserve width for an absent Tooltip or longer template fields. Stacked fields can share width measured from actual labels, required indicators, punctuation and configured Tooltips. Verify colon-to-control spacing, especially with left-aligned fixed labels. Preserve native punctuation/spacing; no empty nodes, negative margins or internal CSS overrides. Measure normal, required, configured/empty Tooltip and validation-error states after save/reopen.

Use the registered dependencies/shouldUpdate, hidden, preserve and noStyle contracts according to the actual Form mode. Decide whether each field remains valid, is cleared or is excluded from the payload when its prerequisite changes. Use [Pagination](pagination.md) and the matching query composition for the actual configuration.

Choose one ownership mode before binding. For local data with component-owned paging, `pagination:{defaultPageSize:20,showSizeChanger:true,pageSizeOptions:[20,50]}` initializes an editable pager without freezing its size (values here are illustrative). If application state owns paging, bind `pagination.current` and `pagination.pageSize` to the existing states and update both from the registered Table `onChange` argument `pagination.current` / `pagination.pageSize`. Reset current on the source-defined filter change. A constant `pageSize:20` is a controlled value, so displaying a size changer does not make size changes work. Verify the installed contract before using this pattern, and check resulting rows as well as the pager label.

For selection, bind selectedRowKeys only when intentionally controlled and use the actual onSelectedRowKeysChange/ref actions. Define whether selection covers the current page, retains keys across pages, or resets after filters/mutations; the current wrapper does not certify arbitrary cross-page retention. Verify keys still identify the intended records after refresh. [Bulk-action composition](../compositions/bulk-actions.md) owns batch effects and permission handling.

### Pagination test data and acceptance

Before generation, prepare a normal initial dataset for every paginated list/Tab in scope. After its initial filters, current App/market, role and record permissions are applied, the actual matching result count must exceed the initial pageSize: at least pageSize + 1. For a 20-row page this means at least 21 matching records; 25–30 usually suffice. The raw backing array's length is insufficient when the initial visible scope contains fewer records. Empty, sparse and failed-query fixtures are separate cases and cannot replace this normal paging dataset.

Prototype fixtures may extend the supplied examples with explicitly simulated local records that obey the source fields, enums, relationships and permissions. Record their simulated nature in the task evidence; do not add debug labels or controls to the business UI. Give every record a complete, unique stable rowKey. Keep the real matching count, native total and retrievable records consistent; a larger total with only a few actual records does not satisfy this rule. With server paging, the backing query/API must really return the subsequent page. If authoritative source/access restrictions prevent sufficient permitted data, report pagination as unverified rather than inventing real records or claiming a pass.

Use the existing native paging props and runtime cases to record the initial pageSize, matching count, active scope/filters and distinct expected record IDs before composition; do not derive these expectations from the finished screenshot or create another data schema. If a larger pageSize must also support a tested page turn, prepare enough matching records for that tested size too.

In real Preview, scope assertions to the actual Table and its native pager:

1. On page 1, verify the first-page record IDs, rendered record count, current page, pageSize and matching total.
2. Go to page 2, verify different expected record IDs and the correct slice size; first-page records must not simply remain repeated. This must demonstrate real records beyond the first page, not just an active page-number change.
3. Return to page 1 and verify its original records and the unchanged total.
4. When a size changer is available, change pageSize and verify the resulting rows, current-page policy and total separately. Also exercise filtering/reset and scope changes under their source-defined page policy.

Retain the native assertion trace for these cases under [runtime evidence](../../../design/component-policy.md#native-runtime-evidence). Static structure and declared case names do not establish the filtered dataset size or a real page transition. A pager visible beside a short sample or a changed counter alone does not pass.

# Form layout

Read this file through `read_reference.py`: include `layout-ownership` for every Form; include `modal-form-layout` only for Forms in a Modal. All applicable acceptance requirements remain mandatory.

## Generation rules

### Layout ownership

Use real labeled inputs, Selects, Buttons and feedback. Modals/Drawers keep the full source page behind them, close unrelated menus, and retain a reachable footer. Keep destructive or unauthorized actions gated according to the source. Loading, failure, success and recovery states belong to the actual flow; do not manufacture generic state boards or placeholder future features.

Compose editable fields as a business Form; adjacent read-only summaries follow [information composition](summary-metrics.md). Keep each field’s real control in its Item children Slot while arranging the Items through registered layout components. Follow [action bars](action-bars.md#buttons-and-action-bars) for workflow ordering and availability.

Choose label direction and field columns separately before markup. Only the current user or the requirement document can make an explicit layout choice; a Pen frame, template, screenshot or previously generated page is a draft, not that choice. If a draft conflicts with these defaults, follow the defaults or ask the user. Otherwise use the defaults:

| Context | Label direction | Field allocation |
| --- | --- | --- |
| Desktop page create/edit form with short labels and sufficient width | Horizontal; native labelAlign=right with a shared labelCol width measured from the longest actual label | Three short fields per row by default; two when the measured control width does not fit three; full row for textarea, editor, Key or other long values |
| Narrow Modal or Drawer | Vertical, to preserve control width | Usually one column; pair only when realistic values, help and errors fit |
| Long labels, complex fields or narrow page regions | Vertical when horizontal labels would crowd controls | Long Keys, URLs, editors and multi-line input use a full row |

A wide overlay can justify horizontal labels; a page can justify vertical labels.

#### Columns and label width

Background and definition text belongs in the label `tooltip`, not in a persistent description. In a multi-column Form a persistent description is limited to one short line of format or range information; long explanatory paragraphs make a grid row tall and crowded, so move them to the label tooltip (the user opens it on demand) or drop them. `verify_forms.py` rejects a description longer than a short line in a three-column Page Form.

A Page create/edit Form uses three fields per row. Use two rows of two only when measured control widths show three would crowd them (`columnsReason` measurement), and cite a source for any other count. A trailing row may hold fewer than three fields; every other row holds exactly three, and a full-row field is a direct child of the layout container rather than an Item alone inside its own row.

Labels are right-aligned. Horizontal labels align on their right edge with `labelAlign="right"`; left alignment needs a source quote that states it (`labelAlignReason`). Size the shared label column from the longest real label plus its required mark and any help icon, set it as `labelCol={flex: "<measured>px"}`, and record the decomposition `labelWidth: {longestLabel, labelTextPx, requiredMarkPx, helpIconPx, paddingPx, measuredPx}` in the field inventory. Measure the real rendered label: `measuredPx = labelTextPx + requiredMarkPx + helpIconPx + paddingPx`, keeping at least 8px trailing padding. When a field shows a label tooltip its icon occupies width, so a column sized without it overlaps the control; re-measure after adding or removing a tooltip. `verify_forms.py` rejects a missing measurement, a native `labelCol` that disagrees with it, a left-aligned Form without a source, and a page Form that deviates from three columns without a measurement showing crowding. Do not inherit the registered vertical default or a template's label spans without making this decision. For one compact horizontal field use content-sized native labels; for multiple fields choose a shared label width from the longest actual label/required mark/help icon. Keep errors and descriptions aligned with controls. Do not force all fields to share one span or widen a compact control merely to remove whitespace.

Every Form and intermediate field-layout wrapper fills its allocated surface/cell through width:100% or proven stretch alignment; grid/flex children use min-width:0. A Form with align-items:flex-start does not stretch an un-sized child, and 1fr 1fr divides that child's width without expanding it. max-width:100% only caps width. Prefer full-width registered Flex and Row/Col with verified gutter/span contracts. Col occupies its intended column, not 100% of its Row. Fill each Form.Item and normal text/selection control's allocated area; keep Switch/Checkbox and deliberately compact controls content-sized. An internal wrapper must not accidentally constrain the whole form.

Record mandatory `formLayout` for every Form in the independent field inventory. A non-default direction needs machine-checkable evidence, never a prose justification:

- `layoutReason: {"kind": "source", "evidence": {"path": "/abs/requirement.md", "sha256": "…", "quote": "…"}}` — the quote must be verbatim and must itself state the label direction or column layout.
- `layoutReason: {"kind": "measurement", "labelWidth": 220, "controlMinWidth": 160, "regionWidth": 360}` — measured widths must show that horizontal labels crowd the control.

A bare string, a boolean or a partial object fails generation, and one reason object cannot be reused by two Forms. If you cannot cite or measure the deviation, change the Form to the default instead of writing a reason. Infer page versus Modal/Drawer from the actual owning model, not a claimed context. Deliberately compact text/selection controls need a field `controlWidthReason` in the same structured form — `{"kind": "measurement", "controlWidth": 180, "columnWidth": 420}` or a `source` quote that specifies the narrower control — including inline-instruction compositions; a control narrower than its column with a prose or missing reason fails generation. These are acceptance metadata, not component props. `verify_forms.py` requires the recorded direction to match explicit native props and checks all Form-to-field width paths, including unnamed wrappers, without requiring optional Grid expectations. It accepts native Row/Col allocation and provable stretch; unknown sizing remains unresolved, not a pass. Use explicit public styles when the static contract cannot prove the width, then verify Preview.

For every affected page and opened overlay, inspect real Preview at the target viewport in normal and validation-error states, then after save/reopen. Record the surface, Form, each field-layout wrapper, Item and control bounds with the screenshot. Check allocated edges after padding/gutter/label space, longest realistic values, full-row fields, equal paired columns, label alignment, readable instructions and errors without overlap. Exercise long Key/person selections. Horizontal labels alone do not fix shrinking wrappers. Model checks cannot certify these rendered measurements; missing Preview evidence leaves layout acceptance unverified.

Spacing between adjacent components has one owner. When the last Form.Item already supplies its theme margin-bottom, a following Alert/help block must not add another margin-top or parent row-gap on the same boundary. Preserve native Form.Item spacing and set the extra wrapper gap/margin to zero for that composition. If a different composition intentionally transfers spacing to the parent, remove the matching child margin instead of stacking both. Verify the rendered control/error-to-next-block distance in normal and validation-error states; checking Alert's margin alone misses parent gap and Form.Item margin.

### Modal form layout

Choose the field arrangement from the complete inventory, content lengths and filling dependencies, then select Modal width. Preserve the designated visual draft under [requirement alignment](../../../requirement-alignment.md); the following product defaults fill unspecified decisions and are not Ant Design component defaults. A wider Modal can still contain a single-column Form.

#### Width and columns

| Content and workflow | Arrangement | Desktop width |
| --- | --- | --- |
| A short basic form or fields with a strong sequential dependency | One column | Default 520px |
| Related, independently fillable short fields can be paired and pairing meaningfully reduces excessive single-column height | Two equal columns; long fields span both | Default 720px |
| Long names, Keys, text or complex controls dominate | Keep one column; widen for actual content | 640–720px |
| Two columns are justified but realistic person/entity selections, multi-selects or adjacent actions still crowd them | Two columns with full-row exceptions | 800px, with a recorded content/geometry reason |

Two columns require both a meaningful field pairing and sufficient space: after actual body padding and the 16px column gap, each control has roughly 240px or more usable width and its longest expected label/value, instruction and error fit. Field count alone does not select two columns. If that space is unavailable, use one column. Do not widen solely to make a form look larger, remove fields to reduce height, or reorder dependent inputs to fill a grid. Use one or two columns unless an explicit dense-entry requirement specifies otherwise.

#### Field allocation

| Field content | Default allocation |
| --- | --- |
| Long business names, generated/editable Keys, URLs or addresses | Full row |
| Textarea, code/rich-text editors, upload lists and complex nested fields | Full row |
| Short enums such as type/status/scenario, short numbers, single date/time | Half row when the label, control, help and error all fit |
| Person/entity Select, multi-select, date range | Decide from the longest expected content; use a full row when a half row would truncate or crowd it |
| Switch/Checkbox and fixed read-only metadata | Compact related group or information row; avoid a large empty control area |

Input component type alone does not determine column span. Pair related short fields; make an unpaired final field span the row or choose a narrower single-column Modal. Do not leave an unexplained empty half-row beside an editable field. A full-row Key with an adjacent regeneration action must reserve action space without wrapping or overlapping it.

#### Labels and spacing

Default this Modal composition to explicit Form layout="vertical": each Item's label stays above its control in both one- and two-column arrangements. Apply the layout decision and justified exceptions above. Keep native label/required/help/error ownership from [Form](../components/form.md#formitem).

Apply width ownership above to the Modal body. Use equal columns, a 16px column gap and explicit full-row spans. Verify actual component geometry rather than assuming native CSS grid properties apply to Row/Col. Preserve native Form.Item vertical spacing; do not add parent row-gap on top of it. Keep each real control directly in its Item children Slot even when the Items are arranged in a grid.

#### Header and field guidance

Keep one native Modal title that names the operation. Do not add a subtitle, workflow introduction, generic filling instructions or a repeated “Basic information” heading before the fields. Omit text such as “Fill in the basic information to enter the creation page”; express the next step through the actual native footer action under [Modal](../components/modal.md#footer).

Necessary user-facing constraints stay with their fields through [field instructions](../components/form.md#field-instructions) or [label help](../components/form.md#label-help). State only what the user needs to enter or decide; do not paste implementation notes, source-system reuse, API/uid behavior or requirement prose into the Form. A generated editable Key may need a short uniqueness/editability instruction; detailed derivation rules belong in field help only when useful to the user.

#### Layout acceptance

Before markup, record the source-selected width, native Form layout, complete ordered fields and full-row/paired allocations in the existing field/layout inventory. Keep native component props as the implementation contract. Apply [overlay structure and close behavior](modal-drawer.md#structure-and-close-behavior) for viewport limits, body scrolling, reachable header/footer and closing/reopening; apply [Modal submission](../components/modal.md#submission) for validation and pending/failure behavior.

For Antd6 Row/Col layouts, verify real gutter/span props and rendered column widths, full-row fields and ownership; the optional CSS-grid row check below does not validate Row/Col props. Form field/validation checks still apply to every layout.

For authored CSS-grid rows, additionally record `layout: {container: "NewGroupFields", modalWidth: 720, columns: 2, columnGap: 16, rows: [{container: "NewTypeScenarioRow", fields: ["NewTypeField", "NewScenarioField"]}]}` and each field's `span` (1 or 2) in the independent field inventory. Place fields structurally the way the check reads them: every row container holds exactly `columns` Items except a trailing partial row, and a full-row field (`span` = `columns`) is a direct child of the layout container between those rows, not an Item alone inside its own row container. Omit modalWidth for page Forms. `verify_forms.py` checks the Modal width, full-width stacked container and paired rows, columns/gap, complete field group and full-row/half-row placement for either label direction. A mismatch fails generation. Run before delivery and after save/reopen. Apply the Preview checks above, including invalid, corrected and reopened states and reachable native footer. Capture the opened Modal, not its background or hidden editor node. Update generation source and delivered model together when fixing a layout failure.

# Modal + Drawer composition

## Generation rules

Applies to [Ant Design v6](../index.md) registrations and theme behavior. Select the matching project library through the [library index](../../index.md) before using this recipe; another library or major requires its own verified composition rules.

Read before creating, editing or reviewing a Modal/Drawer, including result tables and read-only details. Use the actual registered component's Props, Slots, defaults and events. Read [Modal](../components/modal.md) only when using Modal; read [Form layout](form-layout.md) only when the overlay contains a business Form. Read [Actions](action-bars.md) for present action groups and [Layout](../../../design/layout.md) for bounded scrolling. A read-only detail Drawer does not require Form or Modal rules.

### Footer with only an exit button

When the native top-right close icon is enabled and usable, do not retain a footer whose sole visible button only dismisses the overlay. Remove that button and the now-unused footer; use the native close icon for dismissal. This applies to Cancel, Close, Done, Return and differently named buttons with the same actual effect. Judge the handler/state transition, not the label.

This rule does **not** remove Cancel/Close from a multi-button footer. Save + Cancel, Confirm + Cancel, and other required action groups may retain the exit button even with a header close icon. Keep native ownership through the [Modal footer contract](../components/modal.md#footer), with order and hierarchy from [Actions](action-bars.md). Do not hide native Cancel from a normal two-button Modal merely because X exists.

- Read-only results, details and help with no required business operation normally need no footer. Apply the component's actual removal contract ([Modal](../components/modal.md#footer) or Drawer footer Slot); do not leave an empty footer Slot, spacer or separator.
- A single button that downloads, submits, stops work or returns to a previous workflow step is a business action and can remain. “Return to SQL editing” is an exit-only action if it merely closes the current result overlay; it is a business action if it performs a required distinct transition. Record and verify that effect.
- Pagination, table row actions and body controls do not turn an exit-only footer into a multi-button footer. Count buttons in the actual footer only. Disabled buttons still occupy that footer; check each required runtime state when buttons are conditionally hidden.
- If no usable close icon exists, do not remove the only usable exit. Keep the supported dismissal path or enable the native icon where the requirement permits it. Do not add a custom header close icon.

### Drawer sizing

A Drawer sizes its panel through the official `width` prop (pixels); `size` is only the official `default`/`large` choice. Choose the width by the content that must stay readable without horizontal scrolling, and record the number in the overlay inventory:

| Content | Width |
| --- | --- |
| Read-only key/value detail, short help, a compact confirm | 480 |
| A Form or a Table | 640 |
| Code or SQL text, long values | 720 |

A Modal records its exact `width` in the same inventory, matching the width decision from [Form layout](form-layout.md#modal-form-layout) or the result content. Neither value may be left implicit.

### Structure and close behavior

Keep one native header/title and one footer owner. Form Modals leave at least 24px clearance at each viewport edge; constrain their outer width/height accordingly. Bound long body content using the shared scrolling contract, with the header and any business footer outside that scrolling region and reachable at the target viewport. No nested native scrolling, clipped last row or blank reserved footer after removal.

Never declare an empty `closeIcon` Slot: an empty declaration replaces the native icon with nothing, so the overlay loses its close control. Omit the Slot to keep the native icon, or place one registered Icon plus its close handler. `verify_slots.py` rejects an intended empty `closeIcon` Slot, and the overlay inventory still records `closeIcon: true`. Bind dismissal to the actual controlled open state. Available X/Cancel/Esc/mask paths follow the same dirty-input, cleanup and processing policy; closing does not imply backend cancellation. Failure preserves recoverable input. Selection/reveal must not persist an open initial state. In Preview verify close/reopen, retained business actions, keyboard focus and return to the trigger; editing also checks dirty input and processing restrictions. Save/reopen and reread after edits. For every overlay whose inventory records `closeIcon: true`, the opened Preview must visibly show the close control; confirm the same after save/reopen and record that check in the review evidence.

### Generation gate

Derive an independent acceptance inventory from requirements before generation. For each affected owning component, inventory every Modal/Drawer in its full public `baseVariantTplTree`, including hidden branches. Read referenced custom components separately; private internals need their own readback. The inventory is verification evidence, not persisted design props.

Declare the exact component identity, expected usable `closeIcon`, footer mode (`none`, `native`, `custom`) and ordered visible `footerActions`. For a native Modal footer use `nativeCancel` and `nativeOk`; for a custom footer use actual Button node names. Each action declares `effect: "dismiss"` or `"business"`; a business action needs a concrete `reason`. Optional action `props` checks required handler/visibility values from the public readback. Review effects against actual interactions; do not derive them solely from labels or generated output.

Also inventory inline `trigger` Slot roots by their ordered node names, e.g. `trigger:["OpenDetails"]`. Omitted `trigger` means `[]`: external business controls own opening and the Slot must be empty. The gate checks hidden/closed models too and rejects leftover default openers; do not accept them just because the overlay itself starts closed. Trigger ownership and footer ownership are independent.

Plan Pages by exact path (or unique name / known componentUuid) through [unified verification](../../../verification.md#reviewed-suite-configuration). Its runner resolves selectors from current readbacks. The standalone command below requires actual componentUuid values already resolved; do not fabricate UUIDs before creating Pages. Example of a resolved inventory for a read-only SQL result:

```json
{"pages":[{"componentUuid":"reviewed-owner-uuid","overlays":[{"name":"SQLPreview","component":"plasmic-antd6-modal","closeIcon":true,"footer":"none","footerActions":[]}]}]}
```

Run `python3 scripts/verify_overlays.py <inventory.json> <mcp-read.json>` using scripts from the resolved resource root, before delivery and again on saved/reopened readbacks. It rejects missing/extra overlays, mismatched footer/action inventories and a sole exit-only footer button with a usable close icon. A normal multi-button Confirm + Cancel footer must pass. Flat native Button object bindings with literal values or simple `$state`/`$ctx` property reads are inspected without execution. Quoted literal text cannot substitute for a read binding. Dynamic `disabled`/`loading` does not alter the visible action inventory; inventory action `props` can require its exact binding. Dynamic `hidden`/`style`, non-boolean hidden values, prototype keys, spreads, computed keys and unsupported expressions still fail. Conditional visibility that cannot be resolved statically fails with a request for state-specific evidence; do not execute expressions or assume dynamic configuration is hidden. For Antd6, explicit `closable: true` or an object preserves the native fallback icon even with top-level `closeIcon: false/null`; object `disabled` must be a literal boolean. Literal custom icons follow React rendering: numbers including `0` render, booleans/null/blank text do not. Nonempty custom `closeIcon` Slots cannot be classified as the native fallback; their unresolved rendered availability fails the gate. `hideFooter` must also be a literal boolean. Hidden inline CSS remains hidden with case/whitespace differences or `!important`. CSS variables, inherited/conditional visibility and other unresolved styles require rendered evidence; do not treat them as visible or exempt the gate. Nested overlay footers and trigger Slots belong to their own scope.

The gate cannot infer business meaning or execute handlers. Review the inventory and actual interaction readbacks, inspect opened overlays at the target viewport, and exercise dismissal/retained actions in each relevant state. Passing structure alone does not prove behavior or geometry.

Its geometry is: 239px white sidebar, 64px brand/header, header horizontal padding 24px, content background neutral and padding 16px. The page body fills available width and has no forced white background; SearchForm and business cards own their own surfaces. Avoid another enclosing card. Use product branding and menu evidence from the original design. Configure AppShell menuItems once as the complete nested navigation tree with href routes; put detail and creation routes under their parent with hidden=true when they must not appear in the sidebar. AppShell derives breadcrumbs and selection from Plasmic pagePath, including all menu ancestors. Never pass a separate per-page breadcrumb list or render it again in business content. Apply [admin content entry](../../../design/layout.md#admin-content-entry) for Page headings and business copy.

Use [viewport/layout rules](../../../design/layout.md) for component-owned sizing, bounded scrolling and target device geometry. The shell fills viewport height independently of the Page root height. Apply the [shell height gate and Preview acceptance](../../../design/layout.md#viewport-shell-height-acceptance) before delivery and after save/reload.

### App source context

Recognize App 来源, App Source, app_source, appSource, appId/app_id/application_id, app_name, 应用标识/应用名称, multi-App requirements and equivalent identifiers of the current work App. Record a source-backed `appContext` decision using the [context inventory](../../../design/component-policy.md#app-context-inventory). When the requirement distinguishes Apps, keep the native header AppSource control. “No App source filter/form option” removes the business field, not the shell's working context. Only an explicit current instruction excluding the top-level/global switcher overrides this baseline; do not infer it from a SQL validation or form-field restriction. A generic application title alone does not establish multiple working Apps; resolve that semantic distinction from the source.

Populate `appSources` from the requirement/authorized configuration, not demo defaults. An empty array intentionally hides the native control and cannot stand in for unrecognized context. Bind `appSource` to the same native implicit state or verified shared context used by data queries, creation, export and navigation. AppShell already exposes a writable appSource state; reuse it when appropriate instead of creating another visual selector or redundant event/state layer. If using explicit shared state, onAppSourceChange updates that state. A header-only local change is insufficient.

Inventory in-scope consumers and verify app-switch plus their context-data/create/export/navigation cases. Check initial entry, option authorization, switched data, new-object source, export target, and supported direct entry/back navigation. Keep switcher context separate from business filter reset. One authorized App is not permission to fabricate another; show its real identity and report unavailable switching coverage. Cross-page persistence follows the actual host/router contract below.

### Menu routes and context

`menuItems` is the real registered array prop. Prefer a static complete tree when destinations and visibility are static. The shell uses `pagePath` for selection/breadcrumbs and passes each `href` to the host's Plasmic Link; it does not append the current query or transfer role/environment state itself. `appSource` and `language` controls do not establish cross-page persistence.

Route matches take priority over `selectedMenuKey`: exact paths win, followed by the longest menu path at a complete path-segment boundary. A hidden `/groups/detail` menu route therefore covers `/groups/detail/<id>`, retaining its breadcrumb ancestry and highlighting the nearest visible parent. `/groups-extra` does not match `/groups`, and `/` only matches itself. Query strings, hashes and trailing slashes do not affect matching. When no route matches, the explicit selection supplies the menu path, including for menus without hrefs. Navigation expands the selected item's visible submenu ancestors. Runtime menu expansion survives page remounts within the same window for an identical navigation tree (keys, hrefs, visibility, types and nesting); users can close a branch until the next navigation reveals it again. New windows initialize from their current route. Canvas instances keep expansion local to editing and separate from runtime navigation.

For required cross-page context, first read the installed host Link/router or global-context contract. Use that verified contract, or supported bindings when the destination genuinely depends on runtime state. Record which query keys must survive, destination-value precedence, and direct-entry/back-navigation behavior; do not blindly copy all current query parameters. A role query used in a prototype is not an authorization contract. Do not document implicit preservation or a global provider that the project does not actually have.

Dynamic `menuItems` bindings are supported. The structure gate recognizes only static trees and the explicitly inventoried restricted `navigation.roleQuery` transform; other dynamic expressions remain statically unverified. Do not add an anonymous mapping expression to otherwise static menus merely as a convention. When dynamic menus are required, keep an independently reviewed tree for each relevant role/state and verify rendered visibility and link destinations in Preview. Do not execute arbitrary expressions in Python or treat an extracted static skeleton as proof of runtime behavior. See [structure acceptance](../../../requirement-alignment.md#structural-gate).

## Generation rules

设计来源为 fintechgrowthui 的 SearchForm；该来源不是任务必需的本地文件。Overseas 实现保留查询卡片、24 栅格、末行右侧操作、展开/收起、字段初始值及业务清除值语义，使用 Ant Design 6。输入控件由画布节点提供。

### 可编辑结构

Read [SearchForm.Item](search-form.md#searchformitem) for field Props, control value/event mapping and label/help Slots.

`plasmic-overseas-search-form` 的 Fields (`children`) Slot 放置 `plasmic-overseas-search-form-item` 实例。一个实例代表一个字段，字段顺序就是画布节点顺序。插入、复制、删除、移动和修改通过 Studio/MCP 的现有节点操作完成，无独立的字段数组或另一套简化模式。

SearchForm 提供 Extra actions (`extraActions`) Slot，用于查询辅助操作，位于查询/重置之后。新建、导入等业务动作按[列表组合](../compositions/search-table.md#query-and-list-structure)放置，不因存在此 Slot 就放入查询操作列。内置按钮文本通过属性编辑，其行为固定为提交和重置。

### 布局与状态

先按[业务内容与视觉适配](../../../requirement-alignment.md#content-before-presentation)确定完整筛选字段，并在现有 `components` 清单中逐项记录 Item 的业务键、标签、来源和 SearchForm Slot 归属，再选择列数。列数只规定排版密度，不限制字段总数；不能通过漏项、删项、合并不同字段或移到无关的全局控件来凑满一行。超过一行的字段保留真实 Item，由原生换行与折叠承接；需求明确移除字段时才更新字段清单。

常规生成只有四列和三列两种模式。`colSpan` 是每个字段占用的 24 栅格份数，不是列数：四列写 `colSpan=6`，三列写 `colSpan=8`；不能把“四列”写成 `colSpan=4`。

生成前按以下顺序选择，后续调整使用同一依据：

1. 需求文档明确规定列数或栅格时按文档执行；四列、三列以外的配置也必须有该文档的明确要求，并按[来源例外](../../../design/component-policy.md#protected-configuration)记录原文、哈希和属性覆盖。
2. 文档未指定时，只有视觉稿的筛选字段明确排成多行、每行按三列对齐，才选择三列 `colSpan=8`。读取原图，在现有 reference-region `decision` 中记录画板、视口和多行三列的观察。只数筛选字段，不把查询/重置操作当成字段；末行不满时仍按三列对齐。
3. 其他情况固定选择四列 `colSpan=6`：包括没有视觉稿、布局不清楚、单行三个字段，以及视觉稿显示其他列数。其他列数只是无效的视觉输入，忽略该排列并按四列重排，不照搬为新的模式，也不为了把所有字段塞在一行而压窄列宽。

在生成前的 `components` 中记录选定的真实 `props.colSpan` 和来源；三列是受支持的常规模式，不需要伪造需求文档来申请例外。静态脚本核对模式与保存值，不能证明原图确实满足“多行三列”，该判断保留原图证据并独立审查。原生 API 的其他栅格值保留给需求文档明确要求的例外，不作为模型自行选型的候选。

两种常规模式均采用 `minRows=1` 和运行态初始 `collapsed=true`，Item 不覆盖 span，继承选定列宽。选择三列不代表初始展开或常驻多行；这些初始状态只有明确需求才允许覆盖。动作使用末行剩余栅格；末行占满时换行。超出 minRows 时提供折叠；折叠至少保留第一个字段。小屏保持原组件 xs=24、sm=12、md=指定 span 的响应式栅格。

`Item.span` 优先于 `Form.colSpan`，因此检查每个字段的有效 span，不能混合三列与四列模式。跨列例外须有需求文档明确要求，在生成前按 Item 声明 `props.span` 和有真实文件、原文、哈希的 `overrides.span`。日期区间、长 placeholder、字段数量或可用空白都不自动授权跨列；不能先扩大字段再改期望清单放行。栅格 span 不是固定像素上限，实际宽度仍取决于容器、gutter 与 labelWidth；后者按最长真实标签测量，不冻结为示例数值。

`labelWidth` 是可选的共享标签栏宽度，单位为 px，没有固定默认值；选中 SearchForm 后在属性面板的 Label width 中修改，导入库的契约必须包含它。

未配置 `labelWidth` 时，各标签按内容宽度显示；配置后所有 Item 使用共享宽度。生成前检查全部标签，包括初始折叠字段、自定义标签、必填和帮助标记、组件生成的冒号及其原生间距；按实际字体和最长标签选择足够的单行宽度，并确认目标视口仍有可用的控件空间。标签变化后重新评估整个表单，不把页面选择的宽度写入组件默认值。标签使用纯文本，不手动追加冒号、空格或 CSS 偏移来补偿窄标签栏。

编辑器强制展开时必须显示“收起”、向上指示和 `aria-expanded=true`；Preview 使用实际 collapsed 状态。检查短/长标签的控件起点、完整单行文字、冒号到控件的原生间距，以及双向展开/收起；清除 labelWidth 后恢复内容宽度，不裁切或省略标签。

卡片使用主题背景和边框，内边距 16px/20px、圆角 8px，默认下间距 16px；父级已有 gap 时设置 marginBottom=0。`embedded` 移除卡片和外间距。className 接收画布样式。

编辑画布展示全部字段，便于选取和修改；交互预览/运行态遵循 collapsed。折叠仅隐藏列，字段不卸载，初始值、校验和提交均包含折叠字段。若折叠区字段校验失败，表单请求展开，以显示可修改的错误字段。

初始值优先级为 Item.initialValue > Form.initialValues > Item.clearValue，保留 0、false 和空字符串。运行中的初始值用于初始化及重置，不覆盖用户当前草稿；编辑器修改默认值会更新字段预览。重置先恢复初始值，再用明确设置的 clearValue 覆盖；输入清除至 null/undefined 也恢复 clearValue。

`onSearch(values)` 在校验通过后返回全部已注册字段；`onReset(values)` 返回重置后的值；`onValuesChange(values)` 提供当前草稿（包含折叠字段），对应 readonly `values` 状态。查询不会自动改变应用的数据；页面交互将提交值赋给 appliedFilters 并将 page 设为 1。重置事件做同样的应用状态更新。`collapsed` 为可写状态；ref actions 为 `submit()`、`reset()`、`setFieldsValue(values)`。

### 页面生成

每个查询字段默认提供可见的 `label` 或真实 `labelContent`，包括关键词输入；placeholder 仅作为输入提示，不能替代标签，也不能为了给输入框更多空间而把 label 清空。标签文本从业务字段含义确定，并重新测量整个表单的 labelWidth。明确要求无标签的特殊搜索入口需在 source-reviewed Item 的 `props.label:""` 和来源中单独声明；参考图中只有 placeholder 不自动构成这一例外。

标准列表保留 `minRows=1`。只有需求明确要求初始展开并保留收起按钮时，才通过来源例外设置 `collapsed=false`，不要通过增加 minRows 实现初始展开。五个 span=6 的字段跨两行：minRows=1 显示展开/收起，minRows=2 会使两行全部成为常驻区域而不显示按钮；只有明确批准常驻两行时才在计划中声明后者。编辑器强制展示全部字段与运行态的折叠设置分别验收。

后台四列组合（colSpan=6、minRows=1）只有三个普通字段时，查询/重置位于同一行第四格，不显示多余的展开控件。检查 Item 的实际 span；日期范围等较宽控件也保持继承，只有明确的来源例外允许跨列，可用空白不构成修改理由。

列表查询区统一使用 Overseas SearchForm，按需求插入真实 Item 和 Antd6 控件，默认四列 colSpan=6。不得生成另一套原生查询网格、重复查询按钮，或不可编辑的 fields/element JSON。生成前读取目标已安装 Overseas 和 Antd6 契约；依赖准备遵循[库选择](../../index.md)，缺少能力时明确报告，不把组件升级或发布作为默认修复。字段增删排序使用节点操作，查询/重置事件接页面状态。

## Generation rules

Read the registered @react/ui ActionGroup contract. Pass complete permission-filtered items and let the component fold them. **max=3 is the mandatory generation baseline**, including More as one of those three positions. Only an explicit current-user/source requirement may override it with [verifiable source evidence](../../../design/component-policy.md#protected-configuration). The number of actions, a wider viewport or the wish to show all buttons is not an exception. Do not truncate the authorized items; retain them in native folding. Rows with fewer authorized actions naturally show fewer controls. ActionGroup uses Antd6’s medium size spelling. [Column](../../antd_v6/components/table.md#operation-column-sizing) owns operation-column measurements.

PC More menus default to dropdownProps.trigger=["hover"]; explicit click/touch requirements and trigger-specific acceptance follow [Dropdown](../../antd_v6/components/dropdown.md). Preserve ordering and danger/disabled behavior after permission filtering and folding.

When the requirement calls for confirmation, row items declare confirm with title/description/okText/cancelText; for those items, onAction fires only after confirmation. Follow [row confirmation](../../antd_v6/compositions/action-bars.md#feedback-and-row-confirmation) for Popconfirm anchoring and business effects. Verify cancel/confirm, repeated use and no mutation before confirmation for these actions in real Preview.

Before handlers, follow [permission generation and acceptance](../../../design/permissions.md) and declare [actionContracts and cases](../../../design/component-policy.md#business-actions-and-transitions): every key, allowed roles/record scope, confirmation and transitions. ActionGroup renders supplied items; it does not infer authorization. The same current-context decision must filter items and guard execution/confirmation. Verify permitted non-administrator actions, rejected submissions and revoked-context confirmation outside the business UI. Enable/disable and different retry origins retain separate source-derived cases. Dynamic items remain runtime-unverified until cases execute.

Navigation uses item href so the registered Plasmic Link performs routing; onAction is for local actions, not window.location replacement. Save/reopen and reread the delivered items, triggers and handlers.
