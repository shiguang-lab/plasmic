# Local canvas previews

Dashboard cards request previews only while intersecting the viewport in a visible browser tab. A tab-wide queue deduplicates project requests and permits one temporary rendering iframe at a time. Leaving the viewport, hiding the tab or unmounting the card removes its subscription; the last subscription aborts the request and destroys its iframe. Jobs have a 90-second deadline and yield between projects.

The isolated engine owns project loading, unbundling, code generation, component registrations and rendering. The parent receives only transferred PNG bytes. The engine is a separate Rsbuild output at `/canvas-preview/index.html`, built after the main application by `pnpm build`; its pure rendering imports do not initialize Studio UI. The host scaffold also mounts at that path. The iframe stays in the viewport with zero opacity so WebKit continues rendering animation frames; it is inert and cannot receive input. The iframe must be served on the Dashboard origin; its JS/runtime assets may use the configured static origin.

The preview covers the first nonempty saved free canvas, retaining artboard positions and saved variants/props. Projects without a free canvas use the widest frame per page, laid out in two columns. All selected artboards fit inside a padded 640×360 image. Each board renders and decodes its SVG at the original CSS viewport, then draws directly into a canvas at its final thumbnail size. Only one source image is decoded at a time; full-size PNGs are not retained. CSS viewport units retain the source artboard size; media queries are evaluated at that size. Closed runtime overlays and content beyond a page's scroll viewport retain their authored initial state.

Only final PNG ArrayBuffers are stored in IndexedDB, partitioned by user, project and build. Every request first checks current project permissions and revision through the existing metadata endpoint. A revision mismatch regenerates the image on demand. The cache holds at most 64 entries and 16 MiB, evicting least recently used images. No thumbnails are uploaded and no server browser is started. Storage failures leave previews usable for the current view. The thumbnail region shows an animated skeleton until the image loads, or a static skeleton after failure. Project metadata remains visible below it.

Bitmap handles are closed, encoding canvases are zeroed, React content is cleared and the iframe realm is discarded. Cards revoke Blob URLs when leaving the viewport or unmounting. Browser native caches/allocator pools can keep process RSS above baseline after these resources are released; JS/DOM cleanup is not a guarantee that the OS immediately reclaims all browser memory.

Enable through `dashboardCanvasPreview`; this self-hosted repository enables it in its default overrides. Cross-origin assets require readable CORS responses. Canvas 2D and SVG charts are captured; tainted canvases fail. Arbitrary WebGL, cross-origin iframe content, shadow DOM and video require component-specific export support. CSS/native form rendering can differ across browser engines. The renderer uses the client main thread, so serial execution does not remove codegen long tasks.

Unit checks: `vitest run src/wab/client/components/dashboard/preview src/wab/client/components/ProjectListItem.test.tsx`.

The `tools/dashboard-preview-probe/production.cjs` and `production-memory.cjs` tests exercise the production renderer and card component with read-only local fixtures at port 3218. Fixtures and resulting images remain outside the repository.
