# UI languages

The application supports English (`en`), Simplified Chinese (`zh-CN`), Traditional Chinese (`zh-TW`), Japanese (`ja`) and Korean (`ko`). Each selectable language has its own JSON message pack, checked for equal keys and interpolation parameters.

`useI18n()` provides `t(message, values)`, `label(displayText)`, the resolved locale, and the language preference. English source messages are typed keys. Add a new message to every language pack before using it. UI translations must not change persisted component props, node names, registration metadata, or business page content.

The initial preference is `system`. The desktop preload supplies the operating system's preferred languages; the web application uses `navigator.languages`. The first supported language wins; unsupported languages fall back to English. Chinese script tags take precedence over regional tags. Manual choices and an explicit return to `system` are stored in `localStorage` under `shiguang.ui.language`, and restored before the first render. Storage failure is reported by the language selector without claiming the preference was saved.

The shared external store updates all React roots, including independently rendered popups. The Ant Design provider uses the corresponding component language pack and updates the document's `lang`. Browser storage events synchronize windows. The top frame sends its resolved UI locale through the existing Comlink connection before mounting the host editor; host frames follow subsequent changes and do not store a second preference in the custom app host's origin.

Studio menus, sidebar controls, common dialogs and generated presentation captions use this layer. `<UiText message="…" />` subscribes independently so module-level JSX and memoized views update when the language changes. Use complete messages for sentences with changing states or interpolated names. Helpers that accept UI message keys must type them as `MessageKey` and translate them at the rendering boundary, including operation labels and empty states. Shared widgets must localize their default captions while preserving caller-provided content.

Language-pack parity checks only validate registered messages; they do not detect untranslated UI. Verify rendered prompts and shared widget defaults in every supported language, including empty states and language changes while open. Default names may be localized when a prompt opens, but changing the UI language must not overwrite user input or existing project, organization, or workspace names.

`label()` and `<UiLabel text={displayText} />` translate known editor presentation captions. Do not use them for component property metadata. Unknown captions retain their original text. Insertable built-in captions and their search terms use the same translation; user-authored component names and item keys remain unchanged.

Component property names, slot names, registration descriptions, help text, choice captions, choice groups and registered action labels retain their English registration wording across UI languages. Empty hints, clear actions and editor menus follow the selected UI language. Stored property names, enum values, CSS values, defaults and business content remain intact; editable CSS input shows its original value.

Desktop bundles these JSON packs and the shared locale resolver with its renderer assets. The trusted Studio main frame sends the resolved locale to the desktop process, which refreshes native menus and broadcasts it to the update, login and MCP dialogs. Native dialogs read the same Studio preference; they do not persist a second language setting.

Run `pnpm --dir platform/wab i18n:audit > /tmp/studio-i18n-audit.json` from the repository root to inventory source candidates across Studio, including generated presentation files. The AST audit reports JSX text, UI attributes and object options, widget defaults, notifications, conditional branches, local string variables, and untranslated fragments inside interpolation values. Parse errors fail the audit. The scanner tests and UI regression tests cover these distinct paths.

Candidates require review: English component contracts, code snippets, URLs, brand names, sample/user data, and captions translated by a downstream renderer are intentional. The report does not assert that every candidate is a leak or that an empty report proves runtime coverage. Cross-file metadata, strings returned by helpers, third-party widget defaults and server responses also require inspection at their rendering boundary. Check the relevant dialogs and state transitions when changing those paths.

API errors retain their class, HTTP status and structured validation fields through `deserializeApiError()` in both AJAX and fetch requests. `showError()` classifies expected API failures as business warnings, with localized titles and reviewed reasons. `ErrorDescription` subscribes to the UI language for open notifications and inline errors. Unknown API diagnostics use a localized status-specific explanation; the original Error retains its diagnostic text. Expected 4xx errors are not reported as unexpected exceptions. Server failures and unavailable services keep their separate classifications.

Run `pnpm --dir platform/wab i18n:audit-errors` to inventory server/shared error sources, permission checks and raw message sinks in the Studio client. This report also includes technical component and tool diagnostics, which must be reviewed in context rather than blindly translated.
